11 把循环收进 `Agent.invoke`，12 给 Action 补了上网。系统提示词从 06 起就是一份静态身份 + 环境快照，11 收成「编程助手」。业务场景一多，这份身份会无限变长。06 的纪律是**精简**：场景限定、单次任务的指令不要写进 system。13 要收的就是：场景专属指令按需加载，而不是一股脑塞进 system。名字叫 Skill。

考虑下面的场景，提示词该如何编排？

- 在 SaaS 系统中，用户**有时候**需要对销售数据分析，数据分析时，需要告诉模型：
  - 从哪里获取销售数据？
  - 数据有哪些字段，每个字段是什么含义？
  - 有哪些常见的分析方式？
  - 如何根据用户的需求选择合适的分析方式？
  - 分析结果用哪种形式展现？
  - ...
- 在智能客服系统中，用户会**经常**询问关于产品的信息，则需要告诉模型：
  - 我们有哪些产品
  - 每个产品的参数、特点、用法、注意事项、价格、活动、购买链接、建议组合...

如果在系统提示词中，完整地塞入这些内容，会导致严重的提示词膨胀。

而实际上，像这些提示词只有在某些场景下才会触发。因此，我们可以用更加优雅的方式完成提示词的注入。

## Skill 是什么

Skill（技能）：一套**可插拔的专业提示词模块**。每个 Skill 对应一个特定场景（越权提问、数据分析、客服应答、某种 UI 风格……），只有用户问题匹配该场景时，完整指令才进入上下文。

它不是 09 那种 Tool。Tool 是对外行动（读文件、跑命令、搜索）；Skill 是给模型看的流程 / 约定 / 领域知识。模型可以**用工具去加载**一份 Skill，但 Skill 本身不是函数。

| | Tool（09） | Skill（13） |
| --- | --- | --- |
| 是什么 | 可执行函数 | Markdown 指令 + 可选脚本 / 参考资料 |
| 进上下文的方式 | `session.tools` 里每轮都带 schema | 平时只带 name + description；正文按需加载 |
| 目的 | 让模型能动手 | 让模型在特定场景下按约定做事 |
| 和 06 的关系 | 不占 system 正文 | 避免把场景手册写进 system |

加载是**渐进披露**（progressive disclosure），不是一次读完：

| 层级 | 装什么 | 何时进上下文 | 代价 |
| --- | --- | --- | --- |
| 元数据 | YAML 里的 `name`、`description` | 会话开始，写进 system 的目录 | 每个 Skill 大约几十到一百 token |
| 指令正文 | `SKILL.md` 分隔线后面的 Markdown | 模型判断「当前问题匹配」之后 | 建议整份不超过约 5000 token |
| 附属资源 | `scripts/`、`references/`、`assets/` | 正文里点名、模型再去读或执行 | 不读就不占窗口 |

官方约定（[Agent Skills 规范](https://agentskills.io/specification)）：一个 Skill 是一个目录，里面至少有 `SKILL.md`；`name` 必须和目录名一致；`description` 既要写**做什么**，也要写**何时用**——模型只靠这一句决定要不要加载正文。

```text
skill-name/
 ├── SKILL.md          必填：YAML 元数据 + Markdown 指令
 ├── scripts/          可选：可执行脚本
 ├── references/       可选：详细文档，按需再读
 └── assets/           可选：模板、静态资源
```

Claude Code 一类实现里，第二层常常就是模型自己用 Read / Bash 去读那份 `SKILL.md`。也可以做成一个专用 `use_skill` 工具：参数是名字，返回正文，再以 `role: tool` 追回会话——和 09 的 Observation 同一条路。这篇代码做的是第一层：扫描目录、把清单注入 system。第二层在试跑里靠已有的 `bash_command` 读文件完成，**没有**单独注册 `use_skill`。

和前面几篇的对应：

| 理论 | 含义 | 这篇里 |
| --- | --- | --- |
| 目录（第一层） | 模型先知道「有哪些、何时用」 | `list_skills()` → `system.j2` 的循环 |
| 触发 | description 和用户问题匹配 | 模型自己判断；提示词要求匹配时去加载 |
| 正文（第二层） | 完整指令进入当前轮次 | 试跑里 `bash_command` 读 `SKILL.md` |
| 身份仍静态 | 06：system 不塞场景手册 | system 只增加 Skill **机制** + **目录**，不增加各场景全文 |

相对 11 的系统提示词：角色、环境段没变；多出来的是 `# SKILL` 这一整段，以及渲染时多传一份 `skills`。

| 11 | 现在 | 为什么 |
| --- | --- | --- |
| system 只有角色 + 环境 | 增加 Skill 机制说明 + 可用清单 | 模型必须先知道有目录、怎么加载 |
| `render_prompt` 只注入 cwd / os / is_git | 再注入 `skills=list_skills()` | 模板多了循环，忘了传就会像 11 里 `os` 空着 |
| 场景规则要么不写、要么写进 system | 规则放在独立 `SKILL.md` | 满足 06 的精简；清单可以很长，正文不必常驻 |

下面按依赖落地：Skill 文件 → 模板只塞目录 → `prompt.py` 扫描并渲染 → 试跑。

## Skill 文件

约定放在 Agent 包旁边：`agent/.agent/skills/<skill-name>/SKILL.md`。一个目录一个 Skill；没有 `SKILL.md` 的目录扫描时跳过。

YAML frontmatter 在文件最上面，两行 `---` 夹住。规范要求至少 `name`、`description`。后面的 Markdown 是第二层正文，**不**在会话开始时注入。

`agent/.agent/skills/no-permission/SKILL.md`：

```markdown
---
name: no-permission
description: 当用户和你和开发无关的问题时，使用此技能
---

统一回复：“我是一个编程助手，我无法回复你这个问题，请把话题限制在开发领域”
```

| 部分 | 进哪一层 | 作用 |
| --- | --- | --- |
| `name` | 目录 | 和文件夹名一致；模型加载时用这个名字找目录 |
| `description` | 目录 | 触发条件。写得越具体，越权提问才不会漏、开发问题才不会误伤 |
| 正文那一句统一回复 | 第二层 | 真正的行为约束。只看 description，模型还不知道要说哪句话 |

这个例子把「何时用」写进了 description，正文极短，适合验证「匹配 → 加载 → 遵守」。销售分析、客服手册会把字段、流程、输出格式写在正文里，甚至拆到 `references/`，机制相同。

> **说明：** `description` 按规范还应带「做什么」。这里几乎只有「何时用」，能触发，但模型在加载正文之前不知道加载之后要干什么。正式 Skill 两句都写，例如：「拦截与开发无关的提问并统一拒绝。当用户问天气、新闻、闲聊等非开发问题时使用。」

## 渲染时扫描 Skill

06 的 `prompt.py` 封装的是：采集运行时环境 → 填进 Jinja。10 加了 `os`；11 模板改成中文，占位符没少。调用方从 10 起只写 `render_prompt("system")`，`Session` 构造不用改。

13 还要往模板里塞 Skill 目录。环境采集原样保留；新增的是「启动时扫一遍磁盘上的 Skill，只把元数据交给模板」。全文仍由这一次 `render_prompt` 产出，system 在会话开始时写死——和 cwd / os 一样，是**当时的快照**，不是每圈重扫。

封装了什么、为什么：

| 原先在调用处或模板里的 | 收进 `prompt.py` 之后 | 为什么 |
| --- | --- | --- |
| 手写「有哪些 Skill」 | `list_skills()` 扫 `SKILL_BASE_DIR` | 增删一个文件夹，下次新建 Session 就会出现在目录里 |
| 把整份 `SKILL.md` 拼进 system | 只解析 YAML，把 `{目录名: meta}` 传给模板 | 第一层只要 name + description；正文留在磁盘 |
| `render_prompt` 只传 cwd / os / is_git | 增加 `skills=list_skills()` | 模板多了 `skills` 循环；11 写过：占位符多了，render 必须把值传进去 |
| 调用方关心 Skill 目录结构 | 仍只调 `render_prompt("system")` | `Session` / `Agent` 一行不用改 |

需要 PyYAML 解析 frontmatter（06 还没有）：


`agent/prompt.py`：

```python
import os
import yaml
import platform
import subprocess
from pathlib import Path
from jinja2 import Environment, FileSystemLoader

SKILL_BASE_DIR = Path(__file__).parent / ".agent" / "skills"

def get_cwd() -> str:
  return os.getcwd()

def get_os() -> str:
  return platform.system()

def get_is_git() -> bool:
  result = subprocess.run(
    ["git", "rev-parse", "--is-inside-work-tree"],
    capture_output=True,
    text=True,
    timeout=5,
  )
  return result.returncode == 0 and result.stdout.strip() == "true"

def list_skills() -> list[dict]:
  if not SKILL_BASE_DIR.exists():
    return []

  skills = []
  for skill_dir in SKILL_BASE_DIR.iterdir():
    if not skill_dir.is_dir():
      continue
    skill_file = skill_dir / "SKILL.md"
    if not skill_file.exists():
      continue

    content = skill_file.read_text(encoding="utf-8")
    parts = content.split("---")
    if len(parts) >= 3:
      meta = yaml.safe_load(parts[1])
      skills.append({skill_dir.name: meta})

  return skills

def render_prompt(prompt_name: str) -> str:
  template_dir = os.path.join(os.path.dirname(__file__), "prompt")
  env = Environment(loader=FileSystemLoader(template_dir))
  template = env.get_template(f"{prompt_name}.j2")
  return template.render(
    cwd=get_cwd(),
    os=get_os(),
    is_git=get_is_git(),
    skills=list_skills(),
  )
```

`get_cwd` / `get_os` / `get_is_git` 与 10 相同，不必当新逻辑读。新的是 `SKILL_BASE_DIR`、`list_skills`、以及 `render` 多出来的那个关键字参数。

`list_skills` 在干什么：

```text
agent/.agent/skills/
  no-permission/
    SKILL.md          ← 有这个文件才收
  某个空目录/         ← 跳过
  某个.txt            ← 不是目录，跳过
```

| 步骤 | 代码 | 作用 |
| --- | --- | --- |
| 根目录不存在 | `return []` | 还没装任何 Skill 时，模板循环为空，不报错 |
| 只扫直接子目录 | `iterdir` + `is_dir` | 不递归；规范也是一层目录名 = skill 名 |
| 必须有 `SKILL.md` | 没有则 `continue` | 附属文件夹、残留目录不会进清单 |
| 拆 frontmatter | `split("---")`，取 `parts[1]` | `parts[0]` 是首个 `---` 之前（通常空）；`parts[2:]` 是正文，这里丢掉 |
| 键用目录名 | `{skill_dir.name: meta}` | 和规范「`name` 必须等于目录名」对齐；模板展示的是目录名，不是 YAML 里可能写错的 `name` |

`split("---")` 只为抽出元数据。正文里即使再出现 `---`，也不影响 `parts[1]`。缺分隔线、`len(parts) < 3` 的文件会被静默跳过，不会进目录——坏掉的 Skill 不会把渲染打崩，但也不会提醒你。

`yaml.safe_load(parts[1])` 得到的就是 frontmatter 那个 dict，里面至少有 `description`，模板用 `skill_meta.description`。

`render_prompt` 仍然每次按**当前**磁盘重扫。`Session` 构造时调用一次，system 消息就固定了（07：历史不可改）。会话跑到一半你新拷进去一个 Skill，当前这条 Session 看不见；新 `Agent()` / 新 `Session()` 才会进清单。这和 cwd 相同：是启动快照，不是每圈刷新。

> **说明：** `npx skills add` 默认往往装到项目根的 `.agents/skills/`（注意复数 agents）。这里扫的是 **`prompt.py` 所在包下的** `.agent/skills/`。装完公共 Skill 若清单里没有，先核对是不是目录不一致，需要的话加 `--dir` 指到 `agent/.agent/skills`。
