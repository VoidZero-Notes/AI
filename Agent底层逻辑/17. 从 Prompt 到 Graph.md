16 把大任务切成独立轮次。前面几篇把零件装齐了：提示词、会话、工具、ReAct、Skill、MCP、子代理。这篇换一条线：行业里对「怎么驾驭模型」先后起过五套名字。它们不是五种新技术，也不是互相取代的口号——是同一条能力往上叠层，每一层都是上一层不够用之后冒出来的。按时间排：Prompt → Context → Harness → Loop → Graph。

## 这一篇在收什么

模型权重固定之后，人能改的只有它**看见什么、处在什么环境、谁来推它、多个它怎么接线**。五套工程分别改这四件事里的一层：

| 层 | 大约何时被叫开 | 改的是什么 | 上一层不够用在哪 |
| --- | --- | --- | --- |
| Prompt Engineering | 2020，2022 大众化 | 窗口里那句话怎么写 | 同一份权重，换任务只能换输入 |
| Context Engineering | 2025.6 | 整个窗口装什么、何时装 | 手写提示只占窗口一小截，失败出在「装错了」 |
| Harness Engineering | 2026.2 | 模型外面的环境：工具、护栏、验证 | 模型够用了，做错了没法自己发现、也拦不住 |
| Loop Engineering | 2026.6 | 谁启动、谁验收、如何自转 | 单次 Agent 可靠了，人还是每一轮的推动者 |
| Graph Engineering | 2026.7 | 多个 loop 怎么接线 | 真实任务有分支、汇合、回退，一条循环画不下 |

和前面几篇的对应：

| 层 | 理论在改什么 | 前面哪篇已经碰到 |
| --- | --- | --- |
| Prompt | 指令、示例、格式、角色 | 06 系统提示词 |
| Context | 历史、工具结果、Skill、检索，何时进窗口 | 07 会话、13 渐进披露 |
| Harness | 工具、权限、可验证的完成条件 | 08 / 09 工具与执行 |
| Loop | 发现任务 → 执行 → 验收 → 再发现 | 10 ReAct；再往上是调度，不是圈本身 |
| Graph | 多个独立轮次如何依赖、分支、汇合 | 16 子代理 |

下面按出现顺序，每一层先说它是什么，再说为什么会出现、解决了什么。原文拼写是 Engeering，这里统一写成 Engineering。

## Prompt Engineering

提示词工程：在**不改模型权重**的前提下，通过改写输入文本（指令、示例、格式、角色、约束）来改变输出。它调的不是模型，是模型这一次调用看见的那几段字。

系统整理见 [Prompt Engineering Guide](https://github.com/dair-ai/Prompt-Engineering-Guide)。

![image-20260729151654925](https://ipic-typora.oss-cn-shenzhen.aliyuncs.com/jishu-img/2026-08-30-102256.png)

### 为什么会出现

2020 年 Brown 等人的论文 [Language Models are Few-Shot Learners](https://arxiv.org/abs/2005.14165) 证明：模型够大之后，不必为每个任务微调。把几个示例直接写进输入，模型就能在上下文里「学会」这个任务——这叫**上下文学习（In-Context Learning）**。同一份权重，换提示就能换任务。

此前的路径是：换任务 → 换数据 → 微调或重训。贵、慢、还要会训。提示词把「训模型」降成了「写输入」。2022 年 Wei 等人提出思维链（Chain of Thought）：让模型先写出中间推理再给答案，复杂推理明显变好。同年 ChatGPT 上线，这个技能从论文走进日常，岗位一度叫「提示词工程师」。

06 写过系统提示词。那一篇收的是「身份 + 环境快照」这一份静态文本；提示词工程比那更宽：用户问题怎么措辞、要不要给示例、要不要逼它一步步想、输出要不要指定 JSON——都算。

### 解决了什么

通用模型不会自动变成你的翻译器、客服或代码助手。提示词工程解决的是：**在模型已经训好的前提下，如何用自然语言把任务边界、输出形状、推理方式说清楚**，让同一次前向传播朝你要的方向走。

它解决不了的：

- 模型没看见的事实（当前目录、线上数据、刚跑完的测试）——提示词再精，也只是在猜
- 窗口被历史和工具结果撑满之后，那句精心写的指令只占几个百分点
- 模型调了工具、转了十几圈——下一圈该看什么，不是写死一句提示能覆盖的

后面四层都是从这里长出来的：提示还在，只是不再是主杠杆。

## Context Engineering

上下文工程：在每一步推理前，**有意设计模型这一次看见的全部 token**——系统提示、用户问题、对话历史、检索结果、工具定义、工具返回、Skill 正文——让窗口里刚好够用，既不太少也不太噪。

> 2025年6月，Shopify的CEO Tobi Lütke 在社交媒体上表示，他更喜欢用“上下文工程”这个词来替代“提示词工程”，因为它更准确地描述了为LLM提供充分信息以完成任务的核心技能

<img src="https://ipic-typora.oss-cn-shenzhen.aliyuncs.com/jishu-img/2026-08-30-102304.png" alt="image-20260730103412811" style="zoom:50%;" />

Karpathy 随后把定义收得更操作化：工业级 LLM 应用里，核心技能是「把上下文窗口填进下一步刚好需要的信息」。太少，模型缺依据；太多或太偏，成本上去、表现下来。提示词是窗口里的一截指令；上下文是窗口里的**全部内容**，而且每一步都在变。

### 为什么会出现

2023–2025，应用不再是「一句提示 → 一句回答」。RAG 把文档检索推进窗口，Agent 把工具结果追回会话，多轮对话把历史越堆越长。手写的那句系统提示，常常只占一次请求 token 的很小一部分，其余是检索块、Observation、上一圈的 Thought。

这时失败形态变了：不是「指令写得不够巧」，是「窗口里装错了东西」。该看的没装进去，不该看的挤满了注意力。提示词工程优化的是那 5%；上下文工程管的是另外 95%，以及这 95% **按什么节奏进出窗口**。

13 的渐进披露就是一次上下文工程：Skill 平时只挂 name + description，命中再读正文。07 的「历史不可改、只会追加」则是上下文工程要治理的对象——圈数一多，窗口被过程占满，后面的决策反而更差。

### 上下文为什么这么脆

**上下文唯一的影响着模型的输出质量。** 模型没有眼睛，窗口之外等于不存在。而窗口不是中性容器，它带**注意力偏差（Attention Bias）**：

- **长度稀释**

  上下文越长，注意力就被分散到更多 token 上，关键信息的权重被摊薄，模型更容易漏掉信息

- 长度**分布外（OOD，Out-of-Distribution）**

  当上下文长度超过训练语料常见长度后，模型回复的置信度会有明显下降

- **信噪比问题**

  噪声信息越多，越会挤占模型对关键信息的注意力预算

- **首尾强化**

  模型对开头（系统提示词）和结尾（最近输入）的关注度天然高于中间（位置偏差 / Positional Bias）

所以「窗口越大越好」不成立。长窗口给的是容量，不给注意力均匀度。上下文工程的工作，就是在这个有偏的窗口里做取舍。

### 关注点：编排与治理

- **编排**

  提示词、用户问题、工具、MCP、Skill 等内容在上下文中如何排列？什么时间加入什么内容？

  系统提示放开头（吃首部强化）；当前任务和工具结果靠后（吃尾部强化）；中间不要堆长期手册。13 的三层披露、16 的子代理隔离，都是编排手段：不该出现在这条 Session 里的过程，根本不要写进来。

- **治理**

  如何确保上下文的内容安全可信？

  如何在持续的循环中，管理和优化不断膨胀的上下文？

  工具返回可能含密钥、无关日志、过时文档。循环每圈追加 Observation，07 的账本只增不改。治理要回答：谁允许进窗口、进了多久该压缩或丢掉、哪一份是系统的记录（repo 里的文档）而不是对话里的口头约定。

<img src="https://ipic-typora.oss-cn-shenzhen.aliyuncs.com/jishu-img/2026-08-30-102310.png" alt="image-20260730112820794" style="zoom:33%;" />

提示词工程是上下文工程的子集。指令还要写清楚，但它不再是整份工作。

## Harness Engineering

驾驭工程 / 缰绳工程：不把力气花在「换一匹更强的马」（换模型），而花在**马具**上——模型外面那套环境：它能调什么工具、能看见什么状态、做错了怎么被自动拦住、做对了依据从哪来。

Harness 一词，意为马具。

> 马具对骑乘的影响非常大。

原作者的意思是，在任务落地的时候，我们应该把更多的注意力从选择什么马（模型）转移到选择什么样的马具身上（如何驾驭模型）

因此，该词也被翻译为"驾驭工程" / "缰绳工程"

两篇源头：

- [Mitchell Hashimoto, My AI Adoption Journey](https://mitchellh.com/writing/my-ai-adoption-journey)（2026.2）：每次发现 Agent 做错，就工程化一项修复，让它以后不再犯。简单的写进 `AGENTS.md`，复杂的做成可编程工具（截图、过滤测试）。他不确定这是不是行业标准名，只是自己这么叫。
- [OpenAI, Harness Engineering](https://openai.com/index/harness-engineering/)（2026.2）：人负责定方向、写验收、补环境；Agent 写代码、跑测试、开 PR。瓶颈从「模型会不会写」变成「环境有没有把对错变成模型自己能读到的信号」。

### 为什么会出现

到 2025 年底、2026 年初，能调工具的 Agent 已经能独立改仓库。人们发现：换一个更强的模型，收益常常不如「给它一个能自己验错的环境」。Hashimoto 的原话是：Agent 第一次就做对、或做错后只需极少返工，最稳的办法是给它**又快又准的反馈工具**，自动告诉它错在哪。

OpenAI 那篇写得更极端：内部一个产品零行手写代码，人几乎不写实现，只补脚手架。早期慢，不是模型不行，是环境没说清楚——缺工具、缺结构、缺「完成」的可检验定义。人的工作变成：缺了什么能力，就做成 Agent 能调用、能验证的东西。

上下文工程管窗口里装什么。Harness 管窗口**外面**那圈：文件系统、测试命令、权限、文档地图、CI。窗口再干净，没有测试脚本，模型也不知道自己写坏了。

### 核心关注点

- **情境与状态管理**

  确保 AI 在复杂、长周期的任务中，能获得正确的上下文信息，并记住任务状态，避免「失忆」和「跑偏」。
  强调 召回 → 规划 → 行动。

  模型每开一轮都是金鱼。跨会话的状态不能只活在 07 的 `messages` 里，要落到仓库：`AGENTS.md` 当目录，`docs/` 当系统记录，执行计划、进度、决策写进文件。OpenAI 的教训是：别写一本 1000 页手册塞进上下文，给一张地图，让它按需再读——和 13 的渐进披露同一原则，只是对象从 Skill 扩成了整个仓库。

- **护栏**

  像给系统设置权限一样，严格管理 AI 能调用哪些工具、访问哪些数据。核心理念是**最小权限原则**——只给 AI 完成当前任务所必须的权限，以防误操作或恶意利用。

  能 `rm -rf` 的环境和只能在 worktree 里改文件的环境，不是同一匹马换鞍，是两套马具。护栏不是提示词里写「请不要删生产数据」，是运行时根本不给那把钥匙。

- **可观测**

  需要做详细的设计，保证模型知晓是否完成了任务？判断的依据是什么？从哪里获取判断需要的信息？

  「写完了」如果只是模型自己说的，不算完成。完成条件必须是模型能自己跑出来的信号：测试绿、lint 过、UI 截图对得上、启动时间低于阈值。OpenAI 把应用做成每个 worktree 可启动，把日志和指标暴露给 Agent，就是把「对错」从人的脑子里搬进环境。Hashimoto 说的 programmed tools，指的也是这一层。

![image-20260830182352174](https://ipic-typora.oss-cn-shenzhen.aliyuncs.com/jishu-img/2026-08-30-102352.png)

<img src="https://ipic-typora.oss-cn-shenzhen.aliyuncs.com/jishu-img/2026-08-30-102400.png" alt="image-20260730124725225" style="zoom:33%;" />

和上一层的边界：上下文工程决定「这一步看见什么」；Harness 决定「它有手没有、手能伸到哪、伸完能不能自己看见对错」。08 / 09 的工具注册是 Harness 的最小形态；完整 Harness 还包含权限、验收脚本、仓库知识的入口。

## Loop Engineering

循环工程：不再由人一句一句提示 Agent，而是**设计一套会自己发现工作、分配、验收、记账、再决定下一步的系统**。人设计循环，循环去提示 Agent。

https://x.com/addyosmani/status/2064127981161959567

Addy Osmani 的收法：Loop Engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead. 循环在这里是一个递归目标——你定义目的，AI 迭代直到完成。Peter Steinberger 说：不该再提示编码 Agent，该设计会去提示 Agent 的循环。Claude Code 负责人 Boris Cherny 说：自己已经不提示 Claude 了，工作是写循环。

Loop Engineering 关注的是如何让 Agent 自我推动，最终完成一个可交付的产品。

它的实现方式是循环，在循环中：

- 自主发现还未完成的任务
- 驱动多个子代理并行任务，并使用工作树隔离
- 自主沉淀知识
- 自主接入工具
- 不同的子代理分工

### 为什么会出现

Harness 让**单次** Agent 变得可靠：环境对、权限对、做错能自检。但启动权还在人手里——人发现任务、写提示、等结果、再写下一句。人是外环，Agent 是内环。

任务变成「每天分拣 issue、每晚扫 CI、一个功能做到测试全绿」，人当外环就成了瓶颈：不是模型慢，是没人去按下一发。循环工程把外环也自动化。Osmani 的位置判断：它在 Harness **上面一层**——Harness 是单匹马的马具；Loop 是这套马具按节拍自己跑，会派帮手，会喂自己。

10 的 ReAct 也是循环，但那是一轮次**内部**的圈：Thought → Action → Observation，直到不再发 Action。Loop Engineering 说的循环更大：跨轮次、跨会话、常带定时——早上发现工作，派子代理修，验收，写下进度，明天接着干。不要把 10 的圈和这里的 Loop 当成同一个东西。

### 循环靠什么转起来

Osmani 拆成五件套，外加一份活在对话之外的状态（markdown / 看板都行）。模型会忘，仓库不会。

| 零件 | 在循环里干什么 | 和前面几篇 |
| --- | --- | --- |
| 自动化 / 调度 | 按时间或按目标自己开工，而不是等人打字 | 10 的圈没有定时器；这是圈外面的心跳 |
| 工作树 | 并行时文件不互相踩 | 隔离的是工作副本，不是 16 的 Session |
| Skill | 项目知识写在外面，每轮不用重讲 | 13 |
| 连接器 / MCP | 循环能碰 issue、CI、聊天，而不只是本地文件 | 14 |
| 子代理 | 做的人和查的人分开；做的人不能给自己打分 | 16 |
| 外部状态 | 记下已做、未做、试过什么 | 不能只靠 07 的一条 Session |

`/goal` 一类原语是「做到某个可检验条件为真再停」；`/loop` / cron 是「按节拍醒来」。停圈的人最好不是写代码的那个模型——和 16「父代理只拿最终结果」同一理由：做的人给自己打分会偏松。

循环没有删掉人。它放大三件事：无人值守时的错误、人对代码的理解债、以及「循环给什么就收什么」的放弃判断。设计循环是杠杆，不是退出工程。

## Graph Engineering

图工程：把工作写成一张**可执行的图**——节点是 Agent、工具、门闸或确定性步骤，边是依赖、分支、汇合、回退。Loop 让「一个 Agent 怎么转」可编程；Graph 让「一群 Agent 怎么组织」可编程。

https://x.com/steipete/status/2078277297791189132

<img src="https://ipic-typora.oss-cn-shenzhen.aliyuncs.com/jishu-img/2026-08-30-102409.png" alt="image-20260730134041913" style="zoom:50%;" />

2026 年 7 月 18 日，Peter Steinberger 在 X 上问了一句：Are we still talking loops or did we shift to graphs yet? 帖子本身没有提出框架，也没有发布新能力。「Graph Engineering」这个叫法是随后讨论里叫开的，而且更早就有人用过（2024 年已有 flow / graph engineering 的说法；2026 年 7 月 11 日已有人排出 Prompt → Context → Harness → Loop → Graph 这把梯子）。Steinberger 做的是把梯子的最后一格问响。

图本身也不新。LangGraph、AutoGen、各种工作流编排，早就按节点和边跑。变的是节点里面开始能塞进一个完整的编码 / 研究 Agent，而不只是一次 LLM 调用。节点会自己选工具、改产物、判断「还没做完，扇出、汇合、复验」。这时拓扑不再是画给自己看的流程图，而是产品决策：谁先跑、谁能看见什么、什么输出能挡住下一步、并行如何汇合、环在哪停。

### 为什么会出现

一条 Loop 擅长「同一目标，反复做，直到条件为真」：发现 → 修 → 验 → 再发现。真实交付很少是一条直道。常见形状：

- 研究、实现、审查必须**分开**，审查不过就回到实现（有界回边）
- 数据层和接口可并行，测试必须等两边都完（扇出 + 汇合）
- 涉及外部副作用（发邮件、改生产、合并主支）前面要做人审门闸
- 失败不能整张图重来，只重跑坏掉的那一段

用一条循环硬塞这些，控制流会藏进提示词和 if-else，谁也 diff 不了、也回放不了。图把控制流抬成一等公民：边可以写清「何时激活、带什么状态、看见什么上下文、有没有权限」。

16 的子代理已经是图的最小形状：父节点拆任务，若干子节点并行，`join` 后汇合。图工程要收的是把这种接线显式化、可版本化，而不是只在一次 `create_agent` 里写死。

### 解决了什么，以及它不是什么

它解决的是：**多个带概率的工人之间，控制、数据、上下文、权限如何接线**。一张能跑的图至少要答四件事：

| 边要说清的 | 含义 |
| --- | --- |
| 控制 | 目标节点何时可以启动（前置是否齐、是否超时） |
| 数据 | 跨节点传什么，类型是什么 |
| 上下文 | 目标节点能看见哪些 token，不是整张图的全部历史 |
| 权限 | 到这一步是否重新验权，尤其是有外部副作用时 |

「图替代循环」不成立。生产里的图通常**含有**循环：某个节点内部仍是 10 的 ReAct，某条回边仍是「审查不过再改」。Loop 是简单的环形图；Graph 是带分支和汇合的图。一个目标、一个上下文边界、一个权限边界、一个可测停条件——留在 Loop 就够，不必画图。

节点也不等于「再堆几个 Agent」。节点可以是一次模型调用、一个确定性脚本、一个门闸、一个人工审批。多节点只在每个节点有自己的契约或失败边界时才有意义。

## 五层怎么叠

不是后一层宣布前一层死亡。后一层把前一层收成零件：

```text
Graph          多个 loop / 节点怎么接线
  └ Loop       谁启动、谁验收、状态写在哪、下一拍做什么
      └ Harness    工具、权限、验收信号、仓库地图
          └ Context    这一步窗口里装什么、何时装
              └ Prompt     窗口里那截指令怎么写
```

对应到一次具体任务：

1. 提示词仍要写清目标（Prompt）
2. 历史、Skill、工具结果按需进窗口，中间过程能隔离就隔离（Context）
3. 测试、lint、权限、文档入口事先备好，模型能自己知道对错（Harness）
4. 发现剩余工作、派活、验收、记账，不必人每句去推（Loop）
5. 研究 / 实现 / 审查 / 发布不是一条直道时，把依赖画成图再跑（Graph）

缺哪一层，症状不一样：提示含糊，单步就歪；窗口脏了，后半段开始忘事；没有马具，错了还自信；没有循环，人成了心跳；没有图，并行和门闸只能靠提示词里的散文维持。

前一层仍是后一层的地基。Graph 画得再好，节点里的窗口是垃圾、环境不能验错，边只是把错误传得更远。
