Transformer：从 Token 到下一 Token 预测，再到训练与推理

> **核心主线：**
>
> `Token ID → Token Embedding → 位置/位置信息 → Transformer Block × N → LM Head → Logits → 下一 Token 概率 → 采样 → 新 Token`
>
> 训练时，再把预测结果与真实的下一个 Token 比较，通过损失函数和反向传播更新参数。

## 先建立一张总图

对于一个 Decoder-only LLM，可以先把整个过程理解成：

```text
文本
 ↓
Tokenizer
 ↓
Token IDs
例如：[101, 5821, 736, 42]
 ↓
Token Embedding
 ↓
[4 × d_model]
 ↓
加入/注入位置信息
 ↓
Transformer Block 1
 ↓
Transformer Block 2
 ↓
...
 ↓
Transformer Block N
 ↓
最后一层隐藏状态
[4 × d_model]
 ↓
LM Head / 输出投影
 ↓
[4 × vocab_size]
 ↓
Logits
 ↓
Softmax（需要概率时）
 ↓
每个位置对“下一个 Token”的概率分布
 ↓
训练：与真实下一个 Token 计算 Cross Entropy
推理：只取最后一个位置 → 采样/贪心 → 得到新 Token
 ↓
把新 Token 接回序列
 ↓
继续生成
```

这里最重要的一点是：

> **Transformer 并不是直接输出“文字”，而是输出对词表中每个 Token 的分数。**

最终通过选择或采样，把一个 Token 生成出来。

## Token Embedding：把 Token ID 变成向量

### Token ID 为什么不能直接输入 Transformer？

Tokenizer 会把文本转换成 Token ID。

例如：

```text
你好世界
↓
["你好", "世界"]
↓
[5821, 736]
```

这里的 `5821`、`736` 本质上只是词表中的编号。

它们没有天然的数学意义：

```text
736 > 5821
```

并不意味着“世界”比“你好”更大。

同样：

```text
5821 + 736
```

也没有语言学意义。

所以不能把 Token ID 本身当成语义向量直接送进神经网络。

### Token Embedding 是什么？

模型会维护一张可学习的矩阵：

```text
Embedding Matrix

[vocab_size × d_model]
```

假设：

```text
vocab_size = 120000
d_model = 6
```

那么：

```text
Embedding Matrix
= [120000 × 6]
```

可以把它想成一本“查表”：

```text
Token ID      对应向量

0       → [0.12, -0.31, 0.88, ...]
1       → [0.54,  0.22, 0.11, ...]
2       → [-0.7, 0.15, 0.33, ...]
...
33256   → [......]
11789   → [......]
```

输入：

```text
[33256, 11789]
```

实际上就是：

```text
取 Embedding Matrix 的第 33256 行
取 Embedding Matrix 的第 11789 行
```

最终得到：

```text
[2 × 6]
```

### 更准确地说应该叫 Token Embedding

很多资料把它叫：

> Word Embedding（词嵌入）

但对于现代 LLM，更准确的叫法是：

> **Token Embedding**

因为一个 Token 不一定等于一个完整的词。

例如某些分词器可能把：

```text
unbelievable
```

拆成多个 Token。

中文、英文、数字、标点、特殊符号也都可能分别成为 Token 或 Token 片段。

因此不要把：

```text
Token = Word
```

画等号。

### Embedding 的维度由谁决定？

模型设计者决定：

```text
d_model = 768
d_model = 4096
d_model = 7168
...
```

但通常不会人工规定：

```text
第 1 维 = “食物程度”
第 2 维 = “科技程度”
第 3 维 = “价格程度”
```

这些参数由训练过程自动学习。

因此更准确的说法是：

> **我们人为规定向量有多少维，但通常不人为规定每一维的语义。**

而且不要把每一个维度理解成人类可以直接解释的“特征”。

模型内部表示通常是**分布式表示（distributed representation）**：

> 一个概念往往分布在大量维度和大量参数中，而不是由某一个维度单独表示。

### “词向量可以做数学运算”要谨慎理解

经典 Word2Vec 中确实出现过：

```text
king - man + woman ≈ queen
```

这类著名的向量关系。

但是不要把它理解成：

> 所有 LLM 的 embedding 都严格满足这种公式。

尤其对于现代 Transformer：

- 输入 Token Embedding 是静态的；
- Transformer 内部的 hidden state 是上下文相关的；
- 语义通常是分布式编码；
- 向量空间中的线性关系并不保证对所有概念成立。

所以类似：

```text
2 × 开心 ≈ 狂喜
```

这种例子更适合当作“向量可以存在某些几何关系”的直觉示例，而不能作为 Transformer 的普遍规律。

## Embedding 和 Contextual Representation 的区别

这是理解 Transformer 非常重要的一点。

### Token Embedding 是静态的

假设 Token：

```text
银行
```

无论它出现在：

```text
我去银行取钱
```

还是：

```text
河岸边的银行
```

它刚进入 Embedding 层时，查到的是同一行参数。

所以：

```text
Embedding("银行")
```

本身不会因为上下文不同而自动改变。

### Transformer 让表示变成上下文相关

经过注意力等 Transformer 层之后：

```text
“我去银行取钱”
```

中的“银行”和：

```text
“坐在河岸边”
```

中的相关 Token，会因为上下文不同而形成不同的 hidden state。

所以可以粗略理解为：

```text
Token Embedding
    ↓
静态初始表示
    ↓
Attention + FFN
    ↓
Contextual Hidden State
    ↓
上下文相关的动态表示
```

因此：

> **Embedding 是输入表示；Transformer hidden state 才是经过上下文计算后的表示。**

## Context Length / Context Window

这两个术语在不同资料里有时会混用。

为了学习方便，可以这样区分：

### Context

当前实际提供给模型的一段 Token 序列。

例如：

```text
当前输入 8000 Tokens
```

就是当前上下文的一部分。

### Context Window

模型一次最多能够处理的 Token 范围。

例如：

```text
Context Window = 128K
```

表示模型最多可以在一个上下文中处理约 128K Tokens。

不过不同论文、API 和模型文档对 `context length`、`context window` 的命名可能并不完全一致，因此实际使用时应该以具体模型文档为准。

## Attention：让 Token 之间互相读取信息

Token Embedding 有一个核心问题：

> 一个 Token 自己并不知道当前句子中的其他 Token。

例如：

```text
苹果公司发布了新手机
```

这里的：

```text
苹果
```

和：

```text
我今天吃了一个苹果
```

中的“苹果”，语境不同。

Transformer 需要一种机制，让当前位置能够根据其他位置的信息修改自己的表示。

这就是：

> **Self-Attention（自注意力）**

## Q / K / V

Attention 的核心可以先理解成三个角色：

| 名称 | 含义 |
| --- | --- |
| Query | 我想找什么 |
| Key | 我这里有什么信息，可以被别人匹配 |
| Value | 如果别人关注我，我真正提供什么内容 |

假设输入：

```text
X = [4 × 6]
```

通过三个可学习的线性投影：

```text
Q = XW_Q
K = XW_K
V = XW_V
```

如果：

```text
W_Q = [6 × 6]
W_K = [6 × 6]
W_V = [6 × 6]
```

那么：

```text
Q = [4 × 6]
K = [4 × 6]
V = [4 × 6]
```

## Attention 的数学过程

### Q 和 K 做点积

```text
S = QKᵀ
```

如果：

```text
Q = [4 × 6]
K = [4 × 6]
```

那么：

```text
Kᵀ = [6 × 4]

QKᵀ = [4 × 4]
```

于是得到一个：

```text
4 × 4
```

的注意力分数矩阵。

例如：

```text
        Token1 Token2 Token3 Token4
Token1    3.2    1.1    0.4    2.0
Token2    0.5    4.1    1.2    0.8
Token3    1.0    2.7    3.5    0.9
Token4    0.2    1.1    2.9    4.3
```

第 `i` 行表示：

> 第 `i` 个 Token 想从其他位置读取多少信息。

### 为什么要除以 √d_k？

完整公式是：

```text
S = QKᵀ / √d_k
```

原因是：

> 当向量维度越来越大时，点积的数值尺度通常也会增大。

如果不缩放，Softmax 输入可能过大，使概率分布变得非常尖锐，导致梯度学习变得困难。

因此使用：

```text
1 / √d_k
```

进行缩放。

注意：

> 它不是为了“防止点积绝对不能过大”，而是为了控制点积分布的尺度，让 Softmax 和梯度更加稳定。

## Softmax：把分数变成注意力权重

对每一行做：

```text
A = softmax(S)
```

例如：

```text
[1.0, 2.0, 3.0]
```

经过 Softmax 后可能变成：

```text
[0.09, 0.24, 0.67]
```

于是：

```text
0.09 + 0.24 + 0.67 = 1
```

这些数可以理解为：

> 当前 Token 从不同位置读取 Value 时，各自占多大权重。

## 用注意力权重加权 Value

最终：

```text
Attention(Q,K,V) = AV
```

例如：

```text
A = [4 × 4]
V = [4 × 6]

AV = [4 × 6]
```

因此：

```text
输入：[4 × 6]
输出：[4 × 6]
```

维度可以保持不变。

每一行都变成：

> **融合了其他 Token 信息之后的新表示。**

## Causal Mask：为什么不能看未来？

LLM 训练通常使用：

> **Causal Language Modeling（因果语言建模）**

目标是：

```text
已知前面的 Token
→ 预测下一个 Token
```

假设：

```text
[t1, t2, t3, t4]
```

那么：

```text
t1 → 预测 t2
t1,t2 → 预测 t3
t1,t2,t3 → 预测 t4
```

因此在计算第 `i` 个位置时，不能偷看：

```text
i+1, i+2, ...
```

### Causal Mask

例如 4 个 Token：

```text
      t1 t2 t3 t4

t1    ✓  ×  ×  ×
t2    ✓  ✓  ×  ×
t3    ✓  ✓  ✓  ×
t4    ✓  ✓  ✓  ✓
```

数学上可以在 attention logits 上加入 mask：

```text
允许的位置：
原始分数

禁止的位置：
原始分数 + (-∞)
```

Softmax 后：

```text
softmax(-∞) = 0
```

因此未来 Token 的注意力权重变成 0。

## 为什么训练时可以并行？

这是 Transformer 非常关键的优势。

很多人第一次学自回归模型会认为：

> 既然是“预测下一个 Token”，是不是训练也必须一个一个预测？

不是。

假设：

```text
[t1, t2, t3, t4]
```

训练时可以一次性输入：

```text
[t1, t2, t3, t4]
```

然后通过 causal mask 得到：

```text
位置1 → 预测 t2
位置2 → 预测 t3
位置3 → 预测 t4
```

这些位置可以在 GPU 上并行计算。

因此：

> **训练是并行的；生成推理是自回归的。**

这是理解 Transformer 训练/推理差异的关键。

## Decoder-only Transformer

原始 Transformer（2017）是：

```text
Encoder
+
Decoder
```

主要用于机器翻译等 Seq2Seq 任务。

现代 GPT 类 LLM 通常采用：

```text
Decoder-only
```

但这里的“Decoder-only”容易产生误解。

它并不是说：

> “把原始 Decoder 原封不动拿过来”。

现代 LLM 对 Transformer Decoder Block 做了大量工程改造，例如：

- Pre-Norm
- RMSNorm
- RoPE
- GQA / MQA / MLA 等注意力变体
- SwiGLU / Gated MLP
- MoE
- 更复杂的残差结构

所以更准确的理解是：

> **现代 GPT 类 LLM 属于 Decoder-only Transformer 家族，但具体 Block 已经和 2017 年原论文中的 Decoder 有明显差异。**

## Multi-Head Attention

如果只有一套：

```text
Q K V
```

就是单头注意力的直觉模型。

实际 Transformer 通常会使用多个 Head。

例如：

```text
d_model = 6
num_heads = 2
```

可以拆成：

```text
Head 1 → 3 维
Head 2 → 3 维
```

每个 Head 独立计算：

```text
Attention(Q1,K1,V1)
Attention(Q2,K2,V2)
```

然后拼接：

```text
[4 × 3] + [4 × 3]
→ [4 × 6]
```

通常还会再经过一个输出投影：

```text
Concat → W_O → [4 × 6]
```

所以更完整地说：

```text
Multi-Head Attention
=
多个 Attention Head
→ Concat
→ Output Projection
```

## “不同 Head 学不同关系”只能作为直觉

经常有人说：

> Head 1 负责语法，Head 2 负责指代，Head 3 负责位置……

这可以作为帮助理解的直觉，但不能当成严格规律。

实际模型中：

- 不同 Head 的功能可能重叠；
- 某些 Head 可能具有比较明显的特定模式；
- 某些 Head 的作用很难直接解释；
- 现代模型还可能使用 GQA、MQA、MLA 等结构，而不是传统 MHA。

所以更严谨的表述是：

> **多头机制允许模型在多个不同的投影子空间中同时建立注意力关系，从而增加表示能力。**

## 位置编码：Attention 怎么知道顺序？

如果只有：

```text
A
B
C
```

的内容向量，而没有位置信息，那么模型很难区分：

```text
A B C
```

和：

```text
C B A
```

语言显然不是无序集合。

因此 Transformer 需要位置信息。

## RoPE：现代 LLM 常见的位置编码方法

现代很多 LLM 使用：

> **Rotary Position Embedding（RoPE）**

它不是简单地：

```text
Embedding + Position Vector
```

而是对 Q、K 的部分维度进行与位置相关的旋转，使注意力点积能够编码位置信息。

可以先记住：

```text
Q → RoPE
K → RoPE
V → 通常不做 RoPE
```

然后：

```text
Q_rot K_rotᵀ
```

用于计算注意力。

### RoPE 的核心直觉

RoPE 的一个重要性质是：

> 两个位置之间的相对位置信息会自然地进入 Q/K 的点积关系。

因此模型不仅能感知：

```text
“谁是谁”
```

还能够感知：

```text
“谁和谁距离多远”
```

不过不要写成：

> RoPE 一定能稳定外推到任意更长上下文。

实际长上下文能力还与：

- RoPE scaling
- 训练长度
- 注意力结构
- 模型训练数据
- 长上下文微调

等因素有关。

## Transformer Block：模型真正反复堆叠的基本单元

一个简化的 Transformer Block 可以理解成：

```text
输入 X
 ↓
Norm
 ↓
Self-Attention
 ↓
Residual Add
 ↓
Norm
 ↓
FFN / MLP
 ↓
Residual Add
 ↓
输出
```

但注意：

> **不同模型的具体顺序并不一样。**

## Pre-Norm 和 Post-Norm

### Post-Norm

原始 Transformer 的典型结构更接近：

```text
X
 ↓
Attention
 ↓
Add X
 ↓
Norm
 ↓
FFN
 ↓
Add
 ↓
Norm
```

即：

```text
Norm( X + Sublayer(X) )
```

### Pre-Norm

现代很多 LLM 更常见：

```text
X
 ↓
Norm
 ↓
Attention
 ↓
Add X
 ↓
Norm
 ↓
FFN
 ↓
Add
```

即：

```text
X + Attention(Norm(X))
```

然后：

```text
X + FFN(Norm(X))
```

Pre-Norm 通常更有利于训练深层 Transformer。

因此看模型结构图时：

> **不要默认所有模型都是“Attention → Add → Norm”。**

## RMSNorm 到底在干什么？

RMSNorm 是一种归一化方法。

和 LayerNorm 相比，它不需要先减去均值，而是主要根据均方根进行缩放。

简化理解：

```text
x
↓
计算 RMS
↓
缩放 x
↓
乘以可学习参数
```

它的主要作用是：

> **控制表示的尺度，使网络训练和数值传播更加稳定。**

不要把它写成：

> “把所有值压到 [-3,3]。”

这是不准确的。

RMSNorm 并不保证输出一定落在某个固定区间。

也不要简单写成：

> “防止梯度爆炸和梯度消失。”

更严谨的是：

> **归一化有助于改善优化过程和数值稳定性，降低深层网络训练中的尺度失控风险。**

## Residual Connection：残差连接

注意力模块通常不是直接把输入完全替换掉。

而是：

```text
X_new = X + Attention(X)
```

FFN 也是：

```text
X_new = X + FFN(X)
```

这就是：

> **Residual Connection / Skip Connection**

### 为什么需要残差？

它提供了一条相对直接的信息和梯度通路：

```text
输入 X
 ├───────────────┐
 │               ↓
 │          Sublayer(X)
 │               ↓
 └──────→       Add
```

这样深层网络更容易优化。

不要把它理解成：

> “没有残差，模型就一定会丢失原始信息。”

更准确的说法是：

> **残差结构让每层可以学习对已有表示进行增量式修改，并显著改善深层网络的优化和梯度传播。**

## FFN / MLP：Token 内部的非线性变换

Attention 解决的是：

> **Token 与 Token 之间的信息交换。**

FFN 解决的是：

> **对每个位置自己的表示进行更强的非线性变换。**

一个传统 FFN 可以写成：

```text
FFN(x) = W2 · activation(W1 · x + b1) + b2
```

如果：

```text
d_model = 4096
d_ff = 16384
```

那么：

```text
4096
 ↓
16384
 ↓
4096
```

通常先升维，再经过非线性，再降回原维度。

## FFN 为什么需要升维？

可以粗略理解为：

```text
低维表示
 ↓
扩大内部计算空间
 ↓
非线性组合
 ↓
重新压回 d_model
```

它给模型提供了大量额外的可学习参数和非线性表达能力。

因此：

```text
Attention ≈ Token 之间交换信息
FFN ≈ 每个 Token 自己进行深度计算
```

这是一个非常有用的学习框架。

## FFN 不应该简单理解成“知识数据库”

常见说法：

> FFN 的某些神经元就是某条知识。

这个说法过于简单。

研究确实发现 Transformer 的 MLP/FFN 与知识和模式存储存在重要关系，但模型中的知识通常是：

> **分布式地编码在大量参数和表示中。**

因此更准确的是：

> **FFN 是模型存储和变换知识、模式的重要组成部分之一，但不能把一个神经元简单等同于一条事实。**

## SwiGLU / Gated MLP

现代 LLM 很多已经不是最简单的：

```text
Linear
→ Activation
→ Linear
```

而是使用：

```text
Gated MLP
```

例如 SwiGLU。

直觉上可以理解为：

```text
输入
 ↓
产生两个分支
 ↓
一个负责内容变换
一个负责门控
 ↓
逐元素相乘
 ↓
输出投影
```

它通常比简单的 ReLU FFN 更适合现代 LLM。

因此：

> “FFN 通常是两层全连接”

作为入门直觉可以，但如果写现代 LLM 架构，最好进一步说明：

> **现代模型通常使用 Gated MLP，例如 SwiGLU。**

## MoE：不是所有参数都同时激活

MoE：

> **Mixture of Experts，混合专家**

假设模型有：

```text
384 个 Expert
```

一个 Token 并不一定经过全部 384 个 Expert。

Router 可以为 Token 选择少数 Expert：

```text
Token
 ↓
Router
 ↓
Expert 7
Expert 82
Expert 193
...
 ↓
合并
```

因此：

```text
Total Parameters
```

可以非常大。

但：

```text
Activated Parameters / Token
```

可以明显小于总参数量。

## “参数量”和“激活参数量”不是一回事

例如一个 MoE 模型：

```text
总参数：1.6T
每个 Token 激活：49B
```

并不意味着模型只有 49B 参数。

而是：

> 模型总共拥有约 1.6T 参数，但单个 Token 的一次前向传播只使用其中约 49B 的激活参数规模。

这也是 MoE 能在较大总参数规模下控制单 Token 计算量的重要原因。

## 一个 Transformer Block 的维度变化

继续使用玩具模型：

```text
Token 数量：4
d_model：6
```

那么 Block 输入：

```text
X
[4 × 6]
```

注意力部分：

```text
Q/K/V
[4 × 6]
```

多头拆分后：

```text
Head 1 → [4 × 3]
Head 2 → [4 × 3]
```

每个 Head：

```text
Attention Score
[4 × 4]

Attention Output
[4 × 3]
```

拼接：

```text
[4 × 6]
```

经过输出投影：

```text
[4 × 6]
```

残差：

```text
[4 × 6] + [4 × 6]
→ [4 × 6]
```

FFN：

```text
[4 × 6]
 ↓
[4 × d_ff]
 ↓
[4 × 6]
```

再次残差：

```text
[4 × 6]
```

所以：

> **Transformer Block 的输入输出通常保持 `sequence_length × d_model` 不变。**

## 多个 Transformer Block

如果模型有：

```text
N 个 Block
```

那么：

```text
Embedding
 ↓
Block 1
 ↓
Block 2
 ↓
Block 3
 ↓
...
 ↓
Block N
 ↓
Final Norm
 ↓
LM Head
```

每个 Block 都在前一个 Block 的表示上继续计算。

可以粗略理解为：

```text
浅层
→ 局部模式、词法、简单结构

中层
→ 更复杂的语法和语义关系

深层
→ 更复杂的上下文表示、任务相关模式
```

但这仍然只是一个帮助理解的粗略描述。

> **不能简单地认为“每一层都有固定职责”。**

## LM Head：把隐藏状态映射回词表

经过最后一个 Transformer Block 后：

```text
Hidden States
[sequence_length × d_model]
```

例如：

```text
[4 × 6]
```

模型需要回答：

> 下一 Token 是词表里的哪一个？

因此需要一个输出投影：

```text
LM Head
```

假设：

```text
vocab_size = 120000
```

那么：

```text
W
[6 × 120000]
```

计算：

```text
Logits = XW
```

得到：

```text
[4 × 120000]
```

## Logits 是什么？

每一个位置都会得到：

```text
120000 个分数
```

例如：

```text
Token A → 2.1
Token B → 5.7
Token C → -1.3
Token D → 3.2
...
```

这些还不是概率。

它们叫：

> **Logits**

通常：

```text
Logit 越大
→ Softmax 后概率越高
```

然后：

```text
P = Softmax(Logits)
```

才得到概率分布。

## Softmax 并不是模型“必须执行”的最后一步

需要区分：

### 模型输出

通常是：

```text
Logits
```

### 概率

需要：

```text
Softmax(Logits)
```

### 生成 Token

可以基于 logits 进行：

- Greedy
- Temperature Sampling
- Top-K
- Top-P
- 其他采样/解码策略

工程实现中，有时为了数值稳定性或效率，并不会真的把完整概率分布显式构造出来再做后续操作。

所以：

> **LM Head 输出的是 logits，而不是文字。**

## 为什么训练时每一行都有用？

假设：

```text
输入：

t1 t2 t3 t4
```

模型输出：

```text
position 1 → 预测 t2
position 2 → 预测 t3
position 3 → 预测 t4
position 4 → 预测 t5
```

如果没有 `t5`：

```text
position 4
```

通常没有对应标签，因此不参与这一段序列的 next-token loss。

训练目标可以表示成：

```text
输入：

t1 t2 t3 t4

标签：

t2 t3 t4 t5
```

也就是：

```text
shifted labels
```

这就是：

> **Next Token Prediction**

## Cross Entropy：训练到底在优化什么？

假设真实下一个 Token 是：

```text
Token 736
```

模型预测：

```text
P(Token 736) = 0.8
```

那么损失比较小。

如果：

```text
P(Token 736) = 0.001
```

损失就很大。

对于分类任务，常见损失是：

> **Cross Entropy（交叉熵）**

简化理解：

```text
正确答案概率越高
→ Loss 越小

正确答案概率越低
→ Loss 越大
```

## 训练循环

完整训练可以理解为：

```text
训练数据
 ↓
Tokenization
 ↓
Token IDs
 ↓
Embedding
 ↓
Transformer
 ↓
Logits
 ↓
Cross Entropy Loss
 ↓
Backpropagation
 ↓
Gradients
 ↓
Optimizer
 ↓
更新参数
 ↓
下一批数据
```

不断重复。

更新的参数可能包括：

```text
Embedding
W_Q
W_K
W_V
W_O
FFN / MLP
Norm 参数
LM Head
MoE Router
Experts
...
```

具体取决于模型结构和训练阶段。

## 为什么说预训练是“自监督学习”？

因为训练标签不需要人工逐条标注。

原始文本本身就是监督信号。

例如：

```text
今天 天气 很 好
```

可以自动构造：

```text
输入：今天
标签：天气

输入：今天 天气
标签：很

输入：今天 天气 很
标签：好
```

因此：

> **监督信号来自数据本身，所以叫自监督学习（Self-Supervised Learning）。**

## Teacher Forcing：训练和生成为什么不一样？

训练时：

```text
输入：
t1 t2 t3 t4

目标：
t2 t3 t4 t5
```

模型可以一次看到整段真实历史。

这通常被称为：

> **Teacher Forcing**

而推理时模型没有真实的未来 Token：

```text
已有：
t1 t2 t3

模型生成：
t4

然后：
t1 t2 t3 t4

再生成：
t5
```

因此：

```text
训练：
并行预测

推理：
串行生成
```

这也是为什么 LLM 推理阶段存在明显的自回归成本。

## 推理：Prefill + Decode

LLM 推理通常可以拆成两个阶段：

```text
Prefill
+
Decode
```

### Prefill

用户输入：

```text
请帮我解释 Transformer，要求详细说明 Attention。
```

假设有：

```text
2000 Tokens
```

第一次处理时，模型可以把这 2000 Tokens 一次性送进去。

得到：

```text
每个位置的 hidden state
```

同时计算并保存注意力所需的历史 K/V。

这个阶段叫：

> **Prefill**

它的特点：

- 输入可能很长；
- GPU 可以高度并行；
- Prompt 越长，计算量通常越大；
- 首 Token 延迟的重要组成部分就是 Prefill。

## Decode：一个 Token 一个 Token 生成

Prefill 完成后：

```text
Prompt
+
生成 Token 1
```

然后：

```text
生成 Token 2
```

再：

```text
生成 Token 3
```

一直循环。

这就是：

> **Decode / Generation**

与 Prefill 相比：

```text
Prefill
→ 一次处理很多 Token

Decode
→ 每一步通常只新增一个 Token
```

## KV Cache：为什么不用每次重算历史？

Attention 需要：

```text
Q
K
V
```

假设现在已经有：

```text
Token 1
Token 2
Token 3
Token 4
```

下一步生成 Token 5。

历史 Token 的 K/V 在因果自注意力中不会因为 Token 5 出现而发生变化。

因此可以缓存：

```text
K1 K2 K3 K4
V1 V2 V3 V4
```

下一步只需要计算新 Token 的：

```text
Q5
K5
V5
```

然后：

```text
Q5
 ↓
与缓存中的 K1...K5 做注意力
 ↓
读取对应 V
```

这样就避免了重复计算历史 K/V。

## KV Cache 的代价

KV Cache 不是免费优化。

缓存需要显存。

其占用量大致与以下因素相关：

```text
层数
×
KV Head 数量
×
每个 Head 的维度
×
序列长度
×
每个元素占用的字节数
```

因此：

> **上下文越长，KV Cache 通常越大。**

这也是长上下文推理的重要系统瓶颈之一。

GQA、MQA、MLA 等技术的一个重要目标，就是降低 KV Cache 或注意力相关的内存/计算成本。

## 一个非常重要的区别：计算复杂度 vs 实际延迟

不要简单写：

> “用了 KV Cache，每个 Token 的计算量就是 O(1)。”

这不准确。

因为新 Token 仍然需要与历史信息进行注意力计算。

随着上下文变长，某些标准注意力实现中的计算量仍会随历史长度增长。

KV Cache 的主要作用是：

> **避免每一步重复计算历史 Token 的 K/V。**

所以更准确的理解是：

```text
无 KV Cache
→ 每一步重复处理整个历史

有 KV Cache
→ 历史 K/V 复用
→ 只计算新增 Token 的新状态
→ 仍需读取/匹配历史缓存
```

## 为什么 LLM 生成速度通常按 Tokens/s 衡量？

因为生成阶段是自回归的：

```text
Token 1
→ Token 2
→ Token 3
→ Token 4
...
```

每生成一个新的 Token，都需要进行一次新的 decode step。

所以经常看到：

```text
30 tokens/s
80 tokens/s
150 tokens/s
```

这描述的是：

> **Decode 阶段的 Token 生成速度。**

而用户第一次输入后的等待时间，还受到 Prefill 等因素影响。

## Sampling：模型如何决定“选哪个 Token”？

模型得到：

```text
logits
```

之后，需要进行解码。

最简单的是：

> **Greedy Decoding**

每次直接选择：

```text
logit 最大的 Token
```

例如：

```text
A → 5.2
B → 3.1
C → 1.2
```

直接：

```text
A
```

## Temperature

Temperature 通常作用在 Softmax 前：

```text
P = Softmax(logits / T)
```

### T = 1

```text
不改变原始 logits 的温度尺度
```

### T < 1

分布更尖锐：

```text
高概率 Token 更突出
```

通常更加确定。

### T > 1

分布更平：

```text
低概率 Token 更有机会被采样
```

通常更加随机。

## Temperature = 0 要谨慎理解

工程 API 中经常看到：

```text
temperature = 0
```

但数学公式：

```text
logits / T
```

在：

```text
T = 0
```

时没有定义。

实际推理框架通常会把它作为：

> **近似 greedy / 确定性解码**

来特殊处理。

所以不要写：

> “T=0 就是正常公式里的除以 0。”

## Top-K

Top-K：

```text
只保留概率最高的 K 个 Token
```

例如：

```text
K = 50
```

先找出：

```text
概率最高的 50 个 Token
```

其他 Token：

```text
概率设为 0
```

然后在剩余候选中重新归一化并采样。

## Top-P / Nucleus Sampling

Top-P 不固定候选数量。

例如：

```text
P = 0.9
```

从高概率到低概率不断累加：

```text
0.50
0.20
0.10
0.06
0.04
...
```

直到累计概率达到指定阈值。

最终保留这个动态候选集合。

因此：

```text
Top-K
→ 候选数量固定

Top-P
→ 候选概率质量固定
```

Top-P 通常比固定 K 更能适应不同的概率分布。

## Temperature、Top-K、Top-P 的关系

可以粗略理解为：

```text
原始 Logits
 ↓
Temperature
 ↓
Top-K / Top-P 过滤
 ↓
重新归一化
 ↓
Sampling
 ↓
Token
```

但实际框架的具体实现顺序可能有所不同。

因此不要把：

> “所有模型都严格按照这个顺序”

当成架构定律。

## 训练与推理：一张表看懂

| | 训练 | 推理 |
| --- | --- | --- |
| 输入 | 大量训练 Token | 用户 Prompt + 已生成 Token |
| 目标 | 学习参数 | 使用参数 |
| 是否计算 Loss | 是 | 通常不需要 |
| 是否反向传播 | 是 | 否 |
| 是否更新参数 | 是 | 否 |
| Token 处理 | 可以并行 | 自回归 |
| Causal Mask | 使用 | 使用 |
| KV Cache | 训练时通常不是推理式 KV Cache | 非常重要 |
| 输出 | logits + loss | logits → 解码 Token |

## 预训练：模型最初是怎么获得能力的？

现代 LLM 的训练过程并不是只有一个阶段。

一个非常粗略的生命周期可以理解成：

```text
大规模数据
 ↓
预训练 / Continued Pretraining 等
 ↓
Base Model
 ↓
SFT / Instruction Tuning
 ↓
Preference / Alignment / Reasoning 等后训练
 ↓
可用的 Chat / Reasoning Model
```

具体厂商流程会不同。

## Pretraining：预训练

预训练阶段通常使用海量数据，让模型学习：

```text
Token → 下一个 Token
```

它会逐渐学到：

- 语言规律
- 语法
- 词语和上下文关系
- 世界知识中的统计规律
- 代码模式
- 数学模式
- 各类文本结构
- 一定程度的推理和模式组合能力

关键点：

> **这些能力不是单独写进某个“知识模块”里的，而是在大规模参数优化过程中逐渐形成。**

## “只会预测下一个 Token，为什么还能推理？”

这是理解 LLM 最核心的问题之一。

模型的训练目标确实很简单：

```text
预测下一个 Token
```

但如果想把下一个 Token 预测准确，它必须学习很多隐藏规律。

例如：

```text
1 + 1 =
```

后面更可能出现：

```text
2
```

为了预测得更准确，模型需要学习：

```text
数学模式
符号关系
语言结构
上下文
```

再例如：

```text
法国的首都是
```

后面很可能是：

```text
巴黎
```

因此：

> **“下一 Token 预测”是训练目标，不等于模型内部只存在一个简单的查表过程。**

经过大规模训练后，模型参数中会形成复杂的表示和计算能力。

## 但不要把 LLM 简化成“只会续写”

“它只是续写”作为理解 Transformer 的第一层直觉有帮助。

但如果把它理解成：

> “所以它只是简单统计下一个词。”

就错了。

现代 Transformer 在生成一个 Token 前，会经过大量层级的：

```text
Attention
+
MLP
+
Residual
+
Normalization
+
其他架构模块
```

这些参数共同完成复杂的信息变换。

所以更准确的说法是：

> **LLM 的训练目标是 next-token prediction，但实现这个目标的模型内部包含非常复杂的表示学习和计算过程。**

## Pretraining 不等于“训练完就会聊天”

Base Model 通常更接近：

> “一个非常强的文本预测模型。”

它不一定天然具有理想的：

- 对话格式
- 指令遵循
- 拒答策略
- 安全行为
- 输出风格
- 工具调用能力

因此还需要后训练。

## SFT：监督微调

SFT：

> **Supervised Fine-Tuning**

数据通常类似：

```text
User:
解释一下 Transformer。

Assistant:
Transformer 是一种...
```

模型通过这些高质量示例学习：

```text
看到用户指令
→ 按期望方式回答
```

也可以学习：

- 对话角色
- 输出格式
- 指令遵循
- 特定任务
- 特定风格
- 工具调用格式
- 专业领域任务

## SFT 的 Loss 不一定计算所有 Token

实际训练中经常会：

```text
User Token
→ 不计算 loss

Assistant Token
→ 计算 loss
```

这样可以让模型重点学习：

> **“助手应该如何回答”。**

但这不是所有 SFT 数据和实现都必须如此。

具体取决于：

- 数据格式
- loss mask
- 训练框架
- 训练目标

## Preference / Alignment：让模型更符合人类偏好

仅有 SFT 不一定足够。

例如两个回答：

```text
回答 A：正确、简洁、安全
回答 B：啰嗦、错误、有风险
```

我们希望模型更倾向于 A。

这就进入：

> **Preference Optimization / Alignment**

历史上一个经典路线是：

```text
SFT
 ↓
Reward Model
 ↓
RL
```

即：

> **RLHF（Reinforcement Learning from Human Feedback）**

## RLHF 不是后训练的唯一方法

现代 LLM 后训练已经有很多方法，例如：

```text
SFT
DPO
RLHF
GRPO
RLVR
其他 preference / reward optimization
```

所以不要把：

> “后训练 = 奖励模型 + PPO”

当成固定流程。

更准确的是：

> **RLHF 是后训练/对齐中的一条重要技术路线，而不是所有现代模型都必须完整执行的唯一流程。**

## Reasoning / CoT：需要特别谨慎理解

Chain-of-Thought：

> **CoT，思维链**

可以理解为：

```text
问题
 ↓
中间推理步骤
 ↓
最终答案
```

例如数学题：

```text
10 - 3 = 7
7 + 5 = 12
所以答案是 12
```

训练或推理时，可以让模型生成中间推理 Token。

但需要注意：

> **CoT 不应该简单等同于“模型真正的内部思维被原样打印出来”。**

现代 reasoning model 可能存在：

- 显式可见推理
- 隐式/隐藏推理
- 专门的 reasoning tokens
- 不同的 RL reasoning 训练方式

因此学习时建议记住：

> **CoT 是一种通过生成或训练中间推理序列来增强复杂任务求解能力的方法，而不是“把模型脑子里的真实思维过程直接打印出来”。**

## “承认不知道”不能简单等同于解决幻觉

训练：

```text
不知道 → 承认不知道
```

确实可能改善某些情况下的错误回答。

但：

> **这并不能从根本上解决 hallucination（幻觉）。**

降低幻觉通常需要结合：

- 更好的预训练数据
- 更高质量的 SFT
- Preference / RL
- Tool Use
- RAG
- Search
- Verification
- Grounding
- 更好的推理策略

所以：

> “多训练一些‘不知道就说不知道’的数据”只能算一种校准手段，不是完整的幻觉解决方案。

## 专业知识怎么进入模型？

这里必须区分几种方式。

### 方法 1：继续预训练

拿专业领域数据继续训练：

```text
Base Model
 ↓
Domain Corpus
 ↓
Continued Pretraining
 ↓
Domain-adapted Model
```

会改变模型参数。

### 方法 2：SFT

使用：

```text
专业问题
+
高质量答案
```

进行监督微调。

### 方法 3：RAG

不是把知识直接写进模型参数。

而是：

```text
用户问题
 ↓
检索知识库
 ↓
得到相关文档
 ↓
放入 Context
 ↓
LLM 根据文档回答
```

因此：

> **RAG 是给模型外部知识，不等于训练模型。**

这是 Agent / RAG 学习中非常重要的区别。

## Continual Learning：持续学习

持续学习的核心问题是：

> **模型如何在接收新知识、新任务的同时，尽可能保留旧能力？**

这会涉及：

```text
Continual Pretraining
Continual Fine-tuning
Continual Alignment
```

以及：

```text
Catastrophic Forgetting
```

## 一个非常重要的纠正：模型不会天然“持续吸收所有用户聊天”

不要写成：

> “现在很多大模型厂商会把 AI 和用户之间的对话内容作为语料，持续对大模型进行训练。”

这句话太绝对。

现实中需要区分：

```text
用户聊天记录
≠
自动实时训练模型
```

可能存在：

- 用户对话作为产品记忆
- 对话用于服务质量分析
- 经过政策和隐私处理后用于训练
- 用户明确选择允许数据用于改进
- 离线数据清洗
- 周期性训练
- 人工筛选
- 合成数据
- 评测数据

这些都是不同机制。

因此：

> **不要把“产品记忆”“RAG”“日志分析”“用户数据用于训练”“持续学习”混成一件事。**

## 灾难性遗忘

假设模型原本会：

```text
英语
数学
编程
常识
```

现在只拿一批新的医学数据训练很久。

模型可能：

```text
医学能力 ↑
原有某些能力 ↓
```

这就是：

> **Catastrophic Forgetting**

所以持续学习通常需要考虑：

- Replay / Rehearsal
- 混合旧数据
- 正则化
- 参数高效微调
- Adapter / LoRA
- 模型架构设计
- 数据配比
- 评测与回归测试

## LoRA 与持续学习

LoRA：

> **Low-Rank Adaptation**

它不是“不会遗忘”的魔法。

它的核心思想是：

> **冻结大部分 Base Model 参数，只训练少量低秩参数。**

这样可以：

- 降低训练成本
- 降低显存需求
- 方便维护多个领域 Adapter

但：

> **LoRA 本身并不能保证没有灾难性遗忘。**

如果持续训练的数据和策略不合理，Adapter 本身同样可能出现遗忘或过拟合。

## 一个真实模型不能只用“标准 Attention”概括

到这里，你的玩具模型：

```text
Q = XWQ
K = XWK
V = XWV

Attention = softmax(QKᵀ / √dk)V
```

非常适合学习 Transformer 的基本数学。

但实际前沿模型往往会进行大量改造。

例如：

```text
MHA
GQA
MQA
MLA
Sparse Attention
Sliding Window Attention
RoPE
RMSNorm
SwiGLU
MoE
...
```

所以应该区分：

> **“Transformer 基础公式”**

和：

> **“某一个具体 LLM 的实际架构”。**

## 以 DeepSeek-V4-Pro 为例

如果拿真实的现代模型举例，就不能再简单画成：

```text
标准 MHA
+
普通 FFN
```

DeepSeek-V4-Pro 是 MoE 模型，公开资料显示：

```text
Transformer Layers：61
Hidden Size：7168
Total Parameters：约 1.6T
Activated Parameters：约 49B / Token
```

它还采用了混合注意力架构、MoE、mHC 等现代结构。

因此原笔记里：

> “DeepSeek V4 Pro 拥有 61 个 Transformer Block”

这个数字本身是对的，但它不能代表：

> “DeepSeek-V4-Pro 就是普通的 61 层标准 Transformer。”

实际结构复杂得多。

## 为什么“Block 数量”不等于“模型能力层数”

例如：

```text
61 Layers
```

只是一个架构超参数。

模型能力还与：

- hidden size
- attention 结构
- FFN / MoE
- 参数规模
- 训练 Token 数
- 数据质量
- 优化器
- 后训练
- inference strategy

等大量因素有关。

因此：

> **不能简单认为“层数越多，模型一定越强”。**

## 参数量到底在哪里？

以一个 Dense Transformer 为例，大量参数主要来自：

```text
Embedding
Attention Projection
FFN / MLP
LM Head
Norm
```

其中 FFN/MLP 往往占据相当大的参数比例。

MoE 则进一步把大量参数放进：

```text
Experts
```

但每个 Token 只激活部分专家。

## Weight Tying

有些模型会让：

```text
Input Embedding
```

和：

```text
Output LM Head
```

共享参数。

如果：

```text
Embedding = E
```

那么输出层可能使用：

```text
Eᵀ
```

这样可以：

- 减少参数量
- 让输入/输出 Token 表示空间更加统一

但：

> **不是所有 LLM 都使用 Weight Tying。**

## 为什么 LM Head 输出 vocab_size？

因为模型最终要在：

```text
整个词表
```

里选择下一个 Token。

所以：

```text
d_model
→ vocab_size
```

例如：

```text
[batch, seq, 4096]
```

经过 LM Head：

```text
[batch, seq, 120000]
```

最后一个维度：

```text
120000
```

就是：

> **每个位置对整个词表的打分。**

## Batch 维度不要忘记

之前一直使用：

```text
[4 × 6]
```

是为了方便理解。

真实训练通常还有 Batch：

```text
[batch_size, sequence_length, d_model]
```

例如：

```text
[32, 4096, 4096]
```

经过 LM Head：

```text
[32, 4096, vocab_size]
```

因此实际 LLM 中常见的张量形状是：

```text
[B, T, D]
```

其中：

```text
B = Batch Size
T = Sequence Length
D = Hidden Size / d_model
```

## Attention 的实际形状

以传统 MHA 为例：

```text
X
[B, T, D]
```

拆成 Head：

```text
[B, H, T, d_head]
```

其中：

```text
D = H × d_head
```

Attention Score：

```text
[B, H, T, T]
```

然后：

```text
Softmax
```

再与：

```text
V
[B, H, T, d_head]
```

相乘。

最终：

```text
[B, H, T, d_head]
```

再合并 Head：

```text
[B, T, D]
```

这是理解 Transformer 实现代码非常重要的一组维度。

## 为什么 Attention 的显存容易爆？

传统全注意力需要形成：

```text
[T × T]
```

的注意力关系。

所以随着：

```text
T
```

变长，Attention 的中间计算和内存压力会迅速增加。

这也是为什么长上下文一直是 Transformer 的重要工程问题。

于是出现了很多优化：

```text
FlashAttention
GQA
MQA
MLA
Sparse Attention
Sliding Window Attention
Paged Attention
KV Cache 优化
...
```

它们解决的问题并不完全相同。

## FlashAttention 是什么？

FlashAttention 很容易和“另一种 Attention 算法”混淆。

它的核心重点之一是：

> **通过更好的 GPU 内存访问和分块计算方式，在不需要完整物化巨大 Attention 矩阵的情况下，高效计算精确 Attention。**

因此：

```text
FlashAttention
```

主要是：

> **高效实现 Attention 的方法。**

而：

```text
GQA / MQA / MLA / Sparse Attention
```

更多属于：

> **注意力结构/架构设计。**

二者不是同一层面的概念。

## 一个完整的训练例子

假设：

```text
文本：

我 喜欢 吃 苹果
```

Token IDs：

```text
[t1, t2, t3, t4]
```

训练输入：

```text
[t1, t2, t3, t4]
```

标签：

```text
[t2, t3, t4, t5]
```

如果这里只到 `t4`，最后一个位置可能没有有效标签。

模型：

```text
Embedding
 ↓
Transformer × N
 ↓
LM Head
 ↓
Logits
```

得到：

```text
Position 1 → P(t2 | t1)
Position 2 → P(t3 | t1,t2)
Position 3 → P(t4 | t1,t2,t3)
Position 4 → P(t5 | t1,t2,t3,t4)
```

然后：

```text
Cross Entropy
 ↓
Loss
 ↓
Backpropagation
 ↓
Gradient
 ↓
Optimizer
 ↓
更新模型
```

## 一个完整的推理例子

Prompt：

```text
我今天很
```

假设 Tokenizer 得到：

```text
[t1, t2, t3]
```

Prefill：

```text
[t1, t2, t3]
 ↓
Transformer
 ↓
取最后一个位置
 ↓
Logits
```

模型得到：

```text
开心：0.45
累：0.20
饿：0.10
困：0.08
...
```

采样得到：

```text
开心
```

于是序列变成：

```text
[t1, t2, t3, 开心]
```

继续 Decode：

```text
[t1, t2, t3, 开心]
 ↓
下一个 Token
```

例如：

```text
。
```

于是：

```text
[t1, t2, t3, 开心, 。]
```

不断重复。

## EOS：什么时候停止？

模型词表中通常存在特殊 Token，例如：

```text
EOS / End of Sequence
```

当模型生成对应的停止 Token 后：

```text
停止生成
```

但实际 API 也可能通过：

- stop sequence
- max tokens
- 长度限制
- 工具调用结束条件
- 结构化输出约束

等方式停止。

所以：

> **生成停止不一定只有 EOS 一种原因。**

## “模型理解”应该怎么理解？

学习 LLM 时，建议避免两个极端。

### 极端 1

> “模型真的像人一样理解世界。”

这过于拟人化。

### 极端 2

> “模型只是简单统计下一个词。”

这又过度简化。

更合适的工程描述是：

> **Transformer 通过大规模参数学习，把 Token 序列映射成复杂的上下文表示，并通过这些表示完成预测、分类、推理、代码生成、工具调用等任务。**

## 从 Transformer 到 Agent

到这里，Transformer 本身做的事情可以概括为：

```text
Context
 ↓
Transformer
 ↓
Next Token Distribution
```

Agent 则是在这个能力上增加：

```text
循环
+
工具
+
外部状态
+
环境反馈
```

例如：

```text
User
 ↓
LLM
 ↓
决定调用搜索工具
 ↓
Tool
 ↓
搜索结果
 ↓
加入 Context
 ↓
LLM
 ↓
继续判断
 ↓
调用代码执行工具
 ↓
Tool Result
 ↓
LLM
 ↓
最终回答
```

因此 Agent 不是：

> “一个比 Transformer 更大的模型。”

而是：

> **利用 LLM 作为决策/生成核心，再增加工具、状态、循环和环境交互的一套系统。**

## 最终把整篇压缩成一张图

```text
                 ┌────────────────────┐
                 │      原始文本       │
                 └─────────┬──────────┘
                           ↓
                     Tokenizer
                           ↓
                      Token IDs
                           ↓
                  Token Embedding
                           ↓
                   位置信息 / RoPE
                           ↓
        ┌─────────────────────────────────┐
        │       Transformer Block 1        │
        │                                 │
        │   Norm → Attention → Residual   │
        │                                 │
        │   Norm → FFN/MLP → Residual     │
        └────────────────┬────────────────┘
                         ↓
        ┌─────────────────────────────────┐
        │       Transformer Block 2        │
        └────────────────┬────────────────┘
                         ↓
                        ...
                         ↓
        ┌─────────────────────────────────┐
        │       Transformer Block N        │
        └────────────────┬────────────────┘
                         ↓
                     Final Norm
                         ↓
                       LM Head
                         ↓

                         ↓
                       Logits
                         ↓

                         ↓
                    Next Token
                         ↓

                         ↺
```

## 最重要的几个概念关系

最后只记住下面这些：

| 概念 | 核心作用 |
| --- | --- |
| Tokenizer | 文本 ↔ Token |
| Token ID | Token 在词表中的编号 |
| Embedding | Token ID → 向量 |
| Attention | Token 之间交换上下文信息 |
| Q | 我想找什么 |
| K | 我有什么可以被匹配 |
| V | 我真正提供什么信息 |
| Causal Mask | 禁止读取未来 Token |
| Multi-Head | 在多个投影子空间中并行做注意力 |
| RoPE | 给 Q/K 注入位置信息 |
| Residual | 保留/叠加已有表示，改善深层优化 |
| RMSNorm | 稳定表示尺度和优化过程 |
| FFN/MLP | 对每个位置做非线性变换 |
| MoE | 只激活部分专家，扩大总参数规模 |
| Transformer Block | Attention + MLP 等组成的基本重复单元 |
| LM Head | Hidden State → Vocabulary logits |
| Logits | 每个 Token 的原始分数 |
| Softmax | logits → 概率分布 |
| Cross Entropy | 衡量预测分布与真实 Token 的差距 |
| Backpropagation | 计算参数梯度 |
| Optimizer | 根据梯度更新参数 |
| Pretraining | 大规模学习通用能力 |
| SFT | 学习指令和回答格式 |
| Preference/Alignment | 让输出更符合偏好、目标和约束 |
| CoT/Reasoning | 通过中间推理过程提升复杂任务求解 |
| Prefill | 一次处理 Prompt |
| Decode | 自回归逐 Token 生成 |
| KV Cache | 缓存历史 K/V，避免重复计算 |
| RAG | 从外部知识源检索内容，不等于训练模型 |
| Continual Learning | 持续适应新数据/任务并控制遗忘 |
| Agent | LLM + 工具 + 状态 + 循环/环境交互 |

## 一句话理解 Transformer

> **Transformer 的核心，就是把一串 Token 变成一串上下文相关的隐藏表示，再把每个位置的隐藏表示映射成“下一个 Token 是谁”的概率分布。**

训练：

```text
预测错了
→ Cross Entropy
→ Backpropagation
→ 更新参数
```

推理：

```text
预测一个 Token
→ 选一个 Token
→ 接回上下文
→ 再预测
→ 循环
```

而现代 LLM 的各种技术：

```text
RoPE
RMSNorm
GQA / MQA / MLA
SwiGLU
MoE
FlashAttention
KV Cache
RL / SFT / Preference Optimization
...
```

本质上都是围绕：

> **如何让这个“上下文 → 下一 Token”的系统更强、更稳定、更高效、更符合目标。**

## 本篇需要特别避免的几个误区

1. **Token ID 不是数字意义上的语义坐标。**
2. **Embedding 不等于完整的上下文语义。**
3. **Token 不等于 Word。**
4. **向量关系可以存在，但不要把经典 Word2Vec 类比当成所有 LLM 的数学规律。**
5. **Attention 不是简单平均所有 Token。**
6. **训练时可以并行计算，不代表生成时也可以并行生成未来 Token。**
7. **Causal Mask 是保证训练目标不泄漏未来信息的关键机制。**
8. **RoPE 不是简单“加一个位置向量”。**
9. **RMSNorm 不会把所有值强制限制到 [-3,3]。**
10. **Residual 不只是“防止信息丢失”，更重要的是改善深层网络的优化和梯度传播。**
11. **FFN 不是简单的“知识数据库”。**
12. **MoE 的总参数量和单 Token 激活参数量不同。**
13. **LM Head 输出的是 logits，不是直接输出文字。**
14. **Softmax 是把 logits 转成概率，不是 Transformer 本身“理解”的过程。**
15. **KV Cache 不是让 Decode 变成严格 O(1)。**
16. **Temperature=0 通常是工程上的确定性解码语义，而不是数学公式中的除以 0。**
17. **Top-K 固定候选数量，Top-P 固定累计概率质量。**
18. **后训练不等于 RLHF，SFT、DPO、GRPO、RLVR 等都可能参与。**
19. **CoT 不等于把模型“真实内心想法”直接打印出来。**
20. **RAG 不等于把知识训练进模型参数。**
21. **用户聊天数据不等于实时自动训练模型。**
22. **LoRA 可以降低适配成本，但不能保证完全没有灾难性遗忘。**
23. **真实前沿模型通常已经不是“原论文标准 Transformer”的简单复刻。**

## 结语

如果把整个 LLM 看成一个函数：

```text
f(已有 Token)
→ 下一个 Token 的概率分布
```

那么：

```text
Embedding
```

负责把离散 Token 变成连续表示；

```text
Attention
```

负责让不同 Token 交换信息；

```text
FFN / MLP
```

负责进行大量位置内的非线性变换；

```text
Residual + Norm
```

负责让深层网络能够稳定地训练和传播信息；

```text
Transformer × N
```

不断加工上下文表示；

```text
LM Head
```

把最终表示映射回整个词表；

```text
Cross Entropy + Backpropagation
```

让模型在训练中不断修正参数；

```text
Prefill + KV Cache + Decode + Sampling
```

让训练好的模型能够高效地一个 Token 一个 Token 地生成文本。

再往上：

```text
SFT / Preference / Reasoning
```

让 Base Model 变成更符合人类使用方式的模型；

```text
RAG / Tools / Memory / Agent Loop
```

则把模型从“只根据上下文生成 Token”扩展成能够访问外部知识、调用工具、执行任务并与环境交互的系统。
