神经网络只吃数字。文本要进入下一篇的词嵌入，必须先被切成一串编号——这套编号叫 **Token ID**，切分过程叫 **分词（Tokenize）**。本篇把「文字如何变成 Token」讲清楚，再补上工程里几乎天天要做的 **Token 统计**（计费、限长、预算）。一条主线贯穿：字符编码 → 词表 / BPE → 分词 → 用量统计 → 交给词嵌入。

| 概念 | 含义 |
| --- | --- |
| **分词（Tokenize）** | 把文字序列转成可被模型使用的数字序列 |
| **分词器（Tokenizer）** | 执行分词的工具（训练时建词表，推理时只查表） |
| **词元（Token）** | 序列里的每一个编号，以及它对应的那一小段文本 |
| **词表（Vocabulary / Vocab）** | Token 与 ID 的对照表，分词器的「词典」 |
| **Token 统计** | 算一段文本会变成多少个 Token（事前预估或事后核对） |

```text
文本序列
 └── 分词器 Tokenizer
      ├── 词表 Vocabulary（训练阶段建成后冻结）
      └── Tokenize（推理阶段只做匹配）
           └── Token ID 序列
                ├── 进入词嵌入（下一篇）
                └── Token 统计（计费 / 限长 / 预算）
```

## 词元

词元来自 NLP：研究如何把文字序列转化成 AI 能计算的数字序列。

- 转化过程称为 **分词（Tokenize）**。
- 转化工具称为 **分词器（Tokenizer）**。
- 转化结果是 **词元（Token）序列**，其中每一个数字就是一个 **词元（Token）**。

注意三个易混概念：

- **字符（Character）**：书写上的最小单位，如一个汉字、一个英文字母。
- **词（Word）**：人类语义上的词，如「人工智能」。
- **词元（Token）**：分词器切出来的单位，可大可小——可能是一个字、一个词、一个词的片段，甚至是不完整的 UTF-8 字节组合。

> **说明：** Token 不是「字」，也不是「词」。它是分词器按词表切出来的统计单元。同一段中文，海外模型往往切得更碎，国产模型往往更接近「一字一 Token」。

## 字符编码：最朴素的分词

实现分词最简单的办法，是把每个字符变成 UTF-8 字节，再把字节值当作 Token ID。

```python
input_text = "你好Hello!123"
result = list(input_text.encode(encoding="utf-8"))
print(f"文本：{input_text}")
print(f"UTF-8：{result}")
```

```text
文本：你好Hello!123
UTF-8：[228, 189, 160, 229, 165, 189, 72, 101, 108, 108, 111, 33, 49, 50, 51]
```

对照：

| 文本 | UTF-8 字节 | 说明 |
| --- | --- | --- |
| `你` | `228, 189, 160` | 一个汉字占 3 个字节 |
| `好` | `229, 165, 189` | 一个汉字占 3 个字节 |
| `Hello` | `72, 101, 108, 108, 111` | 一个英文字母占 1 个字节 |
| `!123` | `33, 49, 50, 51` | 符号与数字各 1 个字节 |

11 个字符膨胀成 15 个数字。这句话还不长；换成合同、论文，膨胀会非常明显。

为什么不直接把 UTF-8 字节序列当作分词结果？主要有三个原因：

- **长度膨胀**：常用汉字一个字 = 3 个 UTF-8 字节数字，序列变长后，计算量、显存、训练与推理速度全部变差。上下文窗口也按 Token 计，同样的窗口能装下的汉字更少。
- **信息浪费**：模型每一层都要重复学习「`228, 189, 160` = 你」这种固定组合，大量参数浪费在记死拼写上。
- **语义不明**：字节边界与字、词边界不对齐，模型很难学到「词从哪里开始、到哪里结束」。

更理想的状态是：每个有意义的字 / 词对应 **一个** 数字，例如：

- `你好` → `10000`
- `Hello` → `10001`
- `!` → `10002`
- `123` → `10003`

这样一来，上面那句话只需 4 个数字，且每个数字对应一块可被学习的语义。要做到这一点，必须先建立一本「词典」——**分词表（token vocabulary，Vocab）**。

## 词表

词表是 Token 到 ID 的双向对照：

- **ID → 文本片段**：解码（detokenize / decode）时用。
- **文本片段 → ID**：编码（tokenize / encode）时用。

词表一旦随模型发布，推理阶段就不再改动。不同模型的词表不同，所以 **同一段文本，在不同模型下的 Token 数可以差很多**。这也是不能拿「字符数 ≈ Token 数」去估所有模型账单的原因。

常见量级（不必记死，建立数量级即可）：

- 早期 GPT-2：约 5 万级。
- GPT-4o、Claude、Gemini 以及多数国产大模型：约 10 万～20 万级。
- 词表越大，越容易把高频词收成「整块」Token，序列往往更短；但也更占嵌入矩阵的参数。

> **说明：** 嵌入层的参数量 ≈ 词表大小 × 隐藏维度。词表从 5 万扩到 15 万，嵌入层直接变成三倍。词表不是越大越好，要在「切得更整」和「嵌入层更贵」之间折中。

## 词表的建立：BPE

词表不是人逐条编写的，而是在大量文本上统计出来的。主流算法之一是 **BPE（Byte Pair Encoding，字节对编码）**：从单字节出发，反复把「出现最频繁的相邻一对」合并成新 Token，直到词表达到目标大小。

直觉上可以这样看。假设语料里「人工智能」反复出现：

1. 一开始只有单字节（或单字符），「人工」是两段。
2. 「人」和「工」总是挨在一起 → 合并成新 Token「人工」。
3. 「人工」又总是和「智」挨在一起 → 再合并成「人工智」。
4. 高频短语会逐渐被收成更长的 Token；罕见组合则继续保持碎片。

现代大模型用的是 **字节级 BPE（BBPE）**：先把文本编成 UTF-8 字节（0～255 共 256 个初始 Token），再在字节序列上做合并。这样任意 Unicode 都能表示，不会出现「词表之外的字符无法编码」的死角。

下面是一个教学用的简易 BPE：在一段文本上合并到指定词表大小。真实训练会用 GB～TB 级语料，并单独保存「合并规则」；这里为了自洽，直接在内存里完成。

```python
from collections import Counter

def bpe_train(text, target_vocab_size=400):
  """简易 BPE：从 UTF-8 单字节出发，不断合并最高频相邻对。"""
  byte_seq = list(text.encode("utf-8"))
  vocab = {i: bytes([i]) for i in range(256)}
  seq = byte_seq.copy()
  step = 0

  print(f"文本: {len(text)} 字符")
  print(f"UTF-8 字节序列: {len(byte_seq)}（初始词表 256）")
  print(f"目标词表大小: {target_vocab_size}")

  while len(vocab) < target_vocab_size:
    pair_counts = Counter()
    for i in range(len(seq) - 1):
      pair_counts[(seq[i], seq[i + 1])] += 1
    if not pair_counts:
      break

    best_pair, _ = pair_counts.most_common(1)[0]
    new_id = len(vocab)
    vocab[new_id] = vocab[best_pair[0]] + vocab[best_pair[1]]
    step += 1

    new_seq = []
    i = 0
    while i < len(seq):
      if i + 1 < len(seq) and seq[i] == best_pair[0] and seq[i + 1] == best_pair[1]:
        new_seq.append(new_id)
        i += 2
      else:
        new_seq.append(seq[i])
        i += 1
    seq = new_seq

  print(f"合并次数: {step}")
  print(f"序列压缩: {len(byte_seq)} → {len(seq)}")
  print(f"词表: 256 → {len(vocab)}")
  return vocab

corpus = "人工智能模型通过深度学习来理解自然语言。" * 50
vocab = bpe_train(corpus, target_vocab_size=400)
```

算法在做什么：

1. 文本 → UTF-8 字节，初始词表固定为 `0～255`。
2. 统计当前序列里所有相邻 pair 的出现次数。
3. 选出最高频 pair，分配一个新 ID，写入词表。
4. 用新 ID 替换序列里所有该 pair，序列变短。
5. 重复 2～4，直到词表达到 `target_vocab_size`（或没有 pair 可合）。

> **说明：** 工业级 BPE 还会保存每一步的 **merge 规则**（哪一对、第几次合并），编码时必须按同样顺序应用，而不是「看见能匹配的最长片段就切」。下面的分词示例用最长匹配，便于理解「查词表」，与生产分词器不完全等同。

除了 BPE，常见还有 WordPiece（BERT 系）、Unigram（SentencePiece 系）。大模型侧目前仍以字节级 BPE 及其变体为主。

## 分词：用固定词表做匹配

词表在训练阶段建好后就冻结。之后的分词只是：把新文本编成字节，再按词表把字节切成一串 ID。不再统计、不再合并。

下面用「最长匹配」演示查表过程——从当前位置起，优先吃进词表里能匹配的最长片段：

```python
def tokenize(text, vocab):
  bytes_to_id = {}
  for tid, raw in vocab.items():
    if raw not in bytes_to_id:
      bytes_to_id[raw] = tid
  max_len = max(len(b) for b in bytes_to_id)

  data = text.encode("utf-8")
  ids = []
  i = 0
  while i < len(data):
    for length in range(min(max_len, len(data) - i), 0, -1):
      piece = data[i : i + length]
      if piece in bytes_to_id:
        ids.append(bytes_to_id[piece])
        i += length
        break
  return ids

test_text = "人工智能模型通过深度学习来理解自然语言。"
ids = tokenize(test_text, vocab)
print(f"测试文本: {test_text}")
print(f"UTF-8 字节数: {len(test_text.encode('utf-8'))}")
print(f"分词数量: {len(ids)}")
print(ids)
```

若词表足够大、且训练语料覆盖了这些词，「人工智能」「深度学习」这类高频块往往会变成很少的几个 Token，序列明显短于 UTF-8 字节数。

实际使用中，常会看到 **某个汉字被拆成多个 Token**。原因通常是：

- **词表太小**：还没把该字（或其常见组合）收进词表，就已达到词表上限。
- **语料没见过**：训练文本里几乎没出现过这个字 / 词，BPE 不会为它单独合并。
- **只见过组合、没见过单字高频**：有的字总是作为词的一部分出现，单独拿出来时只能退回更碎的字节片段。

一个粗略对照（不同模型、不同版本会浮动，只用来建立直觉）：

| 文本单元 | 海外模型 | 国产模型 |
| --- | --- | --- |
| 1 个汉字 | 约 1.3～1.5 Token | 约 0.8～1 Token |
| 1 个英文字母 | 平均 0.25～0.33 Token | 平均 0.25～0.33 Token |
| 1 个英文单词 | 平均约 1.3 Token | 平均约 1.3 Token |

> **说明：** 国产模型词表通常为中文分配了更多「整字 / 整词」条目，所以同样一篇中文，Token 数往往更少，上下文窗口能装下更多汉字，中文计费也相对更划算。英文两侧差异不大，因为 BPE 本就从英文语料长出来。

分词器里往往还有若干 **特殊 Token**，不对应普通文本，而对应协议：

- 序列开始 / 结束（BOS / EOS）
- 填充（PAD）
- 未知（UNK，纯 BPE 较少依赖，因为单字节总能兜底）
- 对话角色、工具调用等聊天模板标记

统计「发给模型的总 Token」时，这些特殊 Token 和聊天模板（system / user / assistant 包装）都会算进去，往往比「纯用户那句话」多一截。

不同训练语料、不同分词算法，会得到不同格式和内容的词表，从而得到不同的分词结果。**模型与分词器必须配对使用**，不能拿 A 模型的词表去切 B 模型的输入。

## Token 统计

Token 统计：把一段文本序列换算成 Token 数量。分为 **事后统计** 和 **事前统计**。

**事后统计**：调用模型服务商 API 后，响应里会带回本次实际用量（prompt tokens、completion tokens、total tokens）。账单以这个为准。

**事前统计**：把文本发给大模型 **之前** 先算一遍。常见用途：

- **单轮输入长度拦截**：用户粘贴 10 万字合同，事前算出已超上下文窗口（如 100k Token），直接弹窗「文本过长，请分段上传」，避免发起无效调用。
- **用户额度 / 充值预校验**：C 端付费产品（AI 写作、客服、知识库问答）在调用前预估本次总 Token；余额不足则拦截并提示充值，不必等 API 报错。
- **企业预算前置审批**：内部 AI 平台按部门做月度预算。员工上传大文件前，本地估算 Token 并换算成本，超阈值先走审批。
- **报价前置展示**：SaaS 在用户确认前实时显示「本次预估消耗 XX Token，约 XX 元」，减少账单争议。

> **说明：** 事前统计是 **估计**。聊天模板、工具定义、多轮历史、思维链隐藏 Token 都可能让实际用量高于「只对用户那句话 encode」的结果。计费仍以事后账单为准；事前统计的价值是拦截、展示与控预算。

统计手段按「你能不能拿到该模型的词表」分成三类。

### API 统计

部分服务商提供专门的 Token 估算接口，用 **官方词表** 在云端计算，不必把词表下载到本地。以 Moonshot AI（Kimi）为例：

```bash
uv add requests==2.34.2 python-dotenv==1.2.2
```

```python
import os
import requests
from dotenv import load_dotenv

load_dotenv("../.env")

# API Key 申请：https://platform.moonshot.cn
API_KEY = os.environ.get("MOONSHOT_API_KEY")

url = "https://api.moonshot.cn/v1/tokenizers/estimate-token-count"
text = "人工智能正在深刻改变我们的生活，从智能助手到自动驾驶，AI 无处不在。"

response = requests.post(
  url,
  headers={
    "Authorization": f"Bearer {API_KEY}",
    "Content-Type": "application/json",
  },
  json={
    "model": "kimi-k3",
    "messages": [
      {"role": "user", "content": text},
    ],
  },
)

result = response.json()
print(f"接口返回：{result}")
print(f"文本：{text}")
print(f"文本长度：{len(text)}")
print(f"Token 数：{result['data']['total_tokens']}")
```

> **说明：** 估算接口通常按 **messages 整段对话** 计，已包含角色等包装开销，比只对 `content` 做 encode 更接近真实请求。模型名、字段路径以当时文档为准。

### SDK 统计

OpenAI 系模型可以用官方分词库 **tiktoken**，词表下载一次后完全本地计算，无需 API Key。

```bash
uv add tiktoken==0.13.0
```

```python
import tiktoken

encoding = tiktoken.encoding_for_model("gpt-4o")

text = "人工智能正在深刻改变我们的生活，从智能助手到自动驾驶，AI 无处不在。"
tokens = encoding.encode(text)

print(f"文本：{text}")
print(f"文本长度：{len(text)}")
print(f"Token 序列：{tokens}")
print(f"Token 数：{len(tokens)}")
```

`encoding_for_model("gpt-4o")` 会选中该模型对应的编码（如 `o200k_base`）。换模型就要换编码：GPT-3.5 / GPT-4 常用 `cl100k_base`，GPT-4o 常用 `o200k_base`。编码不一致，数出来的 Token 就不能拿去估对应模型的账单。

> **说明：** 首次运行会联网下载词表并缓存，之后统计都在本地完成。这只能覆盖 tiktoken 支持的编码；Claude、Gemini、多数国产闭源模型不能用这一套直接估。

### 开源模型：transformers

开源模型的分词器文件会随模型放到 Hugging Face。**transformers** 是 Hugging Face 的官方库，用来加载这些分词器（以及模型）。站点：<https://huggingface.co/>

加载分词器 **不必下载模型权重**，通常只有几 MB 到几十 MB 的 tokenizer 配置与词表。

```bash
uv add transformers==5.14.1
```

```python
import os

# 国内访问 Hugging Face 可走镜像；能直连则删掉这行
os.environ["HF_ENDPOINT"] = "http://hf-mirror.com"

from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("deepseek-ai/DeepSeek-V3")

text = "人工智能正在深刻改变我们的生活，从智能助手到自动驾驶，AI 无处不在。"
tokens = tokenizer.encode(text)

print(f"文本：{text}")
print(f"文本长度：{len(text)}")
print(f"Token 序列：{tokens}")
print(f"Token 数：{len(tokens)}")
```

`from_pretrained` 的参数必须是 **该模型自己的** 分词器仓库（或本地目录）。Qwen、Llama、DeepSeek 的词表不同，交叉使用会得到错误的 ID，后续推理也会错。

三类方式怎么选：

| 方式 | 适用 | 是否本地 | 是否精确对齐该模型 |
| --- | --- | --- | --- |
| 服务商估算 API | 闭源、官方提供估算接口 | 否 | 是（按其词表） |
| tiktoken | OpenAI 系及同编码模型 | 是（首次下词表） | 仅对应该编码 |
| transformers | Hugging Face 上的开源模型 | 是（下 tokenizer 文件） | 是（用模型自己的词表） |

没有词表、也没有估算接口时，只能用经验系数粗估（如「中文 1 字 ≈ 1 Token」），误差可能到 30% 以上，只适合做数量级判断，不适合做计费。

## 和下一篇的衔接

分词的输出是一条 **Token ID 序列**，例如 `[33256, 11789, …]`。下一篇会说明：这些 ID 只是编号，不能做语义算术，所以还要经过 **词嵌入**，把每个 ID 查成一条高维向量，再进入注意力。

同时记住两个长度：

- **上下文长度（Context Length）**：这一次实际送进模型的 Token 数。
- **上下文窗口（Context Window）**：模型能容纳的最大 Token 数。事前统计的首要用途，就是避免还没开算就先把窗口撑爆。

> **说明：** 分词器是模型的一部分，不是可随意替换的前置插件。换分词器等于换了一套 ID 体系，嵌入矩阵对不上，模型立刻失效。
