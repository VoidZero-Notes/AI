大模型不能直接理解 `"你好，世界"` 这样的文本。文本进入模型之前，要先经过 **Tokenizer（分词器）**，被切成若干个 **Token**，再把每个 Token 映射成一个 **Token ID**。这些 ID 后面会被送入 **词嵌入（Embedding）**，转换成模型真正处理的向量。

本篇只解决一个问题：

> **一段文字，是怎样一步一步变成 `[Token ID, Token ID, ...]` 的？**

同时把工程里经常遇到的 **Token 统计、上下文窗口、计费、不同模型为什么 Token 数不同** 一起讲清楚。

## 先建立完整流程

先不要急着记 BPE、词表等术语，先看整个链路：

```text
原始文本
  │
  ▼
Tokenizer
  │
  ├── 文本规范化 / 特殊处理
  │
  ├── 预切分（pre-tokenization，具体实现视 tokenizer 而定）
  │
  ├── 子词 / 字节切分
  │
  ├── 按训练好的规则进行合并 / 匹配
  │
  ▼
Token 序列
  │
  ▼
Token ID 序列
  │
  ├── 统计 Token 数量
  │     ├── 上下文长度检查
  │     ├── 费用估算
  │     └── 配额 / 预算控制
  │
  ▼
Embedding
  │
  ▼
向量
  │
  ▼
Transformer
```

这里最重要的是区分：

- **Token**：切出来的一段文本单元。
- **Token ID**：这个 Token 在词表中的整数编号。
- **Tokenizer**：负责把文本和 Token ID 序列互相转换的组件。
- **Vocabulary（词表）**：保存 Token 与 ID 对应关系的集合。
- **Tokenize / Encode**：文本 → Token ID。
- **Decode**：Token ID → 文本。

## 什么是 Token？

### Token 不是「字」，也不是「词」

这是最容易产生误解的地方。

例如：

```text
人工智能正在改变世界
```

人类可能按照：

```text
人工智能 / 正在 / 改变 / 世界
```

理解。

但是 Tokenizer 不一定这样切。

它可能得到类似：

```text
人工智能 / 正在 / 改变 / 世界
```

也可能得到：

```text
人工 / 智能 / 正在 / 改变 / 世界
```

甚至某些情况下，一个字符也可能被进一步拆成多个更小的 Token。

因此：

> **Token 是 Tokenizer 根据自己的词表和切分规则得到的基本处理单位，不等同于人类语言学意义上的「字」或「词」。**

### 三个概念一定要分清

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 字符 Character | 文本中的字符单位 | `你`、`A`、`!` |
| 词 Word | 人类语言意义上的词 | `人工智能` |
| Token | Tokenizer 切出来的模型处理单位 | `人工`、`智能`、`ing`、某些字节片段 |

例如英文：

```text
unbelievable
```

可能被切成：

```text
un / believable
```

也可能是：

```text
un / believe / able
```

具体怎么切，取决于模型使用的 Tokenizer。

## 为什么不能直接把文字交给模型？

因为神经网络本质上处理的是数字。

例如：

```text
你好
```

本身是文本字符串。

模型真正接收的是类似：

```text
[12345, 67890]
```

这样的整数序列。

所以必须完成：

```text
文本
 ↓
Token
 ↓
Token ID
 ↓
Embedding 向量
 ↓
Transformer
```

注意：

> **Token ID 本身没有语义。**

例如：

```text
100 = 你好
101 = 世界
```

并不代表：

```text
101 比 100 更大，所以“世界”比“你好”更重要。
```

ID 只是编号。

真正让 Token 具有可学习表示的是后面的 **Embedding（词嵌入）**。

## 最简单的方案：把文本变成字节

在理解 BPE 之前，可以先想一种非常朴素的方法：

> **把文本编码成 UTF-8 字节，然后直接使用这些字节作为最基础的单位。**

例如：

```python
text = "你好Hello!123"

data = list(text.encode("utf-8"))

print(data)
```

结果类似：

```text
[228, 189, 160, 229, 165, 189, 72, 101, 108, 108, 111, 33, 49, 50, 51]
```

其中：

```text
你 → 228, 189, 160
好 → 229, 165, 189
H  → 72
e  → 101
l  → 108
o  → 111
!  → 33
1  → 49
2  → 50
3  → 51
```

因此：

```text
你好Hello!123
```

虽然只有 11 个字符，但 UTF-8 后变成了 15 个字节。

### 为什么不直接使用 UTF-8 字节？

这种方法当然可以工作，实际上很多现代 Tokenizer 的基础思路就和「字节」有关。

但如果**每一个字节都直接作为一个 Token**，会产生一个问题：

```text
你好
↓
228 189 160 229 165 189
```

一个常见汉字就可能需要多个 Token。

英文：

```text
Hello
↓
72 101 108 108 111
```

5 个字母就变成 5 个单位。

这样会让序列变得比较长。

而 Transformer 的计算成本和序列长度高度相关，因此我们希望：

> **常见的字节组合可以被压缩成更大的 Token。**

这就是 BPE 等子词 Tokenizer 要解决的问题。

## Vocabulary（词表）是什么？

为了让数字和文本片段对应起来，需要有一张表：

```text
Token ID       Token
----------------------
0              ...
1              ...
2              ...
...
10000          人工
10001          智能
10002          Hello
```

这就是 **Vocabulary（词表）**。

可以简单理解为：

> **词表 = Token 和 Token ID 的映射关系。**

它至少存在两个方向：

```text
文本片段 → Token ID
Token ID → 文本片段
```

对应：

```text
Encode：
文本 → Token ID

Decode：
Token ID → 文本
```

例如：

```text
"Hello" → 1234
1234 → "Hello"
```

## 词表是怎么来的？

这里就进入 Tokenizer 最核心的部分：

> **词表不是人工一个一个写出来的，而通常是通过大量训练语料和某种 Tokenizer 训练算法构建出来的。**

常见方法包括：

- BPE（Byte Pair Encoding）
- WordPiece
- Unigram
- SentencePiece 体系中的不同算法 / 实现

现代大模型中经常看到的是 **BPE 或 BPE 的变体**，但不能简单地说所有大模型都使用 BPE。

## BPE 到底在做什么？

BPE 可以先用一句非常直观的话理解：

> **从比较小的单位开始，不断寻找训练语料中出现频率高的相邻组合，把它们合并成更大的 Token。**

例如假设训练语料中经常出现：

```text
人工
```

那么经过训练后，可能产生：

```text
人 + 工
↓
人工
```

如果：

```text
人工智能
```

也大量出现，那么还可能继续产生：

```text
人工 + 智
↓
人工智
```

然后：

```text
人工智 + 能
↓
人工智能
```

最终，高频组合可能形成更大的 Token。

### 从字节开始的 BPE

现代很多 Tokenizer 使用 **Byte-level BPE（字节级 BPE）** 思路。

可以粗略理解成：

```text
原始文本
  ↓
UTF-8 字节
  ↓
初始的基础 Token
  ↓
不断执行 merge
  ↓
得到更大的 Token
```

UTF-8 的单字节范围是：

```text
0 ~ 255
```

因此可以把 256 个字节作为基础单位。

然后通过训练不断增加合并后的 Token。

## BPE 的训练过程

假设最开始：

```text
A B C A B C A B
```

统计相邻组合：

```text
A B → 3 次
B C → 2 次
C A → 2 次
```

最高频的是：

```text
A B
```

于是合并：

```text
A B → AB
```

序列变成：

```text
AB C AB C AB
```

然后重新统计。

如果：

```text
AB C
```

又是最高频组合，就继续：

```text
AB C → ABC
```

于是：

```text
ABC ABC AB
```

不断重复，直到达到目标词表大小。

所以 BPE 的核心就是：

```text
统计高频相邻 pair
        ↓
选择最高频 pair
        ↓
合并
        ↓
新增一个 Token
        ↓
重新统计
        ↓
继续合并
```

## BPE 真正重要的东西：Merge Rules

这里有一个非常重要、容易被忽略的知识点。

BPE 训练完成之后，不能只保存：

```text
最终词表
```

还必须保存：

```text
Merge Rules（合并规则）
```

例如：

```text
规则 1：A + B → AB
规则 2：AB + C → ABC
规则 3：D + E → DE
...
```

为什么？

因为模型真正分词的时候，需要知道：

> **这些 Token 应该按照什么顺序合并。**

因此，生产环境中的 BPE Tokenizer 并不是简单地：

> 「找到最长字符串，然后切进去。」

而是按照训练得到的规则进行确定性的编码。

## 训练和推理一定要分开理解

这是理解 Tokenizer 的关键。

### Tokenizer 训练阶段

训练 Tokenizer 时：

```text
大量训练语料
   ↓
统计频率
   ↓
学习 Token
   ↓
学习 Merge Rules
   ↓
生成 Vocabulary
```

这是一个「学习规则」的过程。

### 模型推理阶段

模型真正运行时：

```text
新文本
  ↓
使用已经训练好的 Tokenizer
  ↓
按照固定规则编码
  ↓
Token ID
```

此时不会重新统计：

```text
“这个词出现得多不多？”
```

也不会因为今天某个词出现很多次，就临时创造一个新 Token。

所以：

> **Tokenizer 的词表和规则是在训练阶段确定的；推理阶段主要是按照已经确定的规则进行编码。**

## 为什么不同模型的 Token 数不同？

这是实际开发中非常重要的问题。

例如同一句：

```text
人工智能正在改变世界
```

不同模型可能得到：

```text
模型 A：
[人工智能] [正在] [改变] [世界]
→ 4 Token
```

另一个模型可能得到：

```text
模型 B：
[人工] [智能] [正在] [改变] [世界]
→ 5 Token
```

甚至可能切得更碎。

原因主要是：

1. Tokenizer 算法不同
2. 训练语料不同
3. 词表大小不同
4. Merge Rules 不同
5. 对不同语言的优化程度不同
6. 特殊 Token 和聊天模板不同

因此：

> **Token 数量不是文本本身的固定属性，而是“文本 + Tokenizer”的共同结果。**

也就是说：

```text
同一段文本
      ↓
Tokenizer A → 100 Token
Tokenizer B → 130 Token
Tokenizer C → 90 Token
```

完全可能。

## Token 并不一定具有完整语义

这里需要纠正一个很常见的理解。

不要把：

```text
Token = 一个有完整语义的词
```

作为定义。

实际上 Token 更像一种：

> **为了让文本能够高效地表示成离散序列，而通过统计学习得到的子词 / 字节片段单位。**

例如英文：

```text
playing
```

可能被切成：

```text
play + ing
```

其中：

```text
play
```

有比较明显的语义。

但：

```text
ing
```

只是一个高频后缀。

某些情况下 Token 甚至可能只是字节级片段。

所以：

> **Token 的首要目标不是“语义完整”，而是在表达能力、序列长度、词表规模之间取得平衡。**

## 为什么一个汉字有时候会对应多个 Token？

如果使用的是字节级 Tokenizer，那么一个汉字的 UTF-8 表示本身就是多个字节。

例如：

```text
你
↓
E4 BD A0
```

如果 Tokenizer 没有把这个字节组合合并成一个更大的 Token，就可能继续拆成多个 Token。

但如果训练过程中：

```text
E4 BD A0
```

这种组合非常常见，Tokenizer 就可能学习到对应的更大 Token。

因此：

```text
一个汉字 = 1 Token
```

并不是规则。

同样：

```text
一个英文单词 = 1 Token
```

也不是规则。

## 不要死记「中文一个字等于多少 Token」

网上经常看到：

```text
中文 1 字 ≈ 1 Token
英文 1 单词 ≈ 1.3 Token
```

这种说法只能作为非常粗略的经验。

实际上：

```text
Token 数
```

取决于具体模型的 Tokenizer。

因此不能简单得出：

```text
中文 = 1 Token
英文 = 1.3 Token
```

更不能把这种经验直接用于精确计费。

正确的理解应该是：

> **需要精确知道 Token 数，就使用目标模型对应的官方 Tokenizer 或官方 Token 统计接口。**

## 特殊 Token 是什么？

除了普通文本 Token，Tokenizer 通常还会存在一些 **Special Tokens（特殊 Token）**。

它们不是普通文本中的自然语言片段，而是用来表达模型协议或结构。

常见的有：

| 类型 | 含义 |
| --- | --- |
| BOS | Beginning Of Sequence，序列开始 |
| EOS | End Of Sequence，序列结束 |
| PAD | Padding，填充 |
| UNK | Unknown，未知 Token |
| Chat Template Tokens | 对话结构 / 角色 / 工具调用等特殊标记 |

例如聊天模型内部可能需要表达：

```text
system
user
assistant
```

这些信息有时会通过特殊 Token 或聊天模板编码进去。

所以你看到：

```text
用户真正输入的文字
```

和：

```text
最终真正送给模型的 Token
```

并不一定是一回事。

## Chat Template 为什么会影响 Token 数？

假设用户只输入：

```text
你好
```

表面看只有两个汉字。

但聊天模型实际可能把请求组织成类似：

```text
<system>
你是一个助手
</system>

<user>
你好
</user>

<assistant>
```

这些角色、边界、模板标记都会参与模型输入。

因此：

```text
用户看到的文本
≠
模型最终收到的完整 Token 序列
```

这也是为什么：

> **自己简单 encode 用户的 content，得到的 Token 数，不一定等于 API 最终计费的 prompt tokens。**

## 模型和 Tokenizer 必须匹配

这是非常重要的一条。

假设：

```text
模型 A
Tokenizer A
Embedding A
```

三者是配套的。

Tokenizer A 可能规定：

```text
“你好” → [123, 456]
```

而 Tokenizer B 可能规定：

```text
“你好” → [789]
```

那么不能：

```text
Tokenizer B
   ↓
得到 B 的 Token ID
   ↓
送进模型 A
```

因为：

```text
Token ID
```

本身只是一个索引。

模型 A 的 Embedding 矩阵里：

```text
第 123 行
```

对应的是 A 的 Token 体系。

如果你拿 B 的 ID 进去，语义就完全错位了。

因此：

> **模型、Tokenizer、词表、Embedding 的 ID 体系必须保持一致。**

## 词表越大越好吗？

不是。

词表大小存在明显的权衡。

例如：

```text
词表小
↓
Token 更容易切碎
↓
序列更长
```

而：

```text
词表大
↓
更多常见组合可以直接成为 Token
↓
Token 序列可能更短
```

但词表变大也有代价。

Embedding 矩阵的参数量大致与：

```text
词表大小 × 隐藏维度
```

有关。

例如隐藏维度为：

```text
4096
```

词表从：

```text
50,000
```

扩大到：

```text
150,000
```

那么仅从矩阵规模来看，Embedding 相关参数就会明显增加。

所以 Tokenizer 设计本质上是在做一个权衡：

```text
词表规模
    ↕
Token 序列长度
    ↕
Embedding 参数量
    ↕
多语言覆盖能力
```

并不是：

> 词表越大，模型就一定越好。

## Tokenizer 的完整工作过程

现在可以把整个过程串起来。

假设输入：

```text
人工智能正在学习
```

### 第一步：输入文本

```text
"人工智能正在学习"
```

### 第二步：文本预处理

具体操作取决于 Tokenizer，可能涉及：

```text
Unicode / 文本规范化
特殊字符处理
空格处理
特殊 Token 检测
预切分
```

并不是所有 Tokenizer 都完全一样。

### 第三步：转换到内部表示

对于 Byte-level BPE，可以理解为：

```text
文本
 ↓
UTF-8 bytes
```

例如：

```text
人
↓
E4 BA BA
```

### 第四步：应用 Tokenizer 规则

根据训练阶段得到的：

```text
Vocabulary
+
Merge Rules
```

把高频的字节 / 子词组合合并。

例如最终可能得到：

```text
人工智能
正在
学习
```

也可能得到其他切法。

具体结果完全由该模型的 Tokenizer 决定。

### 第五步：映射成 Token ID

例如：

```text
人工智能 → 12345
正在     → 67890
学习     → 24680
```

最终：

```text
[12345, 67890, 24680]
```

这就是模型真正意义上的离散输入。

### 第六步：进入 Embedding

Embedding 根据 Token ID 查表：

```text
12345 → 一条高维向量
67890 → 一条高维向量
24680 → 一条高维向量
```

例如：

```text
12345 → [0.12, -0.31, 0.87, ...]
67890 → [0.42,  0.16, 0.11, ...]
24680 → [-0.08, 0.55, 0.31, ...]
```

然后才进入 Transformer。

所以：

```text
文本
 ↓
Tokenizer
 ↓
Token ID
 ↓
Embedding
 ↓
向量
 ↓
Transformer
```

这条链路一定要记住。

## Token 统计是什么？

Token 统计就是：

> **计算一段文本经过指定 Tokenizer 后，会得到多少个 Token。**

例如：

```text
文本
 ↓
Tokenizer
 ↓
[123, 456, 789, 100]
```

那么：

```text
Token 数 = 4
```

## 为什么要统计 Token？

实际开发中主要有几个用途。

### 检查上下文长度

假设模型最多支持：

```text
128K Token
```

用户上传了一份超长文档。

在请求模型之前，可以先估算：

```text
文档 → 150K Token
```

那么就知道：

```text
已经超过上下文窗口
```

可以提前：

- 拒绝请求
- 自动切分
- 摘要压缩
- RAG 检索后只发送相关内容

### 成本估算

很多模型 API 按 Token 计费。

例如：

```text
输入 Token
+
输出 Token
```

共同决定费用。

所以 AI 应用经常需要：

```text
请求前估算
↓
预算检查
↓
调用模型
↓
读取 API 实际用量
```

### 配额控制

例如产品规定：

```text
每个用户每天最多消耗 1,000,000 Token
```

那么服务端可以根据 Token 用量做：

```text
额度扣减
限流
预算控制
```

## 事前统计 vs 事后统计

这是工程中很重要的区别。

### 事前统计

模型调用之前：

```text
文本
 ↓
Tokenizer
 ↓
估算 Token
 ↓
决定是否允许请求
```

用途：

- 上下文长度检查
- 预算控制
- 用户额度预扣
- 大文件上传拦截
- 前端展示预计消耗

但要注意：

> **事前统计可能只是估算，不一定等于最终 API 账单。**

因为最终请求可能还包含：

```text
System Prompt
Chat Template
历史消息
Tool Definitions
结构化输出相关内容
其他协议字段
```

### 事后统计

API 调用完成以后，服务商通常会返回实际使用量，例如：

```text
prompt tokens
completion tokens
total tokens
```

实际字段名称取决于服务商。

对于计费来说：

> **以服务商最终返回的实际 usage 为准。**

## 如何统计 Token？

根据模型类型，可以分成几种方式。

### 方式一：官方 Token 统计 API

有些模型服务商会提供官方 Token 估算接口。

优点：

```text
使用官方 Tokenizer
↓
不需要自己下载词表
↓
结果更接近真实 API 请求
```

适合：

```text
闭源模型
```

但具体接口、字段、模型名称会随着服务商 API 版本变化，应以官方文档为准。

### 方式二：使用官方 / 对应 SDK

例如 OpenAI 生态常见：

```python
import tiktoken

encoding = tiktoken.encoding_for_model("gpt-4o")

text = "人工智能正在改变我们的生活。"

tokens = encoding.encode(text)

print(tokens)
print(len(tokens))
```

这里：

```python
encoding.encode(text)
```

就是：

```text
文本
 ↓
Tokenizer
 ↓
Token IDs
```

而：

```python
len(tokens)
```

就是：

```text
Token 数量
```

注意：

> `tiktoken` 只能用于它支持的编码体系。不能因为两个模型都是大语言模型，就认为可以用同一个 Tokenizer。

### 方式三：开源模型使用 Transformers

对于 Hugging Face 上的开源模型，可以使用对应模型自己的 Tokenizer。

例如：

```python
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained(
  "模型自己的 tokenizer / 模型仓库"
)

text = "人工智能正在改变我们的生活。"

tokens = tokenizer.encode(text)

print(tokens)
print(len(tokens))
```

关键点是：

```text
必须加载目标模型对应的 Tokenizer。
```

例如：

```text
Qwen → Qwen Tokenizer
Llama → Llama Tokenizer
DeepSeek → DeepSeek 对应 Tokenizer
```

不要随便混用。

## 三种 Token 统计方式对比

| 方式 | 适合场景 | 是否本地计算 | 精确程度 |
| --- | --- | --- | --- |
| 官方 Token 统计 API | 闭源模型 / 服务商提供接口 | 否 | 通常最接近服务商实际规则 |
| 对应 Tokenizer SDK | 有官方或兼容 Tokenizer 的模型 | 是 | 对应编码规则时准确 |
| Transformers | Hugging Face 开源模型 | 是 | 使用模型自己的 Tokenizer 时准确 |
| 经验公式 | 没有 Tokenizer 的情况 | 是 | 只能粗略估算 |

最后一种：

```text
中文 1 字 ≈ 1 Token
```

之类的公式只能用于：

```text
数量级估算
```

不能用于：

```text
精确计费
```

## 一个非常重要的区别：Token 数 ≠ 字符数 ≠ 字节数

这三个长度不要混淆。

假设：

```text
你好Hello
```

可能有：

```text
字符数
↓
8
```

UTF-8：

```text
字节数
↓
11
```

经过某个 Tokenizer：

```text
Token 数
↓
可能是 5，也可能是 6，也可能是其他数量
```

因此：

```text
字符数
≠
字节数
≠
Token 数
```

而模型上下文窗口通常讨论的是：

```text
Token
```

不是字符。

## Context Length 和 Context Window

这两个概念也很容易混。

### Context Window

模型能够处理的**最大上下文容量**。

例如：

```text
Context Window = 128K Token
```

可以理解成：

```text
最多容纳约 128K Token
```

### Context Length

某一次请求实际使用的上下文长度。

例如模型支持：

```text
128K Token
```

这一次请求只使用：

```text
20K Token
```

那么：

```text
Context Window = 128K
Context Length = 20K
```

简单理解：

```text
Context Window = 最大容量
Context Length = 本次实际占用
```

## 为什么 Token 越少通常越好？

在其他条件相同的情况下：

```text
Token 更少
↓
序列更短
↓
需要处理的位置更少
↓
通常计算 / 显存 / 成本压力更低
```

尤其 Transformer 的注意力机制对序列长度比较敏感。

因此一个设计良好的 Tokenizer 希望做到：

> **用合理的词表规模，把常见文本压缩成尽可能短、同时又能够覆盖各种语言和字符的 Token 序列。**

但不是：

```text
Token 越少越绝对好。
```

因为词表过大、Embedding 参数增加、多语言覆盖、训练稳定性等都需要综合考虑。

## 为什么模型的上下文不是「多少字」？

例如：

```text
模型支持 128K Token
```

不能直接理解成：

```text
支持 128K 个汉字
```

也不能直接理解成：

```text
支持 128K 个英文单词
```

因为：

```text
Token 数
```

和：

```text
字符 / 单词数量
```

并不是固定比例。

正确理解：

```text
上下文窗口
↓
按照 Token 计算
```

因此开发 AI 应用时，如果要严格判断文本是否超长：

> **应该使用目标模型对应的 Tokenizer 计算，而不是简单使用 `len(text)`。**

## 一个完整例子

假设用户输入：

```text
请帮我解释 Transformer 的 Attention 机制。
```

整个过程可以理解为：

### 用户输入文本

```text
请帮我解释 Transformer 的 Attention 机制。
```

### Tokenizer 处理

Tokenizer 根据自己的规则进行：

```text
规范化
↓
预处理 / 预切分
↓
子词 / 字节处理
↓
应用 merge rules
```

得到 Token：

```text
[请] [帮] [我] [解释] [Transformer] [的] [Attention] [机制] [。]
```

注意：

> 上面只是为了说明概念，真实模型的切分结果可能完全不同。

### 映射成 Token ID

例如：

```text
[123, 456, 789, 2345, 6789, ...]
```

### Embedding

每个 ID 作为索引，从 Embedding 矩阵中取出向量：

```text
123 → vector
456 → vector
789 → vector
...
```

### Transformer

这些向量进入：

```text
Position Information
        ↓
Self-Attention
        ↓
Feed Forward
        ↓
...
```

最终模型输出：

```text
Token IDs
```

然后再：

```text
Token IDs
 ↓
Tokenizer Decode
 ↓
文本
```

所以完整闭环是：

```text
文本
 ↓
Tokenize / Encode
 ↓
Token IDs
 ↓
Embedding
 ↓
Transformer
 ↓
输出 Token IDs
 ↓
Decode
 ↓
文本
```

## Encode 和 Decode

最后再把两个方向记住。

### Encode

```text
文本
 ↓
Tokenizer
 ↓
Token IDs
```

例如：

```python
tokenizer.encode("你好")
```

### Decode

```text
Token IDs
 ↓
Tokenizer
 ↓
文本
```

例如：

```python
tokenizer.decode([123, 456])
```

因此：

```text
Encode = 文本 → 数字
Decode = 数字 → 文本
```

## 把整个知识压缩成一张图

```text
                    Tokenizer
                       │
                       ▼
                 ┌─────────────┐
                 │ 原始文本     │
                 └──────┬──────┘
                        │
                        ▼
              文本规范化 / 预处理
                        │
                        ▼
              字节 / 子词等内部单位
                        │
                        ▼
              Vocabulary + Merge Rules
                        │
                        ▼
                  Token 序列
                        │
                        ▼
                  Token ID 序列
                        │
            ┌───────────┴───────────┐
            │                       │
            ▼                       ▼
       Token 统计                Embedding
            │                       │
       ┌────┼────┐                  ▼
       │    │    │               向量序列
       │    │    │                  │
       ▼    ▼    ▼                  ▼
     限长  计费  配额             Transformer
```

## 最终一定要记住的 10 件事

### 模型不能直接处理字符串

模型最终处理的是数字表示。

### Token 不是简单等于「一个字」或「一个词」

Token 是 Tokenizer 定义的文本处理单位。

### Token ID 只是编号

```text
ID 本身没有语义。
```

真正的向量表示来自 Embedding。

### Vocabulary 是 Token ↔ ID 的映射

它决定：

```text
某个 Token 对应哪个 ID。
```

### BPE 的核心是「高频相邻组合不断合并」

```text
小单位
 ↓
统计高频 pair
 ↓
merge
 ↓
更大 Token
```

### BPE 不只是最终词表

还需要保存：

```text
Merge Rules
```

否则无法按照训练时的规则正确编码。

### 推理时不会重新训练 Tokenizer

推理阶段使用已经确定的：

```text
Vocabulary
+
Tokenizer Rules
```

处理新文本。

### 同一句话在不同模型中 Token 数可能不同

因为：

```text
Tokenizer 不同
```

所以：

```text
Token 数是“文本 + Tokenizer”的结果。
```

### 精确 Token 统计必须使用目标模型对应的 Tokenizer

不要使用：

```text
中文字符数 × 某个经验系数
```

去做精确计费。

### 最重要的一条链路

```text
文本
 ↓
Tokenizer
 ↓
Token
 ↓
Token ID
 ↓
Embedding
 ↓
向量
 ↓
Transformer
```

理解这条链路，Token、分词、词表、BPE、Embedding 之间的关系就基本串起来了。

## 和下一篇「词嵌入」的衔接

到这里，我们得到的是：

```text
[12345, 67890, 24680]
```

但是这些数字只是：

```text
Token ID
```

例如：

```text
12345
```

本身没有「人工智能」的语义。

模型接下来要做的是：

```text
Token ID
   ↓
Embedding Lookup
   ↓
高维向量
```

例如：

```text
12345
 ↓
[0.12, -0.31, 0.87, ...]
```

这些向量才是 Transformer 后续计算的输入。

因此下一篇自然衔接：

```text
Tokenizer
    ↓
Token ID
    ↓
Embedding
    ↓
为什么一个数字可以变成几千维向量？
    ↓
这些向量为什么能够表示语义？
```

这就是 **词嵌入（Embedding）** 要解决的问题。
