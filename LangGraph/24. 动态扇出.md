动态扇出（Dynamic Fan-out）指并行分支的**数量在运行时才确定**，而不是像第06章 超步的并行图那样在编译时把边写死。LangGraph 用 `Send` 对象承载这种不定数量的分支：条件边的路由函数不返回一个节点名，而是返回一个 `Send` 列表，列表长度由当次运行的状态决定，每个 `Send` 各自携带一份独立的输入，交给同一个节点并发执行——这正是 map-reduce 模式里"map"的那一半：先按需要切出若干份子任务，再统一汇合结果。

Agent底层逻辑第16章的子代理"封装：并行多个，合并结果"一节，用 `threading.Thread` + `join` 手工实现了同样的模式：按 `agent_config` 列表的长度动态起线程，全部结束后再合并 `results`。`Send` 把这件事收编进图引擎本身，不必手写线程与锁。

文档：[Map-Reduce and the Send API](https://docs.langchain.com/oss/python/langgraph/use-graph-api#map-reduce-and-the-send-api) · [Send 参考](https://reference.langchain.com/python/langgraph/types/Send)

| 概念 | 作用 |
| --- | --- |
| `Send(node, arg)` | 指定目标节点，以及传给该节点这一次调用的自定义输入；一次条件边可以返回多个 `Send` |
| 动态扇出 | 并行分支数在运行时由状态决定；对照第06章的并行图，那里的分支数在编译时已经写死 |
| 路由函数返回 `list[Send]` | 条件边的路由函数不再返回节点名，而是直接返回一组 `Send`，每个对应一次独立调用 |
| `path_map`（`add_conditional_edges` 第三参数） | 这里传 `["worker"]`，只用于图可视化推断可能到达的节点，不参与实际路由——路由目标已经写在每个 `Send` 里 |
| reducer（`operator.add`） | 汇合各并行调用写回的结果（第04章 Reducer） |

## 静态并行与动态扇出的区别

第06章的并行图用 `add_edge("A", "B1")`、`add_edge("A", "C1")` 这类静态边扇出：分支叫什么、有几条，编译时已经固定，运行时只是决定要不要走。动态扇出连分支的**个数**都不在编译时确定：路由函数在运行时读到状态里的某个数量（或列表长度），据此生成对应数量的 `Send`，一次运行可能扇出 3 路，下一次输入不同就扇出 10 路，图的拓扑本身没有变化，变化的是同一个节点被并发调用的次数。

## 完整实现

```python
import operator
from typing import Annotated, TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.types import Send

class State(TypedDict):
  """动态扇出图状态"""

  # 需要扇出的任务数量，运行时决定 Send 的个数
  number: int
  # 各 worker 写回的结果，用 operator.add reducer 追加累积（第04章 Reducer）
  result: Annotated[list[str], operator.add]

def fan_out(state: State) -> list[Send]:
  """条件边的路由函数：按 number 生成对应数量的 Send，扇出到 worker 节点"""
  return [Send("worker", f"task_{index}") for index in range(1, state["number"] + 1)]

  # 也可以显式写出每一个 Send，效果相同，只是数量固定在代码里，不再随 state 变化：
  # return [Send("worker", "任务1"), Send("worker", "任务2"), Send("worker", "任务3")]

def worker(task: str) -> dict[str, list[str]]:
  """单次并行调用：接收 fan_out 传入的 task 字符串，写回 result"""
  return {"result": [f"{task}:result"]}

def build_graph():
  """生成动态扇出图：START 按 number 扇出到若干 worker，全部完成后统一进入 END"""
  workflow = StateGraph(State)

  workflow.add_node("worker", worker)  # type: ignore

  workflow.add_conditional_edges(START, fan_out, ["worker"])
  workflow.add_edge("worker", END)

  return workflow
```

### 代码说明

`State` 定义两个字段：`number` 是扇出的数量，由调用方传入；`result` 是各次并行调用的汇合结果，标注了 `operator.add` reducer，多个 `worker` 并发写入时按追加而非覆盖合并（第04章 Reducer）。

`fan_out` 是挂在 `START` 之后的条件边路由函数。它不返回某个节点名，而是返回一个 `Send` 列表：`range(1, state["number"] + 1)` 按 `number` 生成对应个数的任务标识，每个标识各自包成一个 `Send("worker", f"task_{index}")`。这一步就是"数量在运行时才确定"的落地——`number` 传 3 就扇出 3 个 `Send`，传 10 就扇出 10 个，列表长度不写在代码里，而是读状态算出来的。

`worker` 是被扇出的目标节点，但它的函数签名是 `task: str`，不是 `state: State`。原因在于 `Send` 的第二个参数会替换掉这次调用原本该收到的图状态：`Send("worker", f"task_{index}")` 里的 `f"task_{index}"` 就是这一次 `worker` 唯一收到的输入，图的完整 `State` 字典对这次调用不可见。这与 `worker` 注册时按 `State -> Partial` 的签名要求不一致，所以 `add_node` 那一行需要 `# type: ignore` 抑制类型检查报错——这是 `Send` 用法本身带来的、预期之内的类型不匹配，不是代码缺陷。`worker` 返回 `{"result": [f"{task}:result"]}`，各次并发调用各自贡献一条结果，交由 `operator.add` 汇合进同一个 `result` 列表。

`build_graph` 里 `workflow.add_conditional_edges(START, fan_out, ["worker"])` 的第三个参数是 `path_map`。第06章分支图里这个参数是字典（如 `{"小白兔": "B", "大灰狼": "C"}`），把路由函数返回的标签映射到具体节点名，字典本身参与实际路由。这里传的是列表 `["worker"]`，因为 `fan_out` 已经在每个 `Send` 里显式指定了目标节点，路由不需要再查表决定去哪——`path_map` 在这种用法下只用于告诉图可视化"这条条件边可能到达 `worker`"，不参与运行时的实际决策。

### 运行示例

```python
graph = build_graph().compile()
graph.invoke({"number": 3, "result": []})
```

```text
{"number": 3, "result": ["task_1:result", "task_2:result", "task_3:result"]}
```

三个 `worker` 调用落在同一超步内并发执行（第06章 超步），`result` 里各条目的顺序不保证与 `number` 的生成顺序一致——三次调用谁先完成、reducer 按什么次序合并，都不是图定义能保证的，如果结果顺序有业务含义，需要在各条结果里自带排序字段。
