中断（interrupt）指图运行到某个点时主动暂停，把需要的信息交给外部（通常是人），等外部给出答复后再从暂停处继续。这不是异常处理意义上的"报错终止"，暂停期间图不占用任何计算资源，可以过几秒、几天甚至几个月再恢复，恢复后就像没停过一样继续往下走。

这个理念没有对应单一的学术论文，来源是两条工程传统的汇合：一是分布式系统里的"持久执行"（durable execution），像 Temporal 这类工作流引擎，用持久化的执行历史让流程可以在任意时刻暂停、跨进程 / 跨机器恢复；二是"human-in-the-loop"这条更偏 AI/ML 的研究与实践脉络，强调关键决策前必须留有人工介入的位置。LangGraph 的实现把两者接在一起：靠第07章的检查点机制获得可恢复性，再把暂停点做成开发者能在任意代码位置调用的一个函数——官方博客把它类比成协程（coroutine）/生成器（generator）："一段可以在某个时刻挂起、之后在另一台机器上从挂起点恢复的状态机"。

文档：[Human-in-the-loop](https://docs.langchain.com/oss/python/langgraph/interrupts) · [interrupt 参考](https://reference.langchain.com/python/langgraph/types/interrupt) · [Making it easier to build human-in-the-loop agents with interrupt](https://www.langchain.com/blog/making-it-easier-to-build-human-in-the-loop-agents-with-interrupt)

| 概念 | 作用 |
| --- | --- |
| `interrupt(value)` | 暂停当前节点，把 `value` 交给外部；首次调用抛出 `GraphInterrupt`，恢复后的返回值就是外部答复 |
| `GraphInterrupt` | `interrupt` 底层抛出的异常，继承自 `GraphBubbleUp`，框架自己会捕获，不需要也不应该自己捕获 |
| `Command(resume=...)` | 携带答复重新发起运行，从被中断的节点开头重新执行 |
| 恢复位置 | 恢复时重新执行**整个节点**，不是从 `interrupt` 那一行接着走 |
| 索引匹配 | 同一节点内多个 `interrupt`，按调用顺序依次对应一份恢复值列表，与 4 个中断 4 个答案严格按序号对齐 |

## 在任意位置中断

`interrupt` 可以写在任意节点函数内部的任意代码位置，且能加条件判断，是否触发由业务逻辑决定。这与"只能在某个节点执行前后暂停"的静态断点不同——静态断点只能卡在节点边界，`interrupt` 能卡在节点内部的具体某一行。

暂停靠检查点撑住（第07章）：中断发生时，最近一次成功的检查点就是暂停点之前的状态；框架把线程标记为 `interrupted`，把传给 `interrupt` 的值存进检查点，然后立刻返回，不留后台协程等待。

### 基础中断

两个节点各自埋一个中断，顺序执行：

```python
import operator
from typing import Annotated, TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.types import interrupt

class State(TypedDict):
  # 追踪信息，使用 operator.add reducer 追加累积，观察每次进入节点的变化
  traces: Annotated[list[str], operator.add]

async def A(state: State) -> dict:
  print("进入节点A")
  answer = interrupt("请问你要继续执行节点A吗？")
  print(f"answer A:{answer}")
  return {"traces": ["A"]}

async def B(state: State) -> dict:
  print("进入节点B")
  answer = interrupt("请问你要继续执行节点B吗？")
  print(f"answer B:{answer}")
  return {"traces": ["B"]}

def build_graph():
  workflow = StateGraph(State)

  workflow.add_node(A)
  workflow.add_node(B)

  workflow.add_edge(START, "A")
  workflow.add_edge("A", "B")
  workflow.add_edge("B", END)

  return workflow
```

第一次 `ainvoke` 跑到 `A` 里的 `interrupt` 就停下，`print("进入节点A")` 已经执行过；恢复后 `A` 从函数开头重新跑一遍（`print` 再打一次），这次 `interrupt` 直接拿到答复往下走，写入 `traces`，接着进入 `B` 触发第二次中断。两个节点的暂停点先后独立，互不影响。

### 多重中断与并行中断

同一节点可以有多个 `interrupt`；多个节点也可以并行进入同一超步（第06章），各自产生自己的中断：

```python
import asyncio
import operator
from typing import Annotated, TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.types import interrupt

class State(TypedDict):
  # 追踪信息，使用 operator.add reducer 追加累积，观察每次进入节点的变化
  traces: Annotated[list[str], operator.add]

async def A(state: State) -> dict:
  print("进入节点A")
  answer1 = interrupt("A 的第一个中断：请问你要继续吗？")
  print(f"answer A1:{answer1}")
  answer2 = interrupt("A 的第二个中断：请问你要继续吗？")
  print(f"answer A2:{answer2}")
  return {"traces": ["A"]}

async def B(state: State) -> dict:
  print("进入节点B")
  answer1 = interrupt("B 的第一个中断：请问你要继续吗？")
  print(f"answer B1:{answer1}")
  answer2 = interrupt("B 的第二个中断：请问你要继续吗？")
  print(f"answer B2:{answer2}")
  answer3 = interrupt("B 的第三个中断：请问你要继续吗？")
  print(f"answer B3:{answer3}")
  return {"traces": ["B"]}

def build_graph():
  workflow = StateGraph(State)

  workflow.add_node(A)
  workflow.add_node(B)

  # START 并发进入 A、B
  workflow.add_edge(START, "A")
  workflow.add_edge(START, "B")

  # A、B 各自连到结束
  workflow.add_edge("A", END)
  workflow.add_edge("B", END)

  return workflow
```

`A`、`B` 同属第一个超步，并发执行，各自遇到第一个 `interrupt` 就停：这一轮 `ainvoke` 返回时，`__interrupt__` 里同时有 `A` 的第一个中断和 `B` 的第一个中断。恢复时若只答复了其中一个任务的中断，只有那个任务的节点会重新执行到下一个 `interrupt`，另一个仍原样停在原处等待。

`B` 内部三个 `interrupt` 按调用顺序对应一份恢复值列表：节点重新执行时，第一个 `interrupt` 命中列表里第 0 项，第二个命中第 1 项……列表长度不够（比如只答复了第一个）时，恢复执行会重新走到第二个 `interrupt`，再次暂停等待。这意味着节点内**不要**写 `while True` 套 `interrupt`：每次恢复都会重新执行到当前进度，循环体越靠后的迭代，被重复执行的次数越多，是指数级重放而不是线性。

### 子图中断

中断可以发生在子图（第18章）内部，但父图必须能感知到这次暂停，子图的持久化模式必须是 `None`（默认）或 `True`——`False` 没有检查点，无法中断：

```python
import operator
from typing import Annotated, TypedDict

from langgraph.graph import END, START, StateGraph
from langgraph.types import interrupt

class State(TypedDict):
  # 追踪信息，使用 operator.add reducer 追加累积，观察每次进入节点的变化
  traces: Annotated[list[str], operator.add]

# 子图

async def sub_a(state: State) -> dict:
  print("进入子图节点 a")
  answer = interrupt("子图节点 a 的中断：请问你要继续吗？")
  print(f"子图 answer a:{answer}")
  return {"traces": ["子图a"]}

async def sub_b(state: State) -> dict:
  print("进入子图节点 b")
  return {"traces": ["子图b"]}

def build_subgraph():
  workflow = StateGraph(State)

  workflow.add_node("a", sub_a)
  workflow.add_node("b", sub_b)

  workflow.add_edge(START, "a")
  workflow.add_edge("a", "b")
  workflow.add_edge("b", END)

  # 子图 checkpoint 模式设置为 None（per-invocation：每次调用全新开始，
  # 但在单次调用内继承父图 checkpointer，从而支持 interrupt 中断/恢复）
  return workflow.compile(checkpointer=None)

subgraph = build_subgraph()

# 父图

async def A(state: State) -> dict:
  print("进入节点 A")
  # 在节点内部调用子图，checkpointer 会自动继承父图
  result = await subgraph.ainvoke({"traces": []})
  print(f"子图返回:{result}")
  return {"traces": ["A"] + result["traces"]}

async def B(state: State) -> dict:
  print("进入节点 B")
  return {"traces": ["B"]}

def build_graph():
  workflow = StateGraph(State)

  workflow.add_node("A", A)
  workflow.add_node("B", B)

  workflow.add_edge(START, "A")
  workflow.add_edge("A", "B")
  workflow.add_edge("B", END)

  return workflow
```

父节点 `A` 里节点内调用子图（第18章的"节点内调用"），子图 `compile(checkpointer=None)` 让它在单次父图调用内继承父图的检查点器，因此 `sub_a` 里的 `interrupt` 能一路冒泡到最外层，`ainvoke` 在父图这一层收到中断。恢复时父节点 `A` 从头重新执行——包括那一句 `print("进入节点 A")`——再重新 `await subgraph.ainvoke(...)`，子图内部凭检查点跳过已完成的 `sub_a`，直接从中断处继续。

## LangGraph API

### 准备工作

```python
from langgraph.checkpoint.memory import InMemorySaver
from langchain_core.runnables import RunnableConfig
from langgraph_project.graphs.demo import demo_interrupt_parallel_graph

checkpointer = InMemorySaver()
config: RunnableConfig = {
  "configurable": {
    "thread_id": "interrupt_demo"
  }
}
graph = demo_interrupt_parallel_graph.build_graph().compile(checkpointer)
```

### 运行到中断

```python
result = await graph.ainvoke(
  input={},  # type: ignore
  config=config,
)
result
```

遇到中断时 `ainvoke` **正常返回**，不抛异常；返回的状态里多一个 `__interrupt__` 键。`graph.get_state_history(config)`（第07章）能看到这次运行截止到中断为止写下的全部检查点。

### 查看中断的两种方式

运行结果和检查点上都能看到同一批中断：

```python
interrupts = result.get("__interrupt__", [])
interrupts
```

```python
cur_cp = graph.get_state(config=config)
cp_interrupts = cur_cp.interrupts
cp_interrupts
```

`result["__interrupt__"]` 只在触发中断的那次调用返回值里有；换一次单独的 `get_state` 查询同一线程，则要看 `interrupts` 字段——两者内容一致，只是取用的时机不同：前者是本次调用的直接产物，后者是随时按 `thread_id` 查最新检查点。每个中断对象带一个 `id`，恢复时要按 `id` 一一对上。

### 中断的恢复

按 `id` 构造答复字典，交给 `Command(resume=...)` 重新发起运行：

```python
interrupts = result.get("__interrupt__", [])
answers = {
  inter.id: True
  for inter in interrupts
}
answers
```

```python
from langgraph.types import Command

result = await graph.ainvoke(input=Command(resume=answers), config=config)
result
```

这一次 `ainvoke` 从各自暂停的节点开头重新执行，用 `answers` 里对应 `id` 的值作为各个 `interrupt()` 的返回值；跑到下一个 `interrupt` 再次停下，`__interrupt__` 里换成新一批中断，重复上面的查看与恢复即可。

## Agent Server API

进程内的 `graph.ainvoke` 换成 SDK 对某条线程的一次 Run（第14、15章），中断信息走服务端而不是本地内存。

### 创建线程

```python
from langgraph_sdk import get_client
from langgraph_sdk.schema import Command as SDKCommand

client = get_client(url="http://localhost:2024")

# 直接使用 langgraph.json 中注册的图名称作为 assistant_id
assistant_id = "interrupt_parallel_graph"

thread = await client.threads.create(metadata={"__name__": "中断"})
thread_id = thread["thread_id"]
thread_id
```

### 运行到中断

```python
result = await client.runs.wait(
  thread_id=thread_id,
  assistant_id=assistant_id,
  input={},
)
result
```

`runs.wait` 遇到中断同样是**正常返回**，`status` 会是 `interrupted`，返回体里带 `__interrupt__`。

### 查看中断的两种方式

```python
interrupts = result.get("__interrupt__", [])  # type: ignore
interrupts
```

```python
cur_cp = await client.threads.get_state(thread_id=thread_id)
cp_interrupts = cur_cp["interrupts"]
cp_interrupts
```

与进程内一致：一个来自本次 `runs.wait` 的返回值，一个来自对线程的独立状态查询（第14章「获取线程状态」）。

### 中断的恢复

```python
answers = {
  inter["id"]: True
  for inter in interrupts
}
answers
```

```python
# 同时恢复 A、B 的第一个中断，本次 run 会运行到 A、B 的第二个中断
result = await client.runs.wait(
  thread_id=thread_id,
  assistant_id=assistant_id,
  command=SDKCommand(resume=answers),
)
result
```

`SDKCommand` 是 `langgraph.types.Command` 在 SDK 侧的等价物，`resume` 字段同样按 `id` 匹配。若中断分布在并行的多个节点上（如 `A`、`B` 各自的第一个中断），一次 `resume` 可以带上两边的答复，各自恢复到自己的第二个中断，互不干扰。

## 最佳实践

1. 永远不要捕获 `interrupt` 抛出的异常，至少不要捕获它的基类 `GraphBubbleUp`；捕获后不重新抛出，等于让中断悄悄消失，图会继续往下跑而不是真正暂停。
2. 被中断的节点恢复时会整体重新执行一遍，中断之前的所有副作用（写库、调外部接口、发消息）都会重放一次，必须保证幂等——用幂等键、`upsert` 或先查后写。
3. 同一节点内若要连续触发多个中断，必须保证这些 `interrupt` 调用的**数量和顺序**在每次重新执行时都一样，否则索引匹配的恢复值会对错位置；避免 `while` 循环里反复调用 `interrupt`。
4. 子图内部要中断，子图的 `checkpointer` 必须是 `None` 或 `True`，`False` 没有检查点，中断无法在父图这一层被捕获到。
5. 时间旅行（第19章）从某个历史检查点 Replay 或 Fork 时，如果该检查点之后原本就有中断，重放同样会重新触发这次中断，不会因为是"回放"就跳过等待外部答复。
