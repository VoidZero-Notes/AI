本篇讲两件事——**图运行期间出错会怎样、出错后如何恢复**，以及**编译时能配置哪些策略降低出错概率**；与哪种部署模式无关，改动的都是图本身。一次运行可能因为节点抛异常、模型超时等原因中途终止，第15章 Run 的 `status` 里列过 `error` 这种情形；第07章的检查点保证终止前的状态不丢，是本篇讨论恢复的基础。

节点级的重试 / 超时 / 错误兜底是编译前的静态配置；出错后的手动恢复靠已有的接口拼起来：重新发起 Run（第15章 `runs.wait`）、或者 Replay / Fork（第19章）。最后一节把两类串成线上环境的完整链路。

文档：[Fault tolerance](https://docs.langchain.com/oss/python/langgraph/fault-tolerance) · [Fault tolerance 参数](https://docs.langchain.com/oss/python/langgraph/fault-tolerance#parameters) · [进度信号](https://docs.langchain.com/oss/python/langgraph/fault-tolerance#progress-signals)

| 概念            | 作用                                                                 |
| --------------- | -------------------------------------------------------------------- |
| `RetryPolicy`   | 节点抛异常时按策略自动重试，`max_attempts` 等控制次数                |
| `TimeoutPolicy` | 限制节点运行时间，`run_timeout` / `idle_timeout` 两个维度            |
| `error_handler` | 重试耗尽后的兜底函数，代替节点本身的执行结果                         |
| 检查点          | 出错前最后一次成功写入的状态（第07章）；错误不会污染已有检查点       |
| 手动恢复        | 对已终止的运行重新 `invoke`（追加输入）、Replay 或 Fork（第19章）    |

## 出错时发生了什么

图运行期间发生错误时：

- 立即停止图的运行
- 最新的检查点仍是错误发生**之前**那一枚，出错节点本身没有写入

因此重新运行不需要额外操作，直接对同一线程再发起一次即可：

```python
from langgraph_sdk import get_client

client = get_client(url="http://localhost:2024")
assistant_id = "agent"

thread = await client.threads.create(metadata={"__name__": "手动重试错误"})
thread_id = thread["thread_id"]
```

```python
try:
  result = await client.runs.wait(
    thread_id=thread_id,
    assistant_id=assistant_id,
    input={"messages": [{"role": "user", "content": "你好！"}]},
  )
except Exception as e:
  print(e)
```

```python
# 不传 input，直接重试
try:
  result = await client.runs.wait(
    thread_id=thread_id,
    assistant_id=assistant_id,
    input=None,
  )
except Exception as e:
  print(e)
```

第二次调用没有新增用户输入，图会从上一枚检查点对应的位置继续跑，效果与第19章的 Replay 相同：只是这里的起点是「出错前」，而不是手动挑选的历史检查点。

## 重试策略

```python
from langgraph.types import RetryPolicy

# 给所有节点添加默认重试策略：最大重试次数 3 次
workflow.set_node_defaults(
  retry_policy=RetryPolicy(max_attempts=3),
)

# 给某个节点单独添加，覆盖默认
workflow.add_node(
  "call_api",
  call_api,
  retry_policy=RetryPolicy(max_attempts=3),
)
```

以下错误类型会被 `LangGraph` 认为是程序 bug，不会触发重试：

`ValueError` · `TypeError` · `ArithmeticError` · `ImportError` · `LookupError` · `NameError` · `SyntaxError` · `RuntimeError` · `ReferenceError` · `StopIteration` · `StopAsyncIteration` · `OSError`

其余异常（如网络超时、第三方接口报错）才会按 `RetryPolicy` 重试。完整参数见 [Fault tolerance 参数](https://docs.langchain.com/oss/python/langgraph/fault-tolerance#parameters)。

## 超时策略

```python
from langgraph.types import TimeoutPolicy

# 给所有节点添加默认超时策略
workflow.set_node_defaults(
  timeout=TimeoutPolicy(run_timeout=60, idle_timeout=10),
)

# 给某个节点单独添加，覆盖默认
workflow.add_node(
  "call_api",
  call_api,
  timeout=TimeoutPolicy(run_timeout=60, idle_timeout=10),
)
```

> 超时策略仅能作用于异步节点：同步节点在事件循环里无法被中途打断。

两个维度含义不同：

- `run_timeout`：从节点开始算，最多等多久让节点整体跑完
- `idle_timeout`：从节点开始算，最多等多久要收到下一个进度信号；信号包括 LLM 新 token 到达、子图内部产生信号等，完整列表见 [进度信号](https://docs.langchain.com/oss/python/langgraph/fault-tolerance#progress-signals)

## 错误兜底

```python
def my_error_handler(state: State, error: NodeError):
  # 该函数会代替节点的执行结果
  ...

# 给所有节点添加默认错误处理函数
workflow.set_node_defaults(
  error_handler=my_error_handler,
)

# 给某个节点单独添加，覆盖默认
workflow.add_node(
  "call_api",
  call_api,
  error_handler=my_error_handler,
)
```

`error_handler` 在 `RetryPolicy` 重试耗尽后才触发：用它的返回值代替节点本该产生的状态更新，图继续往下走，而不是终止运行。

## 线上环境

节点级配置与手动恢复合在一起，是线上一次异常的完整链路：

```
超时 / 其他错误
  → 重试（RetryPolicy）
  → 错误函数兜底（error_handler）
  → 终止运行
  → 用户手动恢复：Replay（第19章）/ Fork（第19章）/ 追加消息续跑（第15章 runs.wait）
```

前三步是编译时配置好的自动流程，尽量把错误消化在图内部；真正查不出问题或需要人工判断时才终止运行，交给最后一步的人工介入。
