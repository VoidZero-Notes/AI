事件流是 Agent Server 把一次 Run 的执行过程经 SSE 推给客户端：不必等待整张图执行结束再读取最终状态，可以按超步拿到完整状态、按节点拿到增量、按 token 拿到模型输出。本篇用 `langgraph-sdk` 的 `client.runs.stream` 同时订阅多种 `stream_mode`，并按内容块类型把思考、正文与工具调用打印到终端。

第15章用 `create` / `wait` / `join` 管理 Run 的生命周期，并写明流式接口（`/runs/stream`、`join_stream`）留到本篇。Agent底层逻辑第05章把厂商 chunk 整理成自有事件再打印，第06章的 `invoke_stream` 是同一套思路在 Model 上的封装；LangGraph 第02章的 `astream` 只看 Chat Model 的 `AIMessageChunk` 形状。本篇订阅的是整张图在 Agent Server 上的执行事件，模型 token 只是其中一种模式。第18章的子图默认不出现在父图流里，须 `stream_subgraphs=True` 才会带上子图命名空间。

文档：[Streaming API](https://docs.langchain.com/langsmith/streaming) · [RunsClient.stream](https://reference.langchain.com/python/langgraph-sdk/_async/runs/RunsClient/stream) · 本地 OpenAPI：`http://localhost:2024/docs#tag/thread-runs`

| 概念 | 作用 |
| --- | --- |
| 事件流 | 一次 Run 执行过程中，服务端按 SSE 推送的事件序列 |
| `StreamPart` | SDK 在 `version="v1"` 下返回的命名元组：`event` 为事件名，`data` 为载荷 |
| `stream_mode` | 订阅哪些类别的事件；可传单个字符串，也可传列表同时订阅多种 |
| `values` | 每个超步结束后的完整图状态（第06章 超步） |
| `updates` | 每个节点（或同超步内的各个节点）写回的状态增量 |
| `checkpoints` | 每个超步结束后的检查点快照，格式与 `get_state()` 相近（第07章） |
| `messages-tuple` | 模型 token 与调用元数据的二元组 `(message_chunk, metadata)`，对应第02章 `astream` |
| `stream_subgraphs` | 是否把子图内部事件一并推送；默认 `False`（第18章 子图） |
| `version` | 流格式。`v1`（默认）返回 `StreamPart`；`v2` 返回带 `type` / `ns` / `data` 的字典 |

调用前须已按第05章启动本地服务，并按第13章安装 SDK。`assistant_id` 传图 ID（如 `"agent"`）使用默认 Assistant；传 UUID 使用第13章创建的那份具体配置，两种标识不可互换。

## 创建客户端与线程

有状态运行必须先有一条线程。`metadata.__name__` 会被 Studio 读作会话标题：

```python
from langgraph_sdk import get_client

client = get_client(url="http://localhost:2024")

assistant_id = "5f2d9990-abec-497c-a853-90d9909eeb82"

thread = await client.threads.create(  # type: ignore
  metadata={"__name__": "事件流"}
)
thread_id = thread["thread_id"]
thread_id
```

## 流模式

`stream_mode` 决定客户端能看到哪一类事件。本篇示例一次订阅四种：

| 模式 | 推送时机 | `data` 形状 |
| --- | --- | --- |
| `values` | 每个超步结束 | 完整图状态 |
| `updates` | 每个节点写回之后 | `{节点名: 该节点的部分状态}`；同一超步内多个节点会分别推送 |
| `checkpoints` | 每个超步结束（需检查点，Agent Server 默认具备） | 与 `get_state()` 相近的快照 |
| `messages-tuple` | 模型每产出一小段 token | `(message_chunk, metadata)` |

`messages-tuple` 对应图库里的 `stream_mode="messages"`：即使节点内部用 `invoke` 而非 `stream` 调模型，服务端仍会把 token 推出来。`metadata` 里常用的是 `langgraph_node`，用来过滤「哪一个节点」的输出。

官方还提供 `debug` / `custom` / `events`，本篇示例未用。

## 解析消息事件

`version="v1"` 时，每条事件是 `StreamPart(event, data)`。根图的 `event` 就是模式名（`values`、`updates`、`messages`、`checkpoints`）；开启 `stream_subgraphs=True` 后，子图事件的 `event` 写成 `{模式}|{命名空间}`。用 `str.partition("|")` 拆开即可区分来源。

流开始时还会推一条 `metadata`（含 `run_id`），结束时推一条 `end`（`data` 为 `None`）。这两条不属于上面四种 `stream_mode`，但会出现在迭代器里。

`messages` 事件的 `data` 是二元组：

| 位置 | 含义 |
| --- | --- |
| `data[0]` | `message_chunk`：这一小段增量，字段与第02章 `AIMessageChunk` 对齐 |
| `data[1]` | `metadata`：调用发生在哪个节点、哪次 LLM 调用 |

本例只打印 `langgraph_node == "model"` 的内容块，并按块类型切换标题。`thinking` / `text` / `tool_use` 与 Anthropic 风格的 `content_blocks` 对应；未列入映射的类型直接跳过。`tool_use` 只打印工具名，不把参数增量输出到终端。某个子图命名空间首次出现时，先打印一行「子代理：」，再打印标题——对应第18章嵌进父图的子图，以及 Agent底层逻辑第16章的子代理边界。

`print(..., flush=True)` 与 Agent底层逻辑第05章的 `sys.stdout.flush()` 同一目的：流式输出没有换行时，必须立刻刷出缓冲区，否则终端会整段结束才出现。

```python
from typing import AsyncIterator

from langgraph_sdk.schema import StreamPart

msg_types: dict[str, str] = {}
announced_subgraphs: set[str] = set()
msg_type_map = {
  "thinking": "思考：",
  "text": "回复：",
  "tool_use": "调用工具：",
}

def print_message(chunk: StreamPart):
  event_type, _, namespace = chunk.event.partition("|")
  if event_type != "messages":
    return
  if chunk.data[1]["langgraph_node"] != "model":
    return
  source = namespace or "root"
  content_blocks = chunk.data[0]["content"]
  for block in content_blocks:
    type = block["type"]
    if type != msg_types.get(source):
      msg_types[source] = type
      if type not in msg_type_map:
        continue
      title = msg_type_map[type]
      if type == "tool_use":
        title += block["name"]
      if namespace and namespace not in announced_subgraphs:
        announced_subgraphs.add(namespace)
        print(f"\n子代理：\n{title}", flush=True)
      else:
        print(flush=True)
        print(title, flush=True)
    if type not in msg_type_map:
      continue
    if type == "tool_use":
      continue
    print(block[type], end="", flush=True)

chunks = []

async def print_stream(stream: AsyncIterator[StreamPart]):
  global chunks
  chunks = []
  msg_types.clear()
  announced_subgraphs.clear()
  result = {}
  async for chunk in stream:
    chunks.append(chunk)
    print_message(chunk)
    if chunk.event == "values":
      result = chunk.data
  return result
```

`msg_types` 按来源（根图 `root` 或子图命名空间）记住当前块类型，类型切换时才换标题，同一段思考或正文不会反复打印「思考：」「回复：」。`chunks` 保存本次迭代到的全部 `StreamPart`，迭代结束后可对照 `event` 与 `data` 的原始形状。`print_stream` 把最后一次 `values` 当作返回值——等价于第15章 `wait` / `join` 拿到的最终图状态，只是中间过程已经按 token 打印过了。

## 创建运行并订阅事件

> POST /threads/{thread_id}/runs/stream

`stream` 会创建 Run 并立刻返回异步迭代器，边执行边推事件。这与第15章 `wait`（创建并阻塞到结束）相对：二者都创建 Run，差别是本接口按事件推送，而不是只返回最终状态。

```python
stream = client.runs.stream(
  thread_id=thread_id,
  assistant_id=assistant_id,
  input={
    "messages": [
      {"role": "user", "content": "写一首夏天的诗"}
    ]
  },
  stream_mode=[
    "values",
    "checkpoints",
    "updates",
    "messages-tuple",
  ],
  stream_subgraphs=True,
  version="v1",
)

output = await print_stream(stream)  # type: ignore
output
```

`version="v1"` 必须与上面的解析方式一致：解析依赖 `chunk.event` 字符串和 `chunk.data` 下标。`v2` 改成字典的 `type` / `ns` / `data`，本篇的 `partition("|")` 不再适用。

`print_stream` 返回的 `output` 是最后一份完整状态。`chunks` 里则是全部事件，便于核对 `messages`、`values`、`updates`、`checkpoints` 以及 `metadata` / `end` 各自的形状。

> **说明：** 已有后台 Run（第15章 `create`）要用 `client.runs.join_stream` 接入同一条事件流；该接口不缓冲加入之前已经推过的事件。本篇示例只用创建并立刻订阅的 `stream`。
