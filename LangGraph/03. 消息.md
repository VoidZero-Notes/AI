LangChain 的 Message 是对话上下文的基本单元：一条消息带角色、载荷和可选元数据。Chat Completions 无状态，服务端不为「上一轮」留记忆；多轮能够延续，是因为调用方维护消息列表并在下一次请求里原样带上。这一点与 Agent底层逻辑第07章相同：那边用 `dict` / `Session`；本篇用 LangChain 的 `BaseMessage` 子类。

第02章已经对照过四种类型，并停在 `AIMessage.tool_calls`。本篇把工具结果写成 `ToolMessage` 补完一轮，再展开内容块（纯文本 / 图片 / 音频）与系统提示词模板。`SystemMessage` 对应 Agent底层逻辑第06章自行封装的消息类；`ToolMessage` 对应第08章「调用方执行工具后把结果写回 messages」。模板对应第06章的 Jinja2：那里是 `system.j2` + `render_prompt`；这里是 Mustache 的 `.mst` + `prompt_from_filename`。

文档：[Messages](https://docs.langchain.com/oss/python/langchain/messages)

| 概念             | 作用                                                                             |
| ---------------- | -------------------------------------------------------------------------------- |
| Message          | 上下文中的一条。角色 + 载荷 + 可选元数据                                         |
| `BaseMessage`    | 四种消息的共同基类，因此能放进同一个 `list`                                      |
| `content`        | 发给模型的载荷：字符串，或块列表（厂商原生 / 标准块）                            |
| `content_blocks` | 跨厂商对齐后的内容块（`text` / `image` / `audio` / `reasoning` 等）              |
| `ToolMessage`    | 某次工具执行的结果；`tool_call_id` 必须对上对应 `AIMessage.tool_calls` 项的 `id` |
| Mustache 模板    | 静态提示词骨架 + 运行时注入。对应第06章 Jinja2，本篇用 `.mst`                    |

LangChain 也接受 OpenAI 形状的 `{"role", "content"}` 字典；本篇用对象，角色由类型决定，不必手写 `role`。

## 四种消息类型

四种类型与 Chat Completions 的 `role` 对齐：

| 类型            | `role`      | 含义                                                                                |
| --------------- | ----------- | ----------------------------------------------------------------------------------- |
| `SystemMessage` | `system`    | 全局约束与角色。原则见 Agent底层逻辑第06章：精简、自洽、全局约束、保持静态、结构化  |
| `HumanMessage`  | `user`      | 用户输入；载荷可以是纯文本，也可以是多个内容块（图、音频等）                        |
| `AIMessage`     | `assistant` | 模型上一轮输出。多轮回写时追加整个对象（含思维链与 `tool_calls`），不要改写成纯正文 |
| `ToolMessage`   | `tool`      | 某次工具执行的结果，用 `tool_call_id` 对上对应的 `tool_calls` 项                    |

顺序有约定：`SystemMessage` 放最前且尽量固定（与第06章「保持静态」、第07章 prompt cache 前缀一致）；其后按时间追加 human / ai / tool。第07章两条法则在这里同样成立：已入列的历史不可改写、删除或重排；回写 `AIMessage` 时思维链与正文一并保留。

第02章每次手写 `init_chat_model`。这里封装为 `create_model`，默认 Anthropic，换模型或厂商只改参数：

`src/langgraph_project/core/create_model.py`：

```python
from typing import Literal, Union

from langchain.chat_models import init_chat_model

from .config import anthropic_settings

Provider = Union[Literal["anthropic"], Literal["openai_reasoning"]]


def create_model(
  *,
  model_name: str = anthropic_settings.default_model,
  provider: Provider = "anthropic",
  **kwargs,
):
  return init_chat_model(model=model_name, model_provider=provider, **kwargs)
```

下面的 `AIMessage` / `ToolMessage` 是手工写入的历史，用来演示四种类型如何排进同一列表，不是本轮 `bind_tools` 的返回值。第02章已经演示过模型如何发出 `tool_calls`；本例假定上一轮已经决定调用 `get_weather`，工具也已执行完毕，现在把结果送回模型，换最终答复。

```python
from langchain.messages import AIMessage, HumanMessage, SystemMessage, ToolMessage
from langgraph_project.core.config import anthropic_settings
from langgraph_project.core.create_model import create_model

model = create_model(
  api_key=anthropic_settings.api_key,
  base_url=anthropic_settings.base_url,
)

messages = [
  SystemMessage("你是一个智能天气助手。"),
  HumanMessage("你好！请问今天成都的天气怎么样？我下午想去公园散步。"),
  AIMessage(
    content="",
    content_blocks=[{
      "type": "reasoning",
      "reasoning": "我需要调用get_weather工具获取准确的天气数据。",
    }],
    tool_calls=[{
      "id": "call_123456",
      "name": "get_weather",
      "args": {"city": "成都"},
    }],
  ),
  ToolMessage(
    content="成都今天是晴天，气温 25°C",
    tool_call_id="call_123456",
  ),
]

response = model.invoke(messages)

print(response)
```

> **说明：** `ToolMessage.tool_call_id` 必须与对应 `tool_calls` 项的 `id` 一致，模型才能把这条结果关联到那一次调用。对不上时，厂商接口通常报错，或把该结果当成无法归属的噪声。

`print(response)` 会把整份 `AIMessage` 打成一行，`thinking` 与 `response_metadata` 很长。结构如下，冗长字段用省略号代替：

```text
content=[
  {
    "type": "thinking",
    "thinking": "用户询问成都今天的天气，并且计划下午去公园散步。\n我获取到的天气信息是：成都今天是晴天，气温25°C。\n分析：晴天，气温25°C，非常适合去公园散步。\n回复内容：……",
    "signature": ""
  },
  {
    "type": "text",
    "text": "你好！今天成都的天气是晴天，气温在25°C左右，气候非常舒适。\n\n这样的天气非常适合下午去公园散步！……祝你在公园度过一个愉快的下午！"
  }
]
tool_calls=[]
invalid_tool_calls=[]
usage_metadata: {
  "input_tokens": 86,
  "output_tokens": 149,
  "total_tokens": 235,
  "input_token_details": {"cache_read": 0, "cache_creation": 0}
}
```

单独拿出需要看的三处：

- `content` 里的 `thinking` / `text`：模型先根据 `ToolMessage` 里的天气做内部推理，再给出可见回复。对应 `.content_blocks` 的 `reasoning` 与 `text`
- `.tool_calls`：`[]`。工具结果已经在列表里，本轮停在最终答复，不再发出调用
- `usage_metadata`：入 86 / 出 149。历史里四条消息都计入输入；输出主要在 `thinking` 与正文

第08章的闭环在这里落地：模型只返回调用意图 → 调用方执行 → `ToolMessage` 写回 → 再 `invoke` 一次得到答复。本例跳过「真正执行函数」这一步，直接写入了工具结果字符串。

## 基类

四种消息都继承 `BaseMessage`，所以同一个 `list` 里可以混放，`invoke` 按列表顺序发给模型：

```python
from langchain.messages import AIMessage, HumanMessage, SystemMessage, ToolMessage
from langchain_core.messages import BaseMessage

print(
  issubclass(SystemMessage, BaseMessage),  # True
  issubclass(HumanMessage, BaseMessage),  # True
  issubclass(AIMessage, BaseMessage),  # True
  issubclass(ToolMessage, BaseMessage),  # True
)
```

这与 Agent底层逻辑第06章的 `Message` 基类同一思路：那边用 dataclass 把 `role` 写死在子类上；这里由 LangChain 提供基类与四个子类，并额外容纳 `tool_calls`、`content_blocks`、`usage_metadata` 等字段。第06章的三个子类装不下工具结果，第07章才改用 `dict`；LangChain 用 `ToolMessage` 把这一缺口补在类型系统里。

## 消息内容

`content` 是发给模型的载荷，三种写法：

1. 字符串：纯文本
2. 块列表，厂商原生形状（例如 OpenAI 的 `image_url`）
3. 块列表，LangChain 标准内容块（`type` 为 `text` / `image` / `audio` 等）

一条 `HumanMessage` 可以包含多个内容块：一段说明加两张图，仍是**同一轮**用户输入，不必拆成多条消息。初始化时传入块列表，会写入 `content`；读结果时优先看 `.content_blocks`，与第02章读 `AIMessage` 的原则相同。

### 纯文本

最常见的形状是字符串。`model.invoke("你好")` 等价于一条只有正文的 `HumanMessage`（第02章第一次调用已经用过）。需要多角色或多轮时，改用对象列表。

```python
# 字符串入参：内部当成一条 HumanMessage
model.invoke("你好")

# 显式对象，效果相同
model.invoke([HumanMessage("你好")])

# 块列表：一条消息里多段文本，仍是一轮 user
HumanMessage([
  {"type": "text", "text": "第一段说明"},
  {"type": "text", "text": "第二段说明"},
])
```

> **说明：** 多个 `HumanMessage` 表示多轮用户发言；同一条消息里的多个 `text` 块表示同一轮里的多段文字。不要把「同一轮里的两段说明」拆成两条 `HumanMessage`，否则模型会看成两次独立提问。

`SystemMessage` / `AIMessage` / `ToolMessage` 同样可以只传字符串。`ToolMessage` 的字符串就是工具返回给模型看的那段结果。

### 图片

需要模型支持视觉输入，否则会报错。图片按 URL 或 base64 放入内容块；可以与文本块并列，让模型按文字指令理解图像。

```python
url1 = "https://fastly.picsum.photos/id/57/800/600.jpg?hmac=Geuc5OABDrI_1EI9yvAjSWKQpjo0S6g9Y5mB9JxI4r8"
url2 = "https://fastly.picsum.photos/id/58/800/600.jpg?hmac=yQHfIMWMXYg4f264WBOGMBWTYbv6NqTJMVz7r67kN3w"

messages = [
  HumanMessage([
    {"type": "text", "text": "比较这两张图片风格的差异"},
    {"type": "image", "url": url1},
    {"type": "image", "url": url2},
    # {"type": "image", "base64": "...", "mime_type": "image/png"},
  ])
]

model.invoke(messages)
```

三种常见来源：

| 来源          | 块字段                     | 适用                    |
| ------------- | -------------------------- | ----------------------- |
| URL           | `"url": "https://..."`     | 模型服务能访问该地址    |
| base64        | `"base64"` + `"mime_type"` | 本地文件，或 URL 不可达 |
| 服务商文件 ID | `"file_id"`                | 已上传到该厂商的文件    |

本例一条消息里两个 `image` 块加一段 `text`：模型同时看见两张图和比较指令。注释里的 base64 写法把本地字节编进请求，不再依赖外链。

### 音频

需要模型支持 ASR（语音识别），否则会报错。本节示例使用支持 ASR 的模型。

> **说明：** 百炼平台当前没有免费的 ASR 模型，本例运行会产生费用。

```python
import base64

with open("./assets/audio/test.mp3", "rb") as f:
  audio_base64 = base64.b64encode(f.read()).decode()

data_url = f"data:audio/mpeg;base64,{audio_base64}"

asr_model = create_model(
  model_name="qwen3.5-omni-plus",
  provider="openai_reasoning",
)

messages = [
  HumanMessage([
    {"type": "text", "text": "请告诉我这段音频的内容"},
    {"type": "audio", "base64": data_url, "mime_type": "audio/mpeg"},
  ])
]

asr_model.invoke(messages)
```

默认的 Anthropic 对话模型通常不接受音频块，因此这里换 `qwen3.5-omni-plus` 与 `openai_reasoning`。文本块给出任务，音频块给出待识别的载荷，形状与图片消息相同：一条 `HumanMessage`、多个块。

> **说明：** 本例把 data URL 整段放入 `base64` 字段，是当前所用网关的接法。LangChain 标准内容块一般只放裸 base64，另用 `mime_type` 标明格式。

### 其他格式

文件、视频等块与图片 / 音频同一套写法，但必须同时满足：模型本身支持该模态、服务商接口接受该块类型、LangChain 适配器能把它转成请求。缺少任一环都会报错，或该块不会进入请求。完整块类型见官方 [Content block reference](https://docs.langchain.com/oss/python/langchain/messages#content-block-reference)。

## 消息模板

真实 Agent 的系统提示词很长，且含少量运行时信息（工作目录、操作系统、是否 git）。骨架写成模板保持不动，变的值在渲染时注入——模板文件静态，注入值动态，对应第06章「保持静态」。

第06章用 Jinja2（`system.j2`，支持 `{% if %}` 等逻辑）。本篇用 Mustache：只做 `{{ name }}` 替换，模板本身不含分支。LangChain 在 `langchain_core.utils.mustache` 里提供 `render`：

```python
from langchain_core.utils.mustache import render

result = render(
  template="Hello {{name}}, you have {{count}} messages",
  data={"name": "世界", "count": 3},
)

print(result)  # Hello 世界, you have 3 messages
```

`src/langgraph_project/template/system.mst`：

```text
你是一个编程助手，你可以：

- 用简洁、准确的语言回答用户问题
- 调用工具完成任务

# 环境

理解所处的环境，有助于你完成工作:
 - 工作目录（cwd）: `{{ cwd }}`
 - 操作系统: `{{ os }}`
 - 当前工作目录是否处于git仓库管理: `{{ is_git }}`
```

占位符与第06章、第10章同一组运行时快照：`cwd` / `os` / `is_git` 在会话开始时采集，不是每轮都变的用户身份或当前时间。换机器会变，同一次进程里通常不变。

封装：按文件名加载 `.mst`，把 `data` 交给 `render`。调用方只传文件名与注入值，不再手写路径：

`src/langgraph_project/template/__init__.py`：

```python
from pathlib import Path

from langchain_core.utils.mustache import render

_TEMPLATE_DIR = Path(__file__).parent


def prompt_from_filename(*, filename: str, data: dict) -> str:
  template = (_TEMPLATE_DIR / f"{filename}.mst").read_text(encoding="utf-8")
  return render(template=template, data=data)
```

```python
from langgraph_project.template import prompt_from_filename

prompt = prompt_from_filename(
  filename="system",
  data={"cwd": "/yuhuang", "os": "mac", "is_git": True},
)
```

静态段落与模板一字不差；被填充的环境段如下（值随传入的 `data` 变化）：

```text
# 环境

理解所处的环境，有助于你完成工作:
 - 工作目录（cwd）: `/yuhuang`
 - 操作系统: `mac`
 - 当前工作目录是否处于git仓库管理: `True`
```

渲染结果当作 `SystemMessage` 的正文即可，后面组列表、`invoke` 的方式与前面相同：

```python
messages = [
  SystemMessage(prompt),
  HumanMessage("目前在哪个目录？"),
]
```

> **说明：** 每次调用 `prompt_from_filename` 都按传入的 `data` 重新填充。模板文件本身不变，变的是注入值。`filename="system"` 对应 `system.mst`，不要带扩展名。
