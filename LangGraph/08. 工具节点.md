第02章用 `bind_tools` 把 schema 交给模型，停在 `AIMessage.tool_calls`：模型只返回调用意图，函数体尚未运行。第03章用手工写入的 `ToolMessage` 演示回写，跳过了真正执行。本篇把执行实现为图节点：`ToolNode` 按 `name` 找到工具、传入参数、把结果写成 `ToolMessage` 追加进 `messages`；条件边根据「最后一条是否带 `tool_calls`」决定继续调工具还是结束。

这张图是 Agent底层逻辑第10章的 ReAct 在 LangGraph 里的落地：那边是 `while True`，直到本轮没有 `tool_calls`；这里是 `model → tools → model`，停的条件相同。`@tool` 与 schema 对应 Agent底层逻辑第09章的工具注册与执行；`ToolNode` 对应那边的 `registry.invoke`。接入的 `web_search` / `fetch_url` 对应 Agent底层逻辑第12章的 Agent 搜索引擎：那边直接调 Tavily SDK；这里把同一对能力包装成 LangChain 工具，交给图去调。

文档：[Prebuilt tools](https://docs.langchain.com/oss/python/langgraph/prebuilt)

| 概念               | 作用                                                                                         |
| ------------------ | -------------------------------------------------------------------------------------------- |
| `@tool`            | 从函数签名与 docstring 生成 schema；得到的对象本身是 `Runnable`，可直接 `invoke` / `ainvoke` |
| `tool_call_schema` | 发给模型的 JSON Schema：名称、描述、参数类型与必填项                                         |
| `bind_tools`       | 第02章：把 schema 绑到后续请求上；返回新的 Runnable，不改原模型对象                          |
| `ToolNode`         | 预构建节点：读最后一条 `AIMessage` 的 `tool_calls`，执行对应函数，返回 `ToolMessage` 列表    |
| `should_continue`  | 条件路由：最后一条带 `tool_calls` 则走向 `tools`，否则 `END`                                 |
| `args_schema`      | 用 Pydantic 模型覆盖自动推断的入参 schema，把 `Field(description=...)` 写进参数说明          |

Agent底层逻辑第08章的 Tool Calling：模型不会执行函数，只根据 schema 决定「调哪个、参数是什么」。第09章的工具注册与执行把「拆调用 → 执行 → 写成 `role: tool`」封装进 `registry.invoke`。本篇不再手写注册表：`ToolNode(tools)` 就是那一步在图上的节点。第04章的 `add_messages` 负责把节点返回的 `{"messages": [...]}` 追加进状态，因此 `ToolMessage` 会进入下一轮 `call_model` 的上下文。

## 定义工具

`@tool` 包装普通函数。模型看不到函数体，只能看到装饰器生成的 schema。得到的对象是 `Runnable`，不必经过图也能单独 `invoke`，便于先验证入参与返回形状。

```python
from langchain.tools import tool

# tool 装饰器会将函数转换为 Runnable
@tool
def get_weather(city: str):
  """
  获取某个城市的天气，返回的温度为摄氏度

  参数：
  - city: 城市名称
  """
  return {
    "city_name": "beijing",
    "temperature": 25,
    "weather": "cloudy",
  }

print(get_weather.tool_call_schema.model_json_schema())
```

`tool_call_schema.model_json_schema()` 就是发给模型的那份 schema。`description` 来自 docstring（含「参数：」那几行）；`properties.city` 来自类型注解 `city: str`。结构如下：

```json
{
  "description": "获取某个城市的天气，返回的温度为摄氏度\n\n参数：\n- city: 城市名称",
  "properties": {
    "city": {"title": "City", "type": "string"}
  },
  "required": ["city"],
  "title": "get_weather",
  "type": "object"
}
```

发给模型的 schema 里：

- `title`：工具名 `get_weather`，模型在 `tool_calls[].name` 里会原样带回
- `description`：模型靠它决定调不调；写空或与真实行为不符，调用质量会下降（Agent底层逻辑第08章的 Tool Calling）
- `required: ["city"]`：无默认值的参数会进必填列表

直接执行，不经过模型：

```python
print(get_weather.invoke({"city": "北京"}))
# {'city_name': 'beijing', 'temperature': 25, 'weather': 'cloudy'}
```

> **说明：** 函数体写死了返回值，未使用 `city`。此处只演示 schema 与 `invoke`，不是真实天气接口。入参必须是字典，键与 schema 的 `properties` 一致。

第02章问天气时，模型只发出 `tool_calls`，`It's sunny in {location}.` 不会出现。这里 `invoke` 的才是函数体真正运行。图上由 `ToolNode` 做同一件事：读意图、调这个 `Runnable`、把返回值写成 `ToolMessage`。

## 时间与检索工具

工具按文件拆分，再在包入口汇总成一份列表。增删工具时只改这一处，图节点与 `bind_tools` 共用同一份，避免 schema 列表与可执行对象各维护一份（Agent底层逻辑第09章的工具注册与执行要解决的就是这种漂移）。

`langgraph_project/tools/time.py`：当前时刻。docstring 写明「最新、最近」应优先调用，否则模型可能用参数里的过期知识直接回答。

```python
from datetime import datetime, timezone
from langchain.tools import tool

@tool
def get_current_time():
  """
  获取当前的日期和时间，返回当前时刻（北京时区）
  所有涉及到最新、最近等和时间相关的信息获取都应该优先调用此工具
  """
  now = datetime.now(timezone.utc).astimezone()

  return now.isoformat()
```

`datetime.now(timezone.utc).astimezone()` 先取 UTC，再转到进程所在本地时区。docstring 按北京时区约定；运行环境时区不是东八区时，返回值会随环境变化。

`langgraph_project/tools/web.py`：搜索与按 URL 提取。Tavily 的 `search` / `extract` 是同步接口，经 `asyncio.to_thread` 调用，避免在异步节点里阻塞事件循环。

```python
import asyncio
from langchain.tools import tool
from tavily import TavilyClient
from langgraph_project.core.config import tavily_settings

@tool
async def web_search(query: str):
  """根据关键字进行网络搜索，返回结构化的搜索结果"""
  client = TavilyClient(api_key=tavily_settings.api_key)
  response = await asyncio.to_thread(client.search, query=query)
  return response

@tool
async def fetch_url(urls: list[str]):
  """根据提供的url数组，抓取网页内容，返回结构化的搜索结果"""
  client = TavilyClient(api_key=tavily_settings.api_key)
  response = await asyncio.to_thread(client.extract, urls=urls, include_images=False)
  return response
```

两者的 Observation 形状不同，对应 Agent底层逻辑第12章的 Agent 搜索引擎里的分工：

| 工具          | Tavily 方法 | 入参            | 返回要点                                      |
| ------------- | ----------- | --------------- | --------------------------------------------- |
| `web_search`  | `search`    | 关键字          | 多条命中：`title` / `url` / `content`（摘要）/ `score`，不是整页 HTML |
| `fetch_url`   | `extract`   | URL 数组        | 指定页的 `raw_content`；失败项进 `failed_results` |

`langgraph_project/tools/__init__.py`：

```python
from .time import get_current_time
from .web import fetch_url, web_search

tools = [fetch_url, web_search, get_current_time]
```

这份 `tools` 会同时交给 `model.bind_tools(tools)` 与 `ToolNode(tools)`：前者让模型看见 schema，后者让图能按名字执行。只连接其中一侧，循环无法闭合：只 `bind_tools` 则模型发出意图但无人执行；只添加 `ToolNode` 则模型不知道有这些工具，不会发出 `tool_calls`。

## 接入图

第01章：节点做事，边决定下一步。ReAct 在图上就是两个节点加一条条件边：`model` 负责 Thought 与发出 Action；`tools` 负责真正执行并给出 Observation；没有 `tool_calls` 则结束。

```text
START → model ──有 tool_calls──→ tools ──→ model → …
              └──无 tool_calls──→ END
```

`langgraph_project/graphs/core_agent_graph.py`：

```python
from langgraph.graph import END, START, StateGraph
from langgraph_project.nodes.call_model import call_model
from langgraph_project.states.core_agent_state import CoreAgentState
from langgraph.prebuilt import ToolNode
from langgraph_project.tools import tools

def should_continue(state: CoreAgentState) -> str:
  """判断是否需要调用工具：最后一个消息带 tool_calls 则路由到 tools，否则结束"""
  last_message = state["messages"][-1]

  return "tools" if last_message.tool_calls else END  # type: ignore

def build_graph():
  """生成核心 Agent 图（未编译）"""
  workflow = StateGraph(CoreAgentState)
  workflow.add_node("model", call_model)
  workflow.add_node("tools", ToolNode(tools))

  workflow.add_edge(START, "model")
  workflow.add_conditional_edges(
    "model", should_continue, {"tools": "tools", END: END}
  )
  workflow.add_edge("tools", "model")

  return workflow
```

`should_continue` 只看**最后一条**消息。`call_model` 刚写入的是带 `tool_calls` 的 `AIMessage` 时，走向 `tools`；`ToolNode` 写入的是 `ToolMessage`（无 `tool_calls`），边固定回到 `model`，由模型决定是再调工具还是给最终答复。停的条件与 Agent底层逻辑第10章的 ReAct 相同：模型不再发出 Action，不是外面规定转几圈。

`ToolNode(tools)` 内部按 `tool_calls[].name` 查找并调用，一条 `AIMessage` 里若有多项调用会逐项执行，结果全部写成 `ToolMessage`（`tool_call_id` 对上对应项的 `id`，见第03章）。Agent底层逻辑第08章的 Tool Calling 当时只执行了 `tool_calls[0]`；第09章的 `registry.invoke` 才走完整列表。此处预构建节点已经覆盖这一步，不必再手写查找与回写。

`add_conditional_edges` 的第三个参数是路径映射：路由函数返回的字符串必须能在这张表里找到。返回 `"tools"` 进入工具节点，返回 `END` 结束。

## 模型节点绑定工具

`langgraph_project/nodes/call_model.py` 在原有取消息、拼系统提示词、创建模型之后，增加 `bind_tools`。不绑，`should_continue` 看到的 `tool_calls` 恒为假，图永远走 `END`。

```python
from langgraph_project.tools import tools

...

async def call_model(state: CoreAgentState) -> dict:
  """调用模型节点"""
  messages = state["messages"]  # 取出messages，不包含系统提示词
  model_config = state.get("model_config", ModelConfig())
  template_name = state.get("system_prompt_template", "system")
  system_message = _build_system_message(template_name)
  model = create_model(**model_config.to_kwargs())
  model_with_tools = model.bind_tools(tools)
  response = await model_with_tools.ainvoke([system_message, *messages])

  return {"messages": [response]}
```

`bind_tools` 返回**新的** Runnable，原 `model` 不变（第02章）。`ainvoke` 的入参仍是消息列表：系统提示词在前，其后是状态里的历史。工具 schema 走请求体的 `tools` 字段，不进 `messages`，与 Agent底层逻辑第08章的 Tool Calling「`tools` 是当次请求参数，不进历史消息」一致。

返回 `{"messages": [response]}` 由第04章的 `add_messages` 追加。下一超步里，`should_continue` 读到的最后一条就是这份 `AIMessage`。

## 用 Pydantic 约束入参

仅靠类型注解时，参数说明往往集中在工具级 `description` 里，`properties.city` 只有 `type`，没有字段级说明。`args_schema` 用 Pydantic 模型覆盖自动推断，`Field(description=...)` 会写进该参数自己的 schema。这是 Agent底层逻辑第09章的工具注册与执行用 Pydantic 生成入参模型的同一做法。

```python
from langchain.tools import tool
from pydantic import BaseModel, Field

class WeatherInput(BaseModel):
  """查询天气的输入参数"""
  city: str = Field(description="城市名称")

@tool(args_schema=WeatherInput)
def get_weather(city: str):
  """获取某个城市的天气，返回的温度为摄氏度"""

  return {
    "city_name": "beijing",
    "temperature": 25,
    "weather": "cloudy",
  }
```

相对文首那个 `get_weather`：工具级 `description` 只保留 docstring 的一句话；`city` 的说明改由 `Field` 提供。函数体仍是演示用的写死返回值。

## 直接调用搜索与抓取

在图上调用之前，可先对单个工具 `ainvoke`，确认密钥、网络与返回形状。异步工具用 `ainvoke`，入参同样是字典。

```python
# %%
from langgraph_project.tools.web import web_search, fetch_url

await web_search.ainvoke({  # type: ignore
  "query": "黄金价格"
})
```

```json

  "follow_up_questions": null,
  "answer": null,
  "images": [],

      "content": "立即注册开户...每克黄金价格 | $141.07 | ...2026 年 9月 03 日...",
      "score": 0.8245895,
      "raw_content": null,
      "id": "7b8f10-00"
    },
    {
      "url": "https://cn.tradingview.com/symbols/XAUUSD",
```

搜索返回里：

- `query`：原样带回本次关键字
- `results[].content`：摘要，不是整页 HTML。Agent底层逻辑第12章的 Agent 搜索引擎：Observation 要干净、短、可引用；标签和导航不应占用上下文
- `results[].score`：相关性；后续 Thought 可据此决定要不要再 `fetch_url`
- `raw_content`：搜索阶段为 `null`。精读某一 URL 时改调 `fetch_url`

指定 URL 提取：

```python
# %%
await fetch_url.ainvoke({  # type: ignore
  "urls": ["https://cn.tradingview.com/symbols/XAUUSD"]
})
```

`extract` 返回指定页正文，仍可能很长。结构如下，正文用省略号代替：

```json
{
  "results": [
    {
      "url": "https://cn.tradingview.com/symbols/XAUUSD",
      "title": "XAUUSD图表— 今日黄金现货价格",
      "raw_content": "![黄金现货/美元](https://s3-symbol-logo.tradingview.com/metal/gold--big.svg)...# 黄金现货/美元\n\n没有交易\n\n[概览](/symbols/XAUUSD/)[新闻]...",
      "images": []
    }
  ],
  "failed_results": [],
  "response_time": 0.01,
  "request_id": "e5cdd36a-7644-468e-80a5-88278da2f040"
}
```

提取返回里：

- `raw_content`：该 URL 提取出的正文（本例 `include_images=False`，`images` 为空）
- `failed_results`：本例为空。抓取失败时失败项在这里，不与成功项混在 `results` 里
- 与 `web_search` 的差异：搜索给多条摘要；提取给指定页正文。模型通常先搜、再按需提取

这两次调用都还没有经过图：没有 `AIMessage.tool_calls`，也没有 `ToolMessage`。接到 `ToolNode` 之后，同一对 `Runnable` 由节点按意图调用，返回值变成 `ToolMessage.content`，经 `add_messages` 进入下一轮 `call_model`。
