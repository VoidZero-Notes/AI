LangChain 的 Chat Model 把各厂商对话接口的差异挡在适配器后面，对外给出同一套 `invoke` / `ainvoke` / `stream` / `astream`。本篇对应 Agent底层逻辑第06章、第07章里自行封装的 `Model`：那里直接调 OpenAI SDK；这里用 `init_chat_model`，换厂商只改 `model_provider` 与密钥。

消息类型对应 Agent底层逻辑第06章的系统提示词（`SystemMessage`）与第07章的会话（把 `HumanMessage` / `AIMessage` 追加进列表）。工具对应第08章的 Tool Calling 与第09章的 `@tool`：`bind_tools` 把 schema 交给模型，模型只返回 `tool_calls`，真正执行仍在调用方。

文档：[Models](https://docs.langchain.com/oss/python/langchain/models)

| 概念              | 作用                                                                       |
| ----------------- | -------------------------------------------------------------------------- |
| Chat Model        | 对话模型的统一外观。一次调用接收消息（或一句字符串），返回 `AIMessage`     |
| `init_chat_model` | 按 `model_provider` 实例化具体适配器（如 Anthropic、OpenAI），调用方式相同 |
| `AIMessage`       | 一次生成的完整结果：正文、思维链块、工具调用、token 用量                   |
| Message           | 上下文中的一条。`system` / `human` / `ai` / `tool` 四种角色                |
| `bind_tools`      | 把工具 schema 绑到后续请求上；返回新的 Runnable，不改原模型对象            |

Chat Completions 本身无状态：服务端不为「上一轮」留记忆。多轮对话能够延续，是因为调用方自己维护消息列表并在下一次请求里原样带上。这一点与 Agent底层逻辑第07章相同，本篇用 LangChain 的 Message 对象代替那边的 `dict` / `Session`。

## 第一次调用

`init_chat_model` 返回的对象是 `Runnable`（与 LangGraph 第01章编译后的图相同：有 `invoke` / `ainvoke` / `stream` / `astream`）。字符串入参会被当成一条 `HumanMessage`。`ainvoke` 走完一整次生成，返回单个 `AIMessage`，不是原始 HTTP JSON。

```python
import asyncio

from langchain.chat_models import init_chat_model
from langchain_core.tracers.langchain import wait_for_all_tracers
from langgraph_project.core.config import anthropic_settings

model = init_chat_model(
  model_provider="anthropic",
  model=anthropic_settings.default_model,
  api_key=anthropic_settings.api_key,
  base_url=anthropic_settings.base_url,
)

async def main():
  response = await model.ainvoke("你好")

  print(f"返回类型：{type(response)}")
  print(f"回复文本：{response.text}")
  print(f"工具调用：{response.tool_calls}")
  print(f"响应块：{response.content_blocks}")
  print(f"额外信息：{response.additional_kwargs}")
  print(f"token消耗：{response.usage_metadata}")
  wait_for_all_tracers()

if __name__ == "__main__":
  asyncio.run(main())
```

打印字段与 `AIMessage` 的对应关系：

| 打印       | 属性                 | 含义                                            |
| ---------- | -------------------- | ----------------------------------------------- |
| 返回类型   | `type(response)`     | `langchain_core.messages.ai.AIMessage`          |
| 回复文本   | `.text`              | 可见正文，不含思维链                            |
| 工具调用   | `.tool_calls`        | 标准化的调用意图列表；本例无工具，为 `[]`       |
| 响应块     | `.content_blocks`    | 跨厂商对齐后的内容块（`reasoning` / `text` 等） |
| 额外信息   | `.additional_kwargs` | 未纳入标准字段的载荷；本例为 `{}`               |
| token 消耗 | `.usage_metadata`    | 入/出/总 token；含 cache 读写计数               |

`.content` 是厂商原生形状（Anthropic 上常见 `thinking` + `text` 的 list）；`.content_blocks` 把它译成统一的 `reasoning` / `text`。读结果时优先用 `.text`、`.content_blocks`、`.tool_calls`，不要解析某一家的原始 JSON。

`content_blocks` 里 `reasoning` 往往是整段内部推理，数百 token。结构如下，冗长正文用省略号代替：

```text
返回类型：<class 'langchain_core.messages.ai.AIMessage'>
回复文本：你好！请问有什么我可以帮您的吗？
工具调用：[]
响应块：[
  {
    "type": "reasoning",
    "reasoning": "Thinking Process:\n\n1. Analyze the Input: 用户说「你好」...\n2. Determine the Intent: ...\n6. Final Output Generation: 你好！请问有什么我可以帮您的吗？",
    "extras": {"signature": ""}
  },
  {
    "type": "text",
    "text": "你好！请问有什么我可以帮您的吗？"
  }
]
额外信息：{}
token消耗：{
  "input_tokens": 11,
  "output_tokens": 592,
  "total_tokens": 603,
  "input_token_details": {"cache_read": 0, "cache_creation": 0}
}
```

- `.text`：`"你好！请问有什么我可以帮您的吗？"`，给人看的最终回复
- `.tool_calls`：`[]`，没有工具调用
- `.usage_metadata.output_tokens`：`592`，远大于可见回复；差额主要在 `reasoning` 块

Agent底层逻辑第07章要求回写历史时保留思维链：下一轮应把整份 `AIMessage`（含 `reasoning` 块）追加进列表，而不是只留 `.text`。

## OpenAI 接口与思维链

OpenAI 官方 Chat Completions **不把原始思维链当明文返回**。这是接口与产品策略，不是 LangChain 解析失败。走 `model_provider="openai"` 时，`content_blocks` 里通常看不到上面那种 `reasoning` 块，Agent底层逻辑第07章「上下文中应保留思维链」在这条链路上无法落实：没有明文，就不能写入会话、下一轮原样带回。

o1 发布说明 [Hiding the Chains of Thought](https://openai.com/index/learning-to-reason-with-llms/) 给出三条原因：

1. **安全监控。** 原始 CoT 留给内部观察推理过程（欺骗、越狱、操纵用户）。这段过程必须保持未按用户偏好对齐；一旦对用户公开，就会被迫把 CoT 也训成合规文案，监控价值消失。
2. **用户侧风险。** 原始推理含未过滤的中间步骤，不适合直接出现在产品里。
3. **竞争。** 完整轨迹便于蒸馏与复现。官方原文写了 competitive advantage。

因此推理 token **照样计费、计入上下文**，但 `message.content` 里通常只有最终答复。Chat Completions 没有 Anthropic 那种可回写的 `thinking` 块。

|            | Anthropic                     | OpenAI 官方                                                                                |
| ---------- | ----------------------------- | ------------------------------------------------------------------------------------------ |
| 拿到什么   | 明文 `thinking` + `signature` | 默认没有明文；最多摘要，或 Responses API 的密文 blob                                       |
| 下一轮     | 整块原样放回 `messages`       | Chat Completions 无对应字段；Responses 把加密项原样传回，或靠服务端 `previous_response_id` |
| 第07章法则 | 能做到：历史里真有推理上下文  | 落不到明文会话上：看不见，也不能当文本存进消息列表                                         |

Responses API 的加密 reasoning item 解决的是**多轮连续性**，不是「把思维链写进会话记录」：调用方持有密文，解密只在 OpenAI 内存里发生。DeepSeek、通义等兼容接口上的 `reasoning_content` / `reasoning` 是第三方扩展字段，官方 Chat Completions 规范里没有。

LangChain 官方 `ChatOpenAI` 明确不提取这些扩展字段（`langchain_openai/chat_models/base.py` 约 628–630 行）：

```text
Non-standard response fields added by third-party providers
(e.g., `reasoning_content`) are not extracted.
```

目前常见做法：

- 自定义 Provider，从网关的非标准字段里把思维链拆出来（下一小节）
- 改用 Anthropic Messages 接口（本篇其余示例）
- 换其他第三方集成（例如 OpenRouter），视其是否透出 reasoning
- 不用 LangChain 的 Chat Model，直接用 OpenAI SDK 自行封装（即 Agent底层逻辑第06章、第07章那条路）

### 自定义 Provider

兼容 OpenAI 形状的网关（例如 Qwen）会在 `message` / `delta` 上多开 `reasoning_content` 或 `reasoning`。`ReasoningChatModel` 继承 `ChatOpenAI`，在流式与非流式两条路径上把该字段写成 v1 的 `ReasoningContentBlock`，使返回形状与前面 Anthropic 示例的 `.content_blocks` 对齐，LangSmith 也能直接渲染。

非流式先把字段写入 `additional_kwargs`，再令 `content = content_blocks`（属性会读到刚写入的思维链），最后删掉 `additional_kwargs` 里的冗余，避免两处各存一份。流式则直接改 chunk 的 `content` 为 `reasoning` / `text` 块列表。

模块路径须与注册表一致，例如 `langgraph_project/core/reasoning_chat_model.py`：

```python
"""OpenAI Chat Model 集成：补全 `reasoning_content`（思维链）提取。

LangChain 官方 `ChatOpenAI` 明确不提取第三方扩展字段
（langchain_openai/chat_models/base.py:628-630）。

本模块提供 `ReasoningChatModel`，继承 `ChatOpenAI`，
补全流式与非流式下的 reasoning_content 提取。
提取结果以 ReasoningContentBlock(type="reasoning", ...)
直接写入 v1 content_blocks，不经 additional_kwargs 中转。
"""

from __future__ import annotations

from typing import TYPE_CHECKING, Any

from langchain_core.outputs import ChatGenerationChunk, ChatResult
from langchain_openai import ChatOpenAI

if TYPE_CHECKING:
  from langchain_core.messages import BaseMessageChunk


class ReasoningChatModel(ChatOpenAI):
  """继承 ChatOpenAI，从 API 响应中提取思维链。

  v1 output_mode 下思维链以 ReasoningContentBlock 写入
  message.content_blocks，LangSmith 可直接渲染。
  """

  output_version: str = "v1"  # type: ignore  # 启用 content_blocks，LangSmith 可渲染

  def _create_chat_result(
    self,
    response: dict[str, Any] | Any,
    generation_info: dict[str, Any] | None = None,
  ) -> ChatResult:
    result = super()._create_chat_result(response, generation_info)

    response_dict = (
      response if isinstance(response, dict) else response.model_dump()
    )
    choices = response_dict.get("choices", [])

    for i, choice in enumerate(choices):
      if i >= len(result.generations):
        break
      msg = choice.get("message", {})
      reasoning = msg.get("reasoning_content") or msg.get("reasoning")
      if reasoning:
        gen = result.generations[i]
        gen.message.additional_kwargs["reasoning_content"] = reasoning

    # 非流式下基类不会做 v1 转换，手动转为 content_blocks
    for gen in result.generations:
      if gen.message.response_metadata.get("output_version") != "v1":
        gen.message = gen.message.model_copy(
          update={
            "content": gen.message.content_blocks,
            "response_metadata": {
              **gen.message.response_metadata,
              "output_version": "v1",
            },
          },
        )
      # content_blocks 已含 reasoning，去掉 additional_kwargs 中的冗余
      gen.message.additional_kwargs.pop("reasoning_content", None)

    return result

  def _convert_chunk_to_generation_chunk(
    self,
    chunk: dict[str, Any],
    default_chunk_class: type[BaseMessageChunk],
    base_generation_info: dict[str, Any] | None,
  ) -> ChatGenerationChunk | None:
    gen_chunk = super()._convert_chunk_to_generation_chunk(
      chunk, default_chunk_class, base_generation_info
    )
    if gen_chunk is None:
      return None

    choices = chunk.get("choices", [])
    if not choices:
      return gen_chunk

    delta = choices[0].get("delta", {})
    reasoning = delta.get("reasoning_content") or delta.get("reasoning")
    text = delta.get("content", "") or ""

    blocks: list[dict[str, Any]] = []
    if reasoning:
      blocks.append({"type": "reasoning", "reasoning": reasoning, "index": 0})
    if text:
      blocks.append({"type": "text", "text": text, "index": 1})

    if blocks:
      gen_chunk.message.content = blocks  # type: ignore[assignment]
      gen_chunk.message.response_metadata["output_version"] = "v1"

    return gen_chunk

from langchain.chat_models.base import _BUILTIN_PROVIDERS, _call

_PROVIDER_KEY = "openai_reasoning"

if _PROVIDER_KEY not in _BUILTIN_PROVIDERS:
  _BUILTIN_PROVIDERS[_PROVIDER_KEY] = (
    "langgraph_python.core.reasoning_chat_model",
    "ReasoningChatModel",
    _call,
  )
```

直接实例化：

```python
model = ReasoningChatModel(model="qwen3.7-max", temperature=0)
response = model.invoke("什么是量子计算？")

for block in response.content_blocks:
  if block["type"] == "reasoning":
    print(block["reasoning"])
print(response.text)
```

注册进 `_BUILTIN_PROVIDERS` 之后，也可用 `init_chat_model(model_provider="openai_reasoning", ...)`。模块须在调用 `init_chat_model` 之前被 import，否则注册表里还没有这一项。

本篇后续示例一律走 Anthropic，是为了让 `reasoning` / `thinking` 出现在返回里，便于对照字段；走 Qwen 等兼容网关时换本小节的 Provider。

## 流式传输

`ainvoke` 等整份 `AIMessage` 齐了才返回。`astream` 按生成进度产出 `AIMessageChunk`：每个 chunk 的 `content_blocks` 只含这一小段增量（一段 reasoning、几个字、半截工具参数）。本篇只看形状，不接入业务。

```python
chunks = model.astream("你好")

async for chunk in chunks:
  for block in chunk.content_blocks:
    print(block)
```

循环里打印的是单块，例如 `{"type": "reasoning", "reasoning": "..."}` 或 `{"type": "text", "text": "你"}`。需要完整消息时，官方接口是把这些 chunk **相加**（`full = chunk1 + chunk2 + ...`）还原成一份 `AIMessage`。

## 消息

字符串入参只覆盖「一句 user」。多角色、多轮、系统约束必须显式组 `messages` 列表。四种类型与 Chat Completions 的 `role` 对齐：

| 类型            | `role`      | 含义                                                                                           |
| --------------- | ----------- | ---------------------------------------------------------------------------------------------- |
| `SystemMessage` | `system`    | 全局约束与角色。原则见 Agent底层逻辑第06章：精简、自洽、全局约束、保持静态、结构化             |
| `HumanMessage`  | `user`      | 用户输入                                                                                       |
| `AIMessage`     | `assistant` | 模型上一轮输出；多轮时原样追加，不要改写成纯正文                                               |
| `ToolMessage`   | `tool`      | 某次工具执行的结果，用 `tool_call_id` 对上对应的 `tool_calls` 项。本篇尚未执行工具，后面会用到 |

顺序有约定：`SystemMessage` 放最前且尽量固定（与第06章「保持静态」、第07章 prompt cache 前缀一致）；其后按时间追加 human / ai / tool。

```python
import asyncio

from langchain.chat_models import init_chat_model
from langchain.messages import AIMessage, HumanMessage, SystemMessage, ToolMessage
from langchain_core.tracers.langchain import wait_for_all_tracers
from langgraph_project.core.config import anthropic_settings

model = init_chat_model(
  model_provider="anthropic",
  model=anthropic_settings.default_model,
  api_key=anthropic_settings.api_key,
  base_url=anthropic_settings.base_url,
)

async def main():
  messages = [
    SystemMessage("请使用猪八戒的语气回复"),  # role: system
    HumanMessage("你好，呆子"),  # role: user
  ]

  response = await model.ainvoke(messages)

  print(response.content)

  wait_for_all_tracers()

if __name__ == "__main__":
  asyncio.run(main())
```

这里打印的是 `.content`（Anthropic 原生 list），不是 `.text`。完整返回里 `thinking` 同样是数百 token。结构如下，冗长正文用省略号代替：

```text
[
  {
    "type": "thinking",
    "thinking": "用户让我用猪八戒的语气回复，并且称呼我为「呆子」。\n猪八戒的性格特点：贪吃贪睡……\n起草回复：……\n就用这个了。",
    "signature": ""
  },
  {
    "type": "text",
    "text": "去去去！哪来的猴崽子，敢叫俺老猪「呆子」！……要是没别的事，老猪我可先歇着了，哎哟，困死老猪了……"
  }
]
```

同一轮里的两块：

- `thinking`：模型内部推理，对应 `.content_blocks` 里 `type: "reasoning"` 的那一块
- `text`：可见回复，即 `.text`

同一轮结果的两种视图：`.content` 保厂商原样；`.content_blocks` 把 `thinking` 译成 `reasoning`。多轮回写应追加整个 `response` 对象，两块都在。

## 多轮对话

模型当轮只能看见本次传入的 `messages`。第二轮要延续同一段对话，必须把上一轮的 `AIMessage` 留在列表里，再追加新的 `HumanMessage`。只发新的那一句、不带上历史，模型就不知道「呆子」已经说过。这是 Agent底层逻辑第07章「历史上下文不可修改」在 LangChain 里的对应：只在末尾追加，不改、不删、不重排已有条目。

下面用笔记本单元格拆成两次调用，共用同一份 `messages`：

```python
# %%
from langchain.chat_models import init_chat_model
from langchain.messages import AIMessage, HumanMessage, SystemMessage, ToolMessage
from langgraph_project.core.config import anthropic_settings

model = init_chat_model(
  model_provider="anthropic",
  model=anthropic_settings.default_model,
  api_key=anthropic_settings.api_key,
  base_url=anthropic_settings.base_url,
)

messages = [
  SystemMessage("请使用猪八戒的语气回复"),  # role: system
  HumanMessage("你好，呆子"),  # role: user
]

def run1():
  response = model.invoke(messages)
  messages.append(response)

# %%
run1()

# %%
def run2():
  messages.append(HumanMessage("想挨棍子了？"))
  response = model.invoke(messages)
  messages.append(response)

run2()
```

`run1` 之后列表为：system → human（呆子）→ ai（猪八戒那轮，含 thinking）。`run2` 再追加 human（棍子）并 `invoke` 整份列表，返回的新 `AIMessage` 继续 `append`。`run2` 没有重写 `run1` 的回复，prompt cache 的前缀才能对上（见第07章）。

此处用同步 `invoke`，与前面的 `ainvoke` 只是是否异步；返回值同为 `AIMessage`。

## 工具

Agent底层逻辑第08章：模型不会执行函数，只根据 schema 决定「调哪个、参数是什么」。第09章用 `@tool` 从函数签名生成 schema。LangChain 把这两步封装在装饰器与 `bind_tools` 上：

1. `@tool` 包装普通函数，用 docstring / 类型注解生成 schema，得到的对象本身也是 `Runnable`
2. `bind_tools([...])` 返回**新的** Runnable，后续 `invoke` 会把这些 schema 放进请求；原 `model` 不变
3. 返回的 `AIMessage.tool_calls` 是调用意图。本例到此为止，没有按 `name` 执行，也没有构造 `ToolMessage` 回写——那一步仍是第08章、第09章的调用方职责

```python
from langchain.chat_models import init_chat_model
from langchain.tools import tool
from langchain_core.runnables import Runnable
from langgraph_project.core.config import anthropic_settings

model = init_chat_model(
  model_provider="anthropic",
  model=anthropic_settings.default_model,
  api_key=anthropic_settings.api_key,
  base_url=anthropic_settings.base_url,
)

@tool
def get_weather(location: str) -> str:
  """
  获取天气

  参数：
  - location: 城市名称
  """
  return f"It's sunny in {location}."

model_with_tools = model.bind_tools([get_weather])

response = model_with_tools.invoke("伦敦的天气如何？")

print(isinstance(get_weather, Runnable))  # True
print(isinstance(model, Runnable))  # True
print(response)
```

`get_weather` 与 `model` 都是 `Runnable`，所以能进同一套 `invoke` 接口；图节点也接收 `Runnable`（第01章）。`bind_tools` 之后问天气，模型应发出 `get_weather`，而不是直接编造气温。

`print(response)` 会把整份 `AIMessage` 打成一行，`thinking` 与 `response_metadata` 很长。结构如下，冗长字段用省略号代替：

```text
content=[
  {
    "type": "thinking",
    "thinking": "用户想知道伦敦的天气情况。我需要调用 get_weather，参数 location=「伦敦」。",
    "signature": ""
  },
  {
    "type": "tool_use",
    "id": "toolu_17431e7a094a4093a31985af",
    "name": "get_weather",
    "input": {"location": "伦敦"},
    "toolset_name": null
  }
]
tool_calls=[
  {
    "name": "get_weather",
    "args": {"location": "伦敦"},
    "id": "toolu_17431e7a094a4093a31985af",
    "type": "tool_call"
  }
]
response_metadata.stop_reason: tool_use
usage_metadata: {
  "input_tokens": 280,
  "output_tokens": 47,
  "total_tokens": 327,
  "input_token_details": {"cache_read": 0, "cache_creation": 0}
}
```

调用意图出现在两处，本轮停在 `tool_use`：

- `content` 里的 `tool_use`：Anthropic 原生块，`input` 已是解析后的参数字典
- `.tool_calls`：跨厂商标准化后的同一意图；应用代码读这个列表，不要解析厂商原生 `content`
- `stop_reason: tool_use`：本轮停在「要调工具」，不是最终答复。下一步应执行 `get_weather("伦敦")`，把结果做成 `ToolMessage(tool_call_id="toolu_...")` 追加进 `messages`，再 `invoke` 一次

本例 `output_tokens` 只有 47：模型把预算用在发出调用，而不是写长回复。`get_weather` 的函数体此时**尚未运行**；`It's sunny in {location}.` 要等调用方真正去调这个 `Runnable` 才会出现。
