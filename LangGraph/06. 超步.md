第01章把图编译成可运行对象，并指出底层由 Pregel 执行。Pregel 按 BSP（Bulk Synchronous Parallel，整体同步并行）把一次运行切成一串超步：每一步内选出的节点并行计算，全部完成后再同步、写回通道，然后进入下一步。超步是运行时概念，不是编译时拓扑。本篇先说明 BSP 与超步，再用分支、循环、并行三张图对照观察。

Agent底层逻辑第17章的 Graph Engineering 讨论多个 loop 如何连接，常见形状是分支、汇合、回退。本篇不展开那些工程层，只观察同一类拓扑在 Pregel 运行时如何切成超步。

文档：[LangGraph runtime](https://docs.langchain.com/oss/python/langgraph/pregel) · Pregel 论文见第01章

| 概念     | 作用                                                                                          |
| -------- | --------------------------------------------------------------------------------------------- |
| Pregel   | LangGraph 的运行时。第01章 `compile()` 得到的就是 Pregel 实例                                 |
| BSP      | Bulk Synchronous Parallel，整体同步并行。Pregel 按此模型推进一次运行                          |
| 超步     | BSP 的一次迭代：规划 → 并行执行 → 屏障同步并写回通道                                          |
| 屏障     | 当前超步内全部节点结束后，才进入下一超步；先完成的节点不能提前启动其后继                      |
| 运行时   | 拓扑在编译时固定；哪些节点进入哪一超步，由当次运行的边与状态决定                              |

## BSP 与超步

Pregel 来自 2010 年谷歌的大规模图计算系统，执行模型是 BSP。一个完整的 BSP 程序由一系列**串行衔接**的超步组成：超步与超步之间有先后，同一超步内部的节点则并行。

每一个超步包含三个阶段：

| 阶段 | 做什么 |
| ---- | ------ |
| 规划 | 根据上一超步更新过的通道，选出本超步要执行的节点。首次选出订阅了输入通道的节点 |
| 执行 | 选出的节点并行执行，直到全部完成、任一失败或超时。执行期间，本超步写入的通道更新对其他节点不可见 |
| 更新 | 把本超步的写入合并进通道（经由第04章的 Reducer），再进入下一超步 |

没有节点被选出，或达到最大步数，运行结束。

三点必须分开：

1. **编译时固定的是拓扑。** 第01章：`compile()` 之后不能再 `add_node` / `add_edge`。节点集合、边、条件路由表在编译时已经确定。
2. **超步是运行时切分。** 条件边走哪一条、循环走几圈、并行有几路，要到 `invoke` 时才确定。同一张编译好的图，不同输入会走出不同的超步序列。
3. **同一超步内互相看不见对方的写入。** 节点读到的是本超步开始时的状态快照；并行节点即使同时写同一通道，也要等屏障之后才由 reducer 合并，下一超步才能读到。

因此：先完成的节点不能立刻启动其后继。后继被排进**下一**超步，而下一超步必须等本超步最慢的那个节点结束。这就是屏障，也是下面并行图用不同 `sleep` 要观察的现象。

## 用图观察超步

三张图都把进入过的节点名追加到 `traces`，reducer 是第04章的 `operator.add`。Studio 里可以看到每一步激活了哪些节点；下面用超步序列把同一件事写出来。

### 分支

编译时拓扑同时包含 B 与 C；运行时只走其中一条。条件边的标签（`小白兔` / `大灰狼`）只是路由名，真正决定下一跳的是 `branch` 字段。

`langgraph_project/graphs/demo/demo_branch_graph.py`：

```python
import operator
from typing import Annotated, TypedDict
from langgraph.graph import END, START, StateGraph

class DemoBranchGraphState(TypedDict):
  """分支图演示状态"""

  # 追踪信息，使用 operator.add reducer 追加累积，观察每次进入节点的变化
  traces: Annotated[list[str], operator.add]
  # 分支选择信息
  branch: str

def _make_node(name: str):
  """生成一个向 traces 中追加节点名的简单节点"""

  async def node(state: DemoBranchGraphState) -> dict:
    print(f"进入节点：{name}")
    return {"traces": [name]}

  return node

def build_graph():
  """生成带分支的图"""
  workflow = StateGraph(DemoBranchGraphState)

  for node_name in ["A", "B", "C"]:
    workflow.add_node(node_name, _make_node(node_name))

  workflow.add_edge(START, "A")
  # A 之后根据 branch 字段条件路由到 B 分支或 C 分支
  workflow.add_conditional_edges(
    "A",
    lambda state: "小白兔" if state["branch"] == "B" else "大灰狼",
    {"小白兔": "B", "大灰狼": "C"},
  )
  workflow.add_edge("B", END)
  workflow.add_edge("C", END)

  return workflow
```

输入 `{"branch": "B"}` 时的超步：

| 超步 | 执行的节点 | 说明 |
| ---- | ---------- | ---- |
| 1    | A          | 读到 `branch == "B"`，路由名 `小白兔` |
| 2    | B          | C 未被选出，本轮运行不进入 C |

输入其它 `branch` 时，超步 2 执行的是 C。编译结果里 B、C 都在，但当次运行的超步序列只包含被路由选中的那一个。这就是「超步是运行时概念」：拓扑有两条出边，一次运行只产生一条超步链。

### 循环

同一节点可以出现在多个超步里。`a_count` 每进入 A 减一；B 之后若仍大于 0 则回到 A，否则进入 C 结束。

`langgraph_project/graphs/demo/demo_loop_graph.py`：

```python
import operator
from typing import Annotated, TypedDict
from langgraph.graph import END, START, StateGraph

class DemoLoopGraphState(TypedDict):
  """循环图演示状态"""

  # 追踪信息，使用 operator.add reducer 追加累积，观察每次进入节点的变化
  traces: Annotated[list[str], operator.add]
  # A 节点的执行次数
  a_count: int

def _make_node(name: str):
  """生成一个向 traces 中追加节点名的简单节点"""

  async def node(state: DemoLoopGraphState) -> dict:
    print(f"进入节点：{name}")
    return {"traces": [name]}

  return node

async def node_a(state: DemoLoopGraphState) -> dict:
  """A 节点，每次进入将 a_count 减一"""
  print(f"进入节点：A，剩余次数 {state['a_count']}")
  return {"traces": ["A"], "a_count": state["a_count"] - 1}

def build_graph():
  """生成带循环的图：START -> A -> B -> (a_count>0 回到 A，否则进入 C) -> END"""
  workflow = StateGraph(DemoLoopGraphState)

  workflow.add_node("A", node_a)
  for node_name in ["B", "C"]:
    workflow.add_node(node_name, _make_node(node_name))

  workflow.add_edge(START, "A")
  workflow.add_edge("A", "B")
  # B 根据 a_count 字段决定是回到 A 继续循环，还是进入 C 结束
  workflow.add_conditional_edges(
    "B",
    lambda state: "A" if state["a_count"] > 0 else "C",
    {"A": "A", "C": "C"},
  )
  workflow.add_edge("C", END)

  return workflow
```

输入 `{"a_count": 2}` 时的超步：

| 超步 | 执行的节点 | `a_count`（进入 A 时） |
| ---- | ---------- | ---------------------- |
| 1    | A          | 2，写回 1              |
| 2    | B          | 仍为 1，路由回 A       |
| 3    | A          | 1，写回 0              |
| 4    | B          | 已为 0，路由到 C       |
| 5    | C          | 结束                   |

`traces` 最终为 `["A", "B", "A", "B", "C"]`。编译时 A、B 各只有一个节点定义；运行时它们各执行了两轮，对应四个不同的超步。圈数由输入决定，不是编译时固定的。

### 并行

扇出后的多条支路落在**同一超步**里并行；屏障之后才一起进入下一层。`sleep` 用来拉开完成时间，使屏障可观察：先结束的支路不能提前启动其后继。

`langgraph_project/graphs/demo/demo_parallel_graph.py`：

```python
import asyncio
import operator
from typing import Annotated, TypedDict
from langgraph.graph import END, START, StateGraph

class DemoComplexGraphState(TypedDict):
  """复杂图演示状态"""

  # 追踪信息，使用 operator.add reducer 追加累积，观察每次进入节点的变化
  traces: Annotated[list[str], operator.add]

def _make_node(name: str, sleep=0):
  """生成一个向 traces 中追加节点名的简单节点"""

  async def node(state: DemoComplexGraphState) -> dict:
    print(f"进入节点：{name}")
    await asyncio.sleep(sleep)
    return {"traces": [name]}

  return node

def build_graph():
  """生成并发图：
  START -> A -> {B1, C1, D1} -> {B2, C2, D2} -> E(结束)
  """
  workflow = StateGraph(DemoComplexGraphState)

  for node_name, sleep in [
    ("A", 0),
    ("B1", 1),
    ("C1", 2),
    ("D1", 3),
    ("B2", 1),
    ("C2", 2),
    ("D2", 3),
    ("E", 0),
  ]:
    workflow.add_node(node_name, _make_node(node_name, sleep))

  workflow.add_edge(START, "A")
  # A 并发进入 B1、C1、D1
  workflow.add_edge("A", "B1")
  workflow.add_edge("A", "C1")
  workflow.add_edge("A", "D1")
  # 链式推进
  workflow.add_edge("B1", "B2")
  workflow.add_edge("C1", "C2")
  workflow.add_edge("D1", "D2")
  # B2、C2、D2 汇合到 E
  workflow.add_edge("B2", "E")
  workflow.add_edge("C2", "E")
  workflow.add_edge("D2", "E")
  workflow.add_edge("E", END)

  return workflow
```

超步与墙钟时间：

| 超步 | 执行的节点     | 该超步墙钟 | 说明 |
| ---- | -------------- | ---------- | ---- |
| 1    | A              | ~0 秒      | 扇出到 B1、C1、D1 |
| 2    | B1、C1、D1     | ~3 秒      | 三者并行，耗时取 `max(1, 2, 3)`，不是相加 |
| 3    | B2、C2、D2     | ~3 秒      | B1 虽约 1 秒结束，B2 仍须等超步 2 的屏障 |
| 4    | E              | ~0 秒      | 三条支路汇合后再执行 |

B1 先于 D1 约 2 秒结束，但 B2 不会在第 2 秒启动：它属于下一超步，而下一超步要等 D1 结束。整张图约 6 秒，而不是把六次 `sleep` 串起来的 12 秒。

同一超步内的节点读到的都是该超步开始时的状态；它们对 `traces` 的写入要到屏障之后才由 `operator.add` 合并。因此并行节点看不到彼此尚未提交的更新。
