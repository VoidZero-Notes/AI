`RunnableConfig.configurable` 除了框架预留字段与 Chat Model 消费的模型参数，也可以承载节点自己读取的自定义键：用哪一个模型实例、系统提示词正文、绑定哪些工具，都可以作为业务键放进 `configurable`，Chat Model 不会读取，需要在 `call_model` 里显式取出。第10章已经用这条通道传过模型参数，但消费方是 Chat Model 的 `configurable_fields`，节点不必改签名；本篇的消费方换成节点本身。

第07章已经用 `configurable.thread_id` 指定检查点线程。本篇在同一个 `configurable` 字典里增加业务键。Agent底层逻辑第10章的 ReAct 在构造 Session 时允许覆盖 `system_prompt` 与 `tools`；本篇把同一类覆盖从构造参数改到当次 `ainvoke` 的 `RunnableConfig`，不写进图状态，也不被第07章的检查点当作业务状态保存。

| 概念              | 作用                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------------- |
| `RunnableConfig`  | 任何 `Runnable` 的 `invoke` / `ainvoke` 都可接收的配置对象；第10章已用来覆盖模型字段          |
| `configurable`    | 其中的字典。第07章放 `thread_id`，第10章放模型参数，本篇再放 `system_prompt` / `tools` / `model` |
| 依赖注入          | 节点函数第二个参数声明 `config: RunnableConfig`，框架按签名传入                               |
| `ensure_config()` | 节点签名不含 `config` 时，从 `ContextVar` 取出当前这份配置                                    |
| `recursion_limit` | 单次 run 的超步上限（第06章）；默认 25                                                        |

## 注入与读取

第10章：外层图把 `config` 写入 `ContextVar`，嵌套的 Chat Model 自行消费已声明的字段，节点函数不必接收 `config`。那只覆盖 `init_chat_model` 的参数（`model` / `temperature` 等）。本篇的键是节点自己的分支条件，必须在节点内读出。

两种读法得到同一份对象：

```python
import asyncio
from typing import TypedDict
from langchain_core.runnables import RunnableConfig, ensure_config
from langgraph.graph import StateGraph

class State(TypedDict):
  pass

# 依赖注入：第二个参数声明 RunnableConfig，框架按签名传入
def node_di(state, config: RunnableConfig):
  return {}

# 签名不含 config 时，从 ContextVar 取出当前配置
def node_ensure(state):
  config = ensure_config()
  return {}

builder = StateGraph(State)
builder.add_node(node_di)
builder.add_node(node_ensure)
builder.set_entry_point("node_di")
builder.add_edge("node_di", "node_ensure")
builder.set_finish_point("node_ensure")

graph = builder.compile()

asyncio.run(graph.ainvoke(
  input={},
  config={
    "configurable": {
      "a": "1"
    }
  }
))
```

依赖注入便于标注类型；`ensure_config()` 用于不能改签名的节点。下面的 `call_model` 走依赖注入。

## 工程：call_model

第08章最后一次给出完整 `call_model`：从状态读 `model_config` 与 `system_prompt_template`，按模板渲染 `SystemMessage`，`create_model(**model_config.to_kwargs())`，再 `bind_tools(tools)` 绑定全部工具。第10章只改了创建模型那两行：工厂改为无参，节点改为 `create_model()`，不再读状态里的 `model_config`；系统提示词与工具清单未动。

本篇节点增加 `config: RunnableConfig`，三处改为按配置组装。

`langgraph_project/nodes/call_model.py`：

```python
from langchain_core.messages import SystemMessage
from langchain_core.runnables import RunnableConfig
from langgraph_project.core.create_model import create_model
from langgraph_project.core.mock_model import mock_model
from langgraph_project.states.core_agent_state import CoreAgentState
from langgraph_project.tools import get_tools, tools

def _get_system_prompts(config: RunnableConfig):
  """根据配置获取系统提示词"""
  system_msgs = []
  configurable = config.get("configurable") or {}
  system_prompt = configurable.get("system_prompt")
  if system_prompt:
    system_msgs.append(SystemMessage(system_prompt))
  return system_msgs

def _get_model(config: RunnableConfig):
  """根据配置获取模型对象"""
  configurable = config.get("configurable") or {}
  model = configurable.get("model")
  if model == "fake":
    return mock_model()
  else:
    return create_model()

def _get_tools(config: RunnableConfig):
  """根据配置获取工具列表，未配置时返回全部工具"""
  configurable = config.get("configurable") or {}
  tool_names = configurable.get("tools")
  if tool_names:
    return get_tools(tool_names)
  return tools

async def call_model(state: CoreAgentState, config: RunnableConfig) -> dict:
  """调用模型节点"""
  messages = state["messages"]
  model = _get_model(config)
  system_prompts = _get_system_prompts(config)
  active_tools = _get_tools(config)
  model_with_tools = model.bind_tools(active_tools)

  response = await model_with_tools.ainvoke([*system_prompts, *messages])
  return {"messages": [response]}
```

相对第08章（第10章已去掉 `model_config` 与带参 `create_model`）：

| 第08章 / 第10章                                         | 本篇                                                         | 原因                                                         |
| ------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 签名只有 `state`                                        | 增加 `config: RunnableConfig`                                | 自定义键必须由节点读出，不能再只靠 Chat Model 消费           |
| `_build_system_message(template_name)` 渲染模板         | `_get_system_prompts` 把 `configurable.system_prompt` 写成 `SystemMessage` | 提示词改由当次调用注入，不再走模板文件                       |
| 未配置模板时默认 `"system"`                             | 未配置则系统提示词列表为空                                   | 覆盖变成可选；不传就不带 system                              |
| 第08章 `create_model(**kwargs)`；第10章 `create_model()` | `_get_model`：`model == "fake"` 时用第09章的 `mock_model()`  | 同一张图按当次配置在真实模型与假模型之间切换                 |
| `bind_tools(tools)` 绑定全部工具                        | `_get_tools` 按名称取子集，未配置仍绑定全部                  | 与 Agent底层逻辑第10章「空则用默认、传入则覆盖」同一约定     |

`configurable.model` 在第10章表示覆盖 `init_chat_model` 的模型名（如 `qwen3.7-max`）。本篇 `_get_model` 把同一个键当成开关：值为 `"fake"` 时换假模型，否则仍走 `create_model()`。两种语义不要写在同一次调用里互相覆盖。

取消息、`bind_tools`、返回 `{"messages": [response]}` 与第08章相同。`bind_tools` 仍返回新的 Runnable（第02章）；假模型的 `bind_tools` 不消费 schema（第09章）。

## 工程：从状态中移除系统提示词模板

第04章把 `system_prompt_template` 放进图状态，节点按模板名渲染。第10章删除 `model_config` 时保留了该字段。本篇删除模板名：系统提示词不再是图状态的一部分。

与第10章删 `model_config` 同一理由。第07章的检查点会持久化状态；模板名写进状态，会与对话历史绑在同一份快照上，换一次提示词还得改状态。改走 `RunnableConfig` 后，提示词只作用于当次 `ainvoke`，不进入 `messages`，也不被检查点当作业务状态保存。

`langgraph_project/states/core_agent_state.py`：

```python
from typing import Annotated, Required, TypedDict
from langchain_core.messages import BaseMessage
from langgraph.graph.message import add_messages

class CoreAgentState(TypedDict):
  """核心 Agent 图状态"""
  # 消息列表，使用 add_messages reducer 自动累积
  messages: Required[Annotated[list[BaseMessage], add_messages]]
```

相对第10章：去掉 `system_prompt_template: NotRequired[str]` 及其 import。`messages` 不变。第04章的 `_build_system_message`、`_SYSTEM_PROMPT_TEMPLATES`、模板文件在这条路径上不再被节点引用。

## 工程：按名称取工具

第08章最后一次给出 `tools/__init__.py`：三个工具汇总成一份列表，同时交给 `bind_tools` 与 `ToolNode`。本篇改成按名称检索，便于 `configurable.tools` 传入字符串列表。

`langgraph_project/tools/__init__.py`：

```python
from langchain_core.tools import BaseTool
from .time import get_current_time
from .web import fetch_url, web_search

_AVAILABLE_TOOLS: dict[str, BaseTool] = {
  "fetch_url": fetch_url,
  "web_search": web_search,
  "get_current_time": get_current_time,
}

tools: list[BaseTool] = list(_AVAILABLE_TOOLS.values())

def get_tools(names: list[str]) -> list[BaseTool]:
  """根据工具名称列表返回对应的工具函数列表，未知名称会被忽略"""
  return [_AVAILABLE_TOOLS[name] for name in names if name in _AVAILABLE_TOOLS]
```

相对第08章：增加名称到对象的字典与 `get_tools`；`tools` 仍是全部工具的列表，未配置时行为与第08章相同。`ToolNode(tools)` 仍挂全部工具（第08章的图未改）：模型侧按配置只看见子集，执行侧按名字仍能找到。未知名称直接忽略，不会抛错。

## 其他预设字段

`configurable` 之外，`RunnableConfig` 还有一批框架预留字段。与第07章的 `thread_id`、第10章的 `callbacks` 写在同一份对象里，都不是图状态。

| 字段                     | 作用                             |
| ------------------------ | -------------------------------- |
| `configurable`           | 用户自定义任意键值               |
| `configurable.thread_id` | 线程 id（第07章）                |
| `max_concurrency`        | 一个超步中并行任务数上限         |
| `recursion_limit`        | 单次 run 的超步上限（默认 25）   |
| `tags`                   | 给这次运行打标签，用于追踪 / 过滤 |
| `metadata`               | 自定义元数据（LangSmith 追踪用） |
| `callbacks`              | 回调处理器（第10章的 `ConfigPrinter`） |
| `run_name`               | 给运行命名                       |
| `run_id`                 | 手动指定运行 ID                  |

## 超步上限

第09章的假模型用 `max_tool_calls` 模拟「同一条用户消息之后最多连续调用 N 次，再给出 `final`」。当时默认是 2。本篇把该值改为 5，再把 `recursion_limit` 设为 3，用来观察第06章的超步上限。

`langgraph_project/core/mock_model.config.jsonc`：

```jsonc
{
  ...,
  "max_tool_calls": 5,
}
```

```python
asyncio.run(graph.ainvoke(
  input={
    "messages": [HumanMessage("现在什么时间")]
  },
  config={
    "configurable": {
      "model": "fake",
      "system_prompt": "你是一名金融分析师"
    },
    "recursion_limit": 3,
    "tags": ["金融分析", "fake model"],
    "metadata": {
      "app_version": "0.0.1",
      "env": "dev"
    },
    "run_name": "金融Agent"
  }
))
```

用户消息含「时间」，假模型按第09章的规则发出 `get_current_time`。图走第08章的 `model → tools → model`。`max_tool_calls` 为 5，工具结果未满 5 次就不会给出 `final`，循环不会停。`recursion_limit` 为 3，第 3 个超步结束时仍未碰到停止条件，框架抛出 `GraphRecursionError`：

```text
langgraph.errors.GraphRecursionError: Recursion limit of 3 reached without hitting a stop condition. You can increase the limit by setting the `recursion_limit` config key.
For troubleshooting, visit: https://docs.langchain.com/oss/python/langgraph/errors/GRAPH_RECURSION_LIMIT
```

完整栈回溯很长，根因就是这次把超步上限设成了 3，而假模型还要继续调工具。提高 `recursion_limit`，或把 `max_tool_calls` 降到循环能在上限内结束，都可以让这次 run 走完。
