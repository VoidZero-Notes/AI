Chat Completions 无状态，Agent底层逻辑第07章用 Session 在调用方维护消息历史：按 id 标识一条会话，只在末尾追加，整份列表下一轮原样带回。第02章、第03章在 LangChain 里做同一件事：每次 `invoke` 传入完整 `messages`。图的 `invoke` 默认同样无跨次记忆：未配置检查点时，每次只看见本次 input。

本篇把这件事交给 LangGraph：Thread 对应 Agent底层逻辑第07章的会话 id；Checkpointer 对应 Session 的持久化；同一线程上的多次 Run 对应 Agent底层逻辑第11章里同一条 Session 上的多个轮次。第04章的 `add_messages` 负责把本轮新消息合并进已持久化的列表，因此调用方不必再手传完整历史。检查点写在第06章超步的边界上。第05章的 Agent Server 在服务端注入同一套机制；本篇只讲进程内显式配置。

文档：[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence) · [Threads](https://docs.langchain.com/oss/python/langgraph/use-graph-api)

| 概念                | 作用                                                                                |
| ------------------- | ----------------------------------------------------------------------------------- |
| 检查点              | 某一时刻的图状态快照。写在 START 附近，以及每个超步结束之后                         |
| Checkpointer        | 检查点存储器。编译时传入；内置内存、PostgreSQL、SQLite，也可自行实现                |
| 线程 Thread         | 检查点的命名空间。运行时用 `thread_id` 指定；同一张图可在多条线程上各自维护独立会话 |
| Turn / Run          | 某条线程上，图从 START 执行到 END 的一次完整调用                                    |
| `InMemorySaver`     | 内存后端。进程退出后检查点消失                                                      |
| `get_state`         | 读取该线程的最新快照                                                                |
| `get_state_history` | 读取该线程上全部快照（含一次 Run 内部的中间超步）                                   |

层级是：图在某条线程上执行；一条线程可以有多次 Run；一次 Run 经过多个超步（第06章），每个超步可含多个节点；检查点出现在 START 附近以及每个超步之后。换一个 `thread_id` 就是另一条会话，互不读取对方的检查点。

## 编译时指定存储器

检查点能否跨次 `invoke` 存活，取决于编译，不取决于某一次调用。`compile(checkpointer=...)` 之后，运行时必须在 `config` 里给出 `thread_id`，否则框架不知道写入哪条线程。

```python
# %%
from langgraph_project.graphs.core_agent_graph import build_graph
from langgraph.checkpoint.memory import InMemorySaver
from langchain_core.messages import HumanMessage
from langchain_core.runnables import RunnableConfig

graph = build_graph().compile(checkpointer=InMemorySaver())

config: RunnableConfig = {
  "configurable": {
    "thread_id": "chat 1"
  }
}
```

`InMemorySaver` 仅存在于当前进程。需要写入磁盘或跨进程时，换 PostgreSQL / SQLite / 自定义后端，接口相同：仍是编译时传入，运行时只带 `thread_id`。

## 同一线程上的多次运行

第02章多轮对话必须自己 `messages.append`，再把整份列表传给模型。配置检查点之后，每次 `ainvoke` 只需传入本轮新的 `HumanMessage`：框架按 `thread_id` 读出该线程最新快照，用第04章的 `add_messages` 把新消息合并进 `messages` 通道，本轮结束后再写入新的检查点。

下面四个单元格共用同一个 `config`，即同一条线程上的四次 Run：

```python
# %%
await graph.ainvoke(  # type: ignore
  input={
    "messages": [
      HumanMessage("你好，我是秦始皇")
    ]
  },
  config=config
)

# %%
await graph.ainvoke(  # type: ignore
  input={
    "messages": [
      HumanMessage("朕的国家怎么亡的？")
    ]
  },
  config=config
)

# %%
await graph.ainvoke(  # type: ignore
  input={
    "messages": [
      HumanMessage("你能为朕做什么？")
    ]
  },
  config=config
)

# %%
await graph.ainvoke(  # type: ignore
  input={
    "messages": [
      HumanMessage("不,你需要V朕50")
    ]
  },
  config=config
)
```

最后一次返回的是整份图状态，不是单条 `AIMessage`。`messages` 里已有四轮对话共 8 条消息。完整对象含思维链、`response_metadata`、token 用量，很长。结构如下，冗长字段用省略号代替：

```text
{'messages': [
  HumanMessage(content='你好，我是秦始皇', id='de6cfd21-...'),
  AIMessage(content=[
    {'type': 'thinking', 'thinking': '用户说「你好，我是秦始皇」……接梗并回到编程助手身份……'},
    {'type': 'text', 'text': '你好，始皇帝！我是您的编程助手。……请问有什么编程或技术问题需要微臣协助？'}
  ], usage_metadata={'input_tokens': 103, 'output_tokens': 788, ...}),
  HumanMessage(content='朕的国家怎么亡的？', id='f6decc0b-...'),
  AIMessage(content=[
    {'type': 'thinking', 'thinking': '继续扮演秦始皇，问秦朝灭亡……用系统架构类比……'},
    {'type': 'text', 'text': '陛下，从系统架构的角度来看，大秦项目的「宕机」主要有以下几个致命原因：……'}
  ], usage_metadata={'input_tokens': 909, 'output_tokens': 1014, ...}),
  HumanMessage(content='你能为朕做什么？', id='4e9ad95f-...'),
  AIMessage(..., usage_metadata={'input_tokens': 1940, 'output_tokens': 821, ...}),
  HumanMessage(content='不,你需要V朕50', id='865d6b9d-...'),
  AIMessage(content=[
    {'type': 'thinking', 'thinking': '经典「V我50」梗……用代码代替转账……'},
    {'type': 'text', 'text': '陛下，微臣的国库（内存）里只有 `0` 和 `1`，无法进行微信或支付宝转账。……'}
  ], usage_metadata={'input_tokens': 2780, 'output_tokens': 528, ...})
]}
```

四次 Run 合在同一条线程上：

- 四次调用各自只传入一句新的 `HumanMessage`，返回里却是完整的 8 条。历史由检查点提供，不由调用方拼接
- 第二句是「朕的国家怎么亡的？」，模型按秦始皇语境回答。未配置检查点、或不传同一 `thread_id` 时，这一句与「我是秦始皇」无关
- `input_tokens` 103 → 909 → 1940 → 2780，前缀在累积。这是 Agent底层逻辑第07章 prompt cache 能命中的那种「只在末尾追加」的列表，不是每轮重写
- 每条 `AIMessage` 仍带 `thinking` 块。检查点写入的是整份状态，满足 Agent底层逻辑第07章「上下文中应保留思维链」，不是只存 `.text`

## 读取状态

`ainvoke` 的返回值是当次 Run 结束时的状态。不执行图、只查看某条线程当前到哪一步，用 `get_state`；要看这条线程上每一枚检查点（含一次 Run 内部的中间超步），用 `get_state_history`。

```python
latest = graph.get_state(config)
latest
```

返回 `StateSnapshot`。完整 repr 同样很长。结构如下，冗长字段用省略号代替：

```text
StateSnapshot(
  values={'messages': [HumanMessage(...), AIMessage(...), ...共 8 条]},
  next=(),
  config={'configurable': {
    'thread_id': 'chat 1',
    'checkpoint_ns': '',
    'checkpoint_id': '...'
  }},
  metadata={'source': 'loop', 'step': ..., 'parents': {...}},
  created_at=datetime(...),
  parent_config={'configurable': {'thread_id': 'chat 1', 'checkpoint_id': '...'}},
  tasks=()
)
```

这次快照：

- `values`：该线程最新图状态，与最后一次 `ainvoke` 返回的 `messages` 一致
- `next=()`：没有待执行节点，本轮 Run 已结束。若停在中断（interrupt）上，这里会列出下一步要跑的节点名
- `config.configurable.checkpoint_id`：这一枚检查点自己的 id，与 `thread_id` 不是同一个东西。`thread_id` 标识会话，`checkpoint_id` 标识该会话里的某一快照

```python
history = graph.get_state_history(config)
history = [h for h in history]
history
```

`get_state_history` 返回迭代器，需物化成列表。默认最新在前：`history[0]` 与 `get_state` 相同；越往后消息越少，对应更早的超步。列表长度大于 Run 次数，因为一次 Run 会在 START 附近以及每个超步之后各写一枚检查点，而不只在 END 写一次。

## 与 Agent Server 的分界

本篇是进程内用法：`compile(checkpointer=InMemorySaver())`，调用方自己持有 `thread_id`。第05章的 Agent Server 会在运行时注入存储器，图代码不要再传入 `checkpointer`；Thread / Checkpointer / Run 改由服务的 HTTP 接口管理。两条路径不要混用。
