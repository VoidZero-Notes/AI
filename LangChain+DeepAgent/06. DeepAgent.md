Deep Agents（`deepagents`）是一套 Agent harness：在 LangChain 的 `create_agent` 之上，预先组装文件系统、子代理、Skill、记忆与上下文压缩，一次调用得到可 `invoke` 的已编译图。大模型单次请求只完成「输入 → 输出」；`create_agent` 补齐「推理—工具—观察」循环。长任务还需要步骤拆分、中间产物落盘、上下文隔离与按需加载领域指令，这些由默认 harness 提供。本篇说明如何用 `create_deep_agent` 得到该运行单元，并登记为 Agent Server 的图入口。

Agent底层逻辑第17章的 Harness Engineering 是「模型外面的环境：工具、护栏、验证」；Deep Agents 是把这件事落地的库之一。内部控制流仍是 Agent底层逻辑第10章的 ReAct，对外仍是第11章的 `invoke`。子代理对应第16章；Skill 对应第13章。运行时仍是 LangGraph：检查点对应 LangGraph第07章的线程和检查点，人在回路对应第23章（基于第22章的中断），Store 对应第26章，长期记忆对应第27章；经 Agent Server 部署对应 LangGraph第05章。`response_format` 同本目录第02章；额外中间件同第03章、第05章。

LangGraph、LangChain 与 Deep Agents 是同一条栈上的三层。第01章已列出 LangChain 基于 LangGraph 的核心功能：统一模型与消息、工具封装、以及 `create_agent` 工作流（`response_format`、中间件）。Deep Agents 基于该工作流构建，入口改为 `create_deep_agent`，把第05章清单中的文件系统、子代理、摘要等预置中间件组装为默认栈。

Deep Agents 基于 LangChain 构建，提供以下核心功能：

1. 执行环境：自定义工具、虚拟文件系统、路径权限、可选沙箱与代码执行
2. 上下文管理：Skill、Memory、摘要与大结果卸载、提示词缓存
3. 委派：子代理；任务规划（`TodoListMiddleware`）为可选
4. 人在回路：`interrupt_on` 在指定工具调用前暂停，接入 LangGraph 中断

需要自定义编排时用 LangGraph；需要标准循环并自行挑选中间件时用 `create_agent`；需要上述默认 harness 时用 `create_deep_agent`。

文档：[Deep Agents overview](https://docs.langchain.com/oss/python/deepagents/overview) · [Runtimes, frameworks, and harnesses](https://docs.langchain.com/oss/python/concepts/products) · [`create_deep_agent`](https://reference.langchain.com/python/deepagents/graph/create_deep_agent)

| 概念 | 作用 |
| --- | --- |
| harness | 预组装的工具、中间件、提示词与存储，包在 Agent 循环之外 |
| `create_deep_agent` | Deep Agents 入口。返回已编译的 LangGraph 图 |
| `create_agent` | LangChain 入口。同一循环，不含默认 harness 栈 |
| `backend` | 虚拟文件系统的存储实现，默认 `StateBackend` |
| `PatchToolCallsMiddleware` | 默认挂上的节点钩子。修补「已发出 `tool_call`、尚无 `ToolMessage`」的悬挂调用 |

## 安装

```bash
uv add deepagents
```

## 创建 Deep Agent

`create_deep_agent` 一次调用生成已编译的图。`model` 可与第01章相同，写成 `Provider:Model Name`，也可传入已构造的 Chat Model。工具、系统提示词、子代理、Skill、Memory、后端、检查点与 Store 均为选填。返回对象可直接 `invoke`，也可登记为 Agent Server 的图入口。`checkpointer` 与 `store` 经 Agent Server 部署时由服务注入，创建时无须传入。

```python
from deepagents import create_deep_agent

agent = create_deep_agent(
  model="anthropic:qwen3.7-plus",
)
```

> **说明：** 自 `deepagents` v0.7 起，任务规划不再默认开启。需要 `write_todos` 时，将第05章的 `TodoListMiddleware` 传入 `middleware`。

## 选填参数

| 参数名 | 含义 | 默认 |
| --- | --- | --- |
| `tools` | 额外工具，与内置文件系统等工具叠加 | 无额外工具 |
| `system_prompt` | 追加到默认 harness 指令之后 | 仅默认指令 |
| `middleware` | 额外中间件。`.name` 与内置项相同则替换该项，否则插入默认栈末尾 | 默认 harness 栈 |
| `subagents` | 自定义子代理 | 内置 `general-purpose` |
| `skills` | Skill 目录列表，按需加载 `SKILL.md` | 无 |
| `memory` | `AGENTS.md` 路径列表，启动时载入 | 无 |
| `backend` | 文件系统后端 | `StateBackend` |
| `permissions` | 路径级读写规则 | 无（默认允许） |
| `interrupt_on` | 指定工具调用前中断 | 无 |
| `response_format` | 结构化输出，同第02章 | 无 |
| `state_schema` | 图状态结构 | `DeepAgentState` |
| `context_schema` | context 结构，对应 LangGraph第12章 Runtime | 无 |
| `checkpointer` | 检查点。使用 Agent Server 时无须传入 | 无 |
| `store` | Store。使用 Agent Server 时无须传入 | 无 |

## 工程文件

### Agent 入口

`langchain_project/agents/coding_agent.py`：用 `create_deep_agent` 组装编码场景的 Deep Agent。模型取自配置，经 `init_chat_model` 关闭 thinking 后传入。

```python
from deepagents import create_deep_agent
from langchain.chat_models import init_chat_model
from langchain_project.core.config import anthropic_settings

model = init_chat_model(
  model=anthropic_settings.default_model,
  model_provider="anthropic",
  thinking={"type": "disabled"},
)

agent = create_deep_agent(model=model)
```

## 修补悬挂的 tool_call

`create_deep_agent` 会自动挂上 `PatchToolCallsMiddleware`。它是第03章的节点钩子：编译为 `PatchToolCallsMiddleware.before_agent`，每次 `invoke` 开始时运行一次，位于 `model` 之前。

只做一件事：检查 `messages` 里有没有「模型已经发出 `tool_call`，但还没有对应 `ToolMessage`」的悬挂调用。

- 有悬挂：把历史复制一份，在悬挂的 `AIMessage` 之后插入一条表示未完成的 `ToolMessage`，再用 `RemoveMessage(id=REMOVE_ALL_MESSAGES)` 整表替换。Studio 会先显示 Deleted Message，再显示替换后的列表。
- 无悬挂：`return None`。LangGraph 不当作状态更新（第03章：节点钩子返回 `None` 表示不更新状态），Studio 只显示节点执行成功、内容为空。

不修补的话，下一轮把带 `tool_calls` 的 `AIMessage` 与新的用户消息一起发给模型，输出会错乱；OpenAI、Anthropic 等服务商也会直接拒绝该请求。

### 为何必须整表替换

Agent底层逻辑第08章的 Tool Calling、LangGraph第08章的工具节点都要求：带 `tool_calls` 的 `AIMessage` 后面必须有与 `tool_call_id` 对应的 `ToolMessage`。取消发生时，旧的 `tool_call` 已在历史里，新的 `HumanMessage` 已经追加到末尾，配对被打断。

不能只把补丁追加到列表末尾。追加后顺序会变成：

```text
AIMessage(tool_calls=[fetch_url])
HumanMessage("继续")
ToolMessage(...)          # 落在新用户消息之后，位置非法
```

协议要求 `ToolMessage` 紧跟发出它的 `AIMessage`。因此必须复制整份历史，把补丁插进中间，再一次性写回：

```text
AIMessage(tool_calls=[fetch_url])
ToolMessage(...)          # 插在这里
HumanMessage("继续")
```

对应 LangGraph第04章的 `add_messages`：先发 `RemoveMessage(id=REMOVE_ALL_MESSAGES)` 清空通道，再写入复制并打过补丁的列表。Studio 把这条哨兵显示为 Deleted Message：`REMOVE`，`Message ID "...remove_all..." has been deleted`。对话并未丢弃，只是同一份历史被整表写回，并多了未完成说明。

```python
# 无悬挂
return None

# 有悬挂
return {
  "messages": [
    RemoveMessage(id=REMOVE_ALL_MESSAGES),
    *patched_messages,
  ]
}
```

补丁是一条 `ToolMessage`，`status="error"`，正文当前为：

```text
Tool call {name} with id {tool_call_id} did not complete - no result was recorded. It may have been cancelled or interrupted.
```

较早版本写的是 `was cancelled - another message came in before it could be completed`。`invalid_tool_calls`（参数畸形或截断）另有一条 `could not be executed` 文案。无悬挂时这段不执行，不会出现 Deleted Message。

### 示例：工具调用中取消后再继续

TURN 1 输入「帮我查一下历年来法拉利车手的积分情况」。线程首轮没有悬挂调用，`before_agent` 返回 `None`。`model` 发出 `web_search`，`tools` 执行成功并写回 `ToolMessage`；再次 `model` 发出 `fetch_url` 后，在 `tools` 节点取消，得到 `CancelledError`。此时状态里已有带 `tool_calls` 的 `AIMessage`，没有对应 `ToolMessage`。

![image-20260916234333354](https://ipic-typora.oss-cn-shenzhen.aliyuncs.com/jishu-img/2026-09-16-154333.png)

TURN 2 输入「继续」。`before_agent` 发现悬挂的 `fetch_url`，写出 Deleted Message 并重建列表：原 `Human` 与 `web_search` 配对保留，在 `fetch_url` 的 `AIMessage` 后补上未完成的 `ToolMessage`，最后才是「继续」。此后 `model` 看到的是合法配对，可以继续作答。

### 节点何时有输出

| 上一轮停在哪 | 状态里有没有未配对的 `tool_call` | 下一轮 `before_agent` |
| --- | --- | --- |
| 取消发生在 `model` 调用本身（`CancelledError` 出现在 model 节点）。带 `tool_calls` 的 `AIMessage` 通常尚未写入 | 无 | `return None`，Studio 内容为空 |
| 取消发生在 `tools`：模型已经发出 `tool_call`，工具还没执行完或 `ToolMessage` 还没写入，随后又发了新消息 | 有 | 整表替换，Studio 可见 Deleted Message 与补丁 `ToolMessage` |
| 工具已正常返回 `ToolMessage` | 无 | `return None` |
| 线程首轮，历史里还没有 `AIMessage.tool_calls` | 无 | `return None`（上例 TURN 1 即此种） |

只有上一次已经发出 `tool_call`、还没执行完工具、又发了新消息时，这个节点才会有内容。上例 TURN 1 的 `CancelledError` 在 `tools` 节点，属于表中第二行，所以 TURN 2 的 `before_agent` 能看见 Deleted Message。若取消发生在模型调用本身、尚未写出带 `tool_calls` 的 `AIMessage`，下一轮 `before_agent` 仍返回 `None`。

### 为何模型答到一半不必修补

差在协议约束和检查点写到哪一步，不是「半截输出」本身。

普通文本没有配对规则。`Human → AI（半句）→ Human（继续）` 是合法历史，服务商不会拒绝。模型只是看见上一段没说完，接着写即可。`tool_calls` 有硬性配对：带 `tool_calls` 的 `AIMessage` 后面必须有对应 `tool_call_id` 的 `ToolMessage`。`Human → AI(tool_calls) → Human` 非法，OpenAI / Anthropic 会直接返回 400，所以才要补一条未完成的 `ToolMessage`。

取消时状态停在上一成功超步（LangGraph第06章的超步、第07章的检查点）。Studio 里能看到的半截流式输出，是当次 Run 的事件，不一定已经写入线程的 `messages`。

| 取消位置 | 已提交到线程的状态 | 下一轮 |
| --- | --- | --- |
| `model` 还在生成 | 上一个检查点里通常还没有这条 `AIMessage` | 历史仍是完整对话，没有悬挂，不必修补 |
| `tools` 还在执行 | `model` 节点已经成功返回，带 `tool_calls` 的 `AIMessage` 已经进状态；`ToolMessage` 还没有 | 出现悬挂，必须修补 |

因此：模型答到一半就取消，下一轮多半像「上次什么都没说」，再发「继续」即可。工具没调完，上一轮的调用意图已经落盘，不补 `ToolMessage` 就会把非法配对送给模型。

唯一接近「模型半截也要修」的情况：半截输出被写成了带残缺 `tool_calls` / `invalid_tool_calls` 的 `AIMessage`。`PatchToolCallsMiddleware` 连这一支也会补，文案是参数畸形或截断，不是普通文本中断。
