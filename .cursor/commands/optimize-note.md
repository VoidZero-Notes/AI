**禁止删除用户给出的任何代码（最高优先级，先于其后全部条款）。违反本条即任务失败，不得交付。**

**用户贴进目标 `.md` 的代码、通过 `@` 附上的源码、以及配图，优化后必须全部出现在成稿中。** 允许且仅允许：改缩进、围栏语言标签、连续空行、去 Tab、书面语替换说明文字。 **禁止整段删代码、禁止漏示例、禁止把未归位内容当「文末原始粘贴 / 重复 / 范围之外」截断。**

归位 ≠ 删除：先把每一段代码与每一张图嵌进对应小节，再看文末是否还有残留。文末仍有未嵌入的代码或图片时，**禁止截断文件**。编号跳号（如只写入 demo1 / demo3）即为漏删，必须回头补全。

自检：原文每一个代码围栏、每一份 `@` 源码、每一张配图，成稿中都能找到对应块。缺一块不得结束。

优化当前指定的 AI 技术笔记 Markdown：统一为已优化笔记的体例。不补语言类比、不补对照侧代码。

## 输出禁令（硬性）

写入目标 `.md` 的全部正文、以及回复用户的结论，禁止口语。下列说法不得出现在输出中（命令本文的对照表不算输出）：

`吃`（作谓语：吃数字、吃进、吃的就是）、`收`（作谓语：要收的是、这一篇在收、收成、收进、再收）、`交卷`、`账本`、`丢进`、`塞进`、`一股脑`

不误伤规范词：收敛、接收、吸收、收集、收益。

落笔后必须对目标文件检索上述口语；命中则改完再结束，禁止带着口语交付。

## 输入

- 用户会 `@` 一个或多个待优化的 `.md` 文件
- 若未指定文件，先询问要优化哪几个，禁止自行选择

## 风格锚点（必须先读）

在同目录（或同级已优化笔记）中，任选 **1～2 个已优化样本** 作为体例标准。

以这些文件的实际写法为准，不得另行拟定体例。若同目录尚无已优化样本，以当前文件自身的章节逻辑为准，只做格式、结构与书面语统一。

书面语要求优先于锚点样本中的口语习惯：样本若仍使用「吃」「收」等口语，优化当前篇时仍须改为书面表述，不得沿用。

## 必须完成的改造

1. **书面语**
   - 优化后的笔记、以及回复用户的结论，必须是专业技术书面语
   - 禁止口语、课堂口头禅、网络缩略说法，以及用生活化动词代替技术表述
   - 这是**语域转换**：同一命题、同一论证，将口语换成规范术语。不得借此更换大纲、更换讲法、扩写成另一篇教程
   - 规范术语与已定义概念保持不变（如 Token、Agent、ReAct、收敛、接收、收益）
   - 「吃」「收」仅指口语谓语，不误伤含这些字的规范词（收敛、接收、吸收、收集、收益）

   常见口语须改为书面表述（同类类推，不限于下表）：

   | 口语 | 书面 |
   | ---- | ---- |
   | 吃（作输入） | 接收 / 作为输入 / 纳入 |
   | 收、要收的是、这一篇在收 | 本篇说明 / 本篇要解决 / 覆盖 |
   | 收成、收进 | 封装为 / 归纳为 / 转换为 / 写入 |
   | 交卷 | 返回结果 / 汇总结果 |
   | 账本（指 Session） | 会话记录 / 消息历史 |
   | 丢进、塞进 | 传入 / 写入 |
   | 一股脑 | 全部 |
   | 跑通 | 完成最小可运行示例 |
   | 接线（非电路语境） | 编排 / 连接 |

   示例：

   | 原文 | 改为 |
   | ---- | ---- |
   | 神经网络只吃数字。 | 神经网络只接受数值输入。 |
   | 下一个 Block 吃的就是这个 $4 \times 6$。 | 下一个 Block 的输入即为该 $4 \times 6$ 矩阵。 |
   | 16 要收的是：把大任务切成若干独立轮次。 | 本篇要解决的问题是：将大任务切分为若干独立轮次。 |
   | 把一轮次收成 `Agent.invoke`。 | 将一轮次封装为 `Agent.invoke`。 |
   | 全部 `join` 完再交卷。 | 全部 `join` 完成后再汇总结果。 |
   | 父代理的账本不收这些中间过程。 | 父代理的会话记录不纳入这些中间过程。 |

2. **结构体例**
   - 章节之间不要用单独的 `---` 分隔线（与已优化样本一致）
   - 标题一律不带序号：禁止 `## 0. 全景总览` `## 1. 哲学流派` `### 1.1 xxx` 等形式，直接写 `## 哲学流派`、`### 符号主义`
   - 不使用一级大标题（`# 标题`）作为文首标题；文档以一段引言正文开头，再用 `##` / `###` 分节（与已优化样本一致）
   - 保留原有章节逻辑与作业 / 练习；整体按用户的格式和内容走，不要重写成另一篇
   - 不删减教学内容，不借机大改大纲（纠错、补重要缺口、调段落位置、书面语转换除外，见第 1、8、9 条）。**用户给出的代码与配图不在此例外内：只可格式化与挪位，不可删除**
   - 不补 JavaScript / TypeScript / Node.js / Python 等语言类比，不补对照侧代码块
   - 文首概念表默认不补。仅当表是后文反复用到的术语索引（多项 API 名、枚举、模式），且不是把引言再抄一遍时，才保留原文已有的表，或补一张。禁止为「看起来像总览」而编表。不要编造「语言对照表」

3. **开头范式：先自述，再必要时对比**
   - 文首第一段必须先给出本篇主题的自足总述——这是什么、解决什么问题、大致包含哪些内容；不依赖「前几章讲了什么」就能读懂这一段
   - 禁止用「第 X 章覆盖 A / B / C / D，本篇再讲 E」这类章节清单式开场当引子；这是位置性的对比陈述，不是总述，必须改写成先说本篇主题本身
   - 判断是否保留某处前序章节引用，看它是否在说明一个真实的技术依赖或演变关系（例如「这一步搭在第 07 章的检查点机制上」「这是第 02 章 → 第 03 章 → 第 04 章一路演进后的最后一步」）：
     - 是：保留这层对比，但放在自述之后的句子/段落里作为补充说明，不放在开篇第一句
     - 不是（纯粹交代「本篇排在第几篇、前面几章分别讲了什么」的位置性陈述）：删除，或压缩为自述句里的一个从句
   - 前序对比若确有必要保留，且信息量较大（如多章演进链条），可以留在第二段，不必强行塞进第一句
   - 跨目录对应默认不写进开篇（见第 7 条）。确有必要的那一句，放在自述之后，禁止用章节清单代替总述
   - 参考锚点：已优化样本文首若是先给出自足定义、再讲来源或依赖关系，即为本条要达到的效果；不要另立新样式

4. **缩进统一为 2 空格**
   所有代码块内缩进改为 2 空格；删除 Tab；不要混用 4 空格。

5. **空行收敛（硬性，无例外）**
   正文与代码块内，连续空行最多保留 **1 个**（段落之间、逻辑分组之间用单个空行隔开）。连续 2 个及以上空行一律压成 1 个。

   禁止以任何理由保留双空行，包括但不限于：PEP8 顶级函数空两行、分隔独立示例、区分错误/正确示例、锚点样本同一位置用了双空行、版式宽松。

   规则：
   - **代码块内外同一标准**：Markdown 正文与代码块内部都要处理
   - **禁止删除全部空行**：该分段的地方仍保留 1 个空行，避免段落粘连
   - **禁止连续 2 个及以上空行**：任何位置都不允许
   - 工程源码贴进笔记时同样适用，不按 PEP8 空两行保留

6. **代码围栏**
   - 语言标签要准确（如 `python`、`ts`、`js`、`bash`、`json`、`text`）
   - 不要为了版式把说明文字塞进代码块
   - 需要补充差异或易错点时用简短引用块 `> **说明：** ...`

7. **笔记互引与跨目录对应**
   - 引用**当前目录**的笔记：可直接写序号，如 `10`、`10 的 ReAct`
   - 引用**其他目录**的笔记：必须写清「目录 + 第几章 + 主题」，禁止只写目录名加数字。正确：`Agent底层逻辑第10章的 ReAct`、`Agent底层逻辑第17章的 Harness Engineering`。错误：`10`、`Agent底层逻辑 10`（无法判断 10 是第几章、主题是什么）
   - 优化时检查已有引用：跨目录却没写「第几章 + 主题」的，按上面改掉
   - **禁止硬凑对应**：默认不主动补跨目录对应，也不把本目录前后章再列成对照清单。可以没有。仅当同时满足下列条件才写：
     1. 本篇的核心机制，就是在实现另一目录某一章已经讲过的那个概念（不是「凡出现 ReAct / 工具 / 图入口 / 检查点就标注」）
     2. 不写这一句，读者会把两套讲法当成两件事
     3. 一句话能说清「实现了什么、来自哪一章」；写不成一句，说明没有必要
   - 下列情况一律不写、已有则删：
     - 每篇都适用的背景（内部控制流是 ReAct、图入口经 Agent Server、工具走 Tool Calling、状态靠检查点）
     - 把本目录的参数、钩子、后端、沙箱再枚举一遍的章节清单
     - `langgraph.json` 旁例行补「对应 LangGraph第05章的 Agent Server」
     - 概念在后文马上定义，文首概念表只是把引言再抄一遍
   - 写法（仅在确有必要时）：同时说出「实现了什么」和「来自哪一章」。正确：`Agent底层逻辑第17章的 Harness Engineering 是「模型外面的环境：工具、护栏、验证」；Deep Agents 是把这件事落地的库之一。` 错误：只提概念不标章节；或标注到并无对应的篇；或一篇开篇堆多条对应

8. **纠错与补缺（以用户原文为底）**
   - 发现写错、示例输出不对、概念不成立、或漏了比较重要且本篇主题已经碰到的点：可以直接改、可以直接补
   - **底线**：按用户的格式和内容来。补的是缺口、改的是错处，不是换一套讲法、换一个大纲、把原文替换掉
   - 禁止：整段更换论证结构、扩成另一章的教程、借「完善」塞进用户没在讲的旁支。书面语转换、开头范式改写不属于更换讲法
   - 改完必须在结论里**逐条**说明：改了什么、完善了什么、加了什么（原文哪句/哪段 → 改成什么、为什么）。没有内容改动则写「未改内容」。书面语替换须单独列出主要条目，不得只写「润色了行文」

9. **调整段落位置**
   - 某段放在别的小节更合适（例如概念定义散在示例后、该跟图走的说明离图太远）：可以直接挪，不改句子本身也算允许
   - 只调位置、不改含义时，结论里仍要说明：哪一段从哪挪到了哪、原因是什么
   - 调整后须保持上下文连贯
   - **挪走原文之后，禁止把尚未嵌入的剩余代码/配图一并截掉**

10. **直接改文件**
    原地更新目标 `.md`，不要只输出 Diff 而不写入。写入后检索输出禁令中的口语；若仍出现，当场改掉，不得交付含口语的正文。

- [ ] **用户给出的每一段代码、每一份 `@` 源码、每一张配图均已保留**（缺一块即失败）
- [ ] 无 `\t`
- [ ] 代码缩进为 2 空格
- [ ] 无语言类比、无对照侧代码块
- [ ] 章节之间无单独 `---` 分隔线
- [ ] 标题无序号，且文首无一级大标题（以引言正文开头）
- [ ] 文首第一段是自足总述，不是「第 X 章覆盖 A/B/C/D」式的章节清单开场；确有必要的前序对比已挪到自述之后
- [ ] 未把原文整篇换掉；纠错/补缺仍贴着用户的章节与讲法
- [ ] 体例与锚点样本一致（若有样本）；口语习惯以本命令书面语条款为准，不以样本中的口语为准
- [ ] 跨目录引用若保留，已写成「目录 + 第几章 + 主题」；同目录引用可只写序号
- [ ] 未硬凑跨目录对应与文首概念表；仅在确有必要时保留，没有则可以没有
- [ ] 连续空行已收敛：任意位置最多 1 个空行；无连续双空行及以上
- [ ] 已对目标文件检索输出禁令：正文与结论均不出现「吃」「收」（口语义）、「交卷」「账本」「丢进」「塞进」「一股脑」

完成后在结论里交代，不要只说「优化了格式」。结论本身也必须使用书面语，禁止口语与课堂口头禅：

1. 改了哪些文件
2. 体例 / 格式类改造（缩进、空行、标题、围栏等）
3. 开头范式：文首开场是否从章节对比式改写为自足总述；原本合理的前序对比挪到了自述之后的哪一句
4. 书面语：列出主要替换（原文 → 改为）；若原文已是书面语则写「原文已是书面语，未改语域」
5. 段落位置：哪一段从哪挪到哪（没有则省略）
6. 内容：逐条写「改了什么 / 完善了什么 / 加了什么」；没有则写「未改内容」
7. 跨目录对应与文首概念表：写明保留了哪一句/哪张表（及为何必要），或写明删了什么（及为何不必要）；两者都没有则写「无跨目录对应、无文首概念表」
8. **用户代码与配图：逐项确认均已保留**；若有挪位，写明从哪移到哪。不得写「文末原始粘贴已删除」而不交代每一段代码的去向
